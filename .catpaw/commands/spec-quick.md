# CarryHub Spec Quick 流程

## 基本原则

- 所有输出内容使用**中文**
- 优先最简实现，不过度设计
- 三个强制交互节点：**Step 3（范围确认）**、**Step 7（design.md 确认）**、**Step 10（参考代码收集）**，必须等用户明确确认后才能继续
- 严格遵守项目工程规范（Rules 文件已自动加载）

---

## 阶段识别

根据用户输入判断进入哪个阶段：

**文档生成阶段**（Steps 1–8）：
- 用户描述一个功能想法或需求（自然语言）
- 用户提到"写 spec"、"帮我想清楚"、"生成设计文档"等

**实现阶段**（Steps 9–14）：
- 用户提到"开始写代码"、"实现"、"继续"
- 用户指定了 change-id 且 design.md / tasks.md 已存在

识别后直接进入对应阶段，不需要二次确认。

---

## 文档生成阶段

### Step 1：接收功能描述

接受用户用自然语言描述的功能想法，不要求任何格式。

**可选补充材料**（用户有则利用，没有不追问）：
- UI 原型图 / 设计稿截图
- 接口文档（URL 或文字描述）
- 相关参考页面路径

---

### Step 2：结构化追问（澄清阶段）

这是最关键的一步。对用户描述进行**结构化歧义扫描**，找出影响实现的模糊点并主动追问。

**扫描维度**（内部执行，不对用户展示原始 map）：

| 维度 | 检查项 |
|------|--------|
| 功能边界 | 核心目标是什么？明确排除哪些功能？ |
| 用户与权限 | 哪些租户类型可用（buyer / personal_enterprise / org_enterprise）？角色差异（admin vs member）？ |
| 数据与状态 | 涉及哪些实体？有哪些状态流转？ |
| 交互流程 | 关键用户路径？空态 / 加载态 / 错误态如何处理？ |
| 接口依赖 | 需要哪些后端接口？接口已有还是待定？ |
| 边界与异常 | 并发、权限不足、数据为空时如何处理？ |

**追问规则**：

1. 每次只问**一个问题**，等用户回答后再问下一个
2. 每个问题提供**推荐选项**（基于项目规范和最佳实践），格式：
   > **推荐**：选项 X —— 理由（1 句话）
   >
   > | 选项 | 说明 |
   > |------|------|
   > | A | ... |
   > | B | ... |
   >
   > 可直接回复选项字母，或输入自己的答案（不超过 10 字）。
3. 最多追问 **5 个问题**，只问影响架构/实现方向的，不问细节样式偏好
4. 如果用户说"你来决定"或"推荐"，直接用推荐选项，记录在案

---

### Step 3：范围确认（强制交互节点 ①）

追问结束后，扫描代码库确认涉及页面是新建还是迭代，向用户呈现：

**1. 背景与目标**（1–2 句）

**2. 影响范围**

| 页面 / 模块 | 场景 | 现有路径 | 变更内容 |
|------------|------|---------|---------|
| xxx 列表页 | 🆕 新建 | — | 完整实现 |
| yyy 详情页 | 🔄 迭代 | `packages/bid/src/pages/Detail/` | 新增 xx 字段 |

**3. 所属子包**：确认功能放在哪个子包（enterprise / bid / opportunity / tenant-admin）

**4. 决策记录**（追问阶段的最终答案汇总）

> ⏸ **等待用户确认后继续**
> 如有偏差请直接指出，我来修正。

---

### Step 4：生成 change-id 并创建目录

根据功能内容自动生成 change-id：
- kebab-case，动词开头（add- / update- / remove- / refactor-）
- 简洁描述功能

```bash
mkdir -p spec/changes/<change-id>
```

---

### Step 5：分析 UI 图（如有）

若用户提供了设计稿或原型图，读取并执行
`.catpaw/skills/spec-analyze-ui-images/SKILL.md` 进行系统化分析。

---

### Step 6：生成 design.md

在 `spec/changes/<change-id>/design.md` 生成技术设计文档，结构如下：

```markdown
# <功能名称> 技术设计

## 1. 功能概述
<!-- 1-3句：解决什么问题，面向哪类用户 -->

## 2. 涉及模块
<!-- 子包名称 + 页面列表 -->

## 3. 页面设计

### <页面名>
#### 功能描述
<!-- 该页面做什么 -->

#### 交互流程
<!-- 用 EARS 语法描述关键场景 -->
<!-- When <触发条件>, the system shall <系统行为> -->

#### 组件结构
<!-- 页面级组件树，标注私有组件路径 -->

#### 状态管理
<!-- 本地状态 / Zustand store / Context，说明选择理由 -->

## 4. 接口设计

### <接口名>
- **方法**：GET / POST / PUT / DELETE
- **路径**：`/api/xxx`
- **所属子包**：`packages/<sub>/src/api/`

```typescript
// 请求参数
interface XxxRequest {
  // ...
}

// 响应数据
interface XxxResponse {
  // ...
}
```

> ⚠️ 缺少接口：<描述缺失的接口场景>（若有）

## 5. 类型定义
<!-- 本次新增的 TS 类型，标注放在哪个文件 -->

## 6. 权限控制
<!-- 涉及哪些租户类型 / 角色，用 usePermission 还是 PermissionRoute -->

## 7. 关键决策记录
<!-- 追问阶段的结论，方便后续回溯 -->
```

---

### Step 7：确认 design.md（强制交互节点 ②）

生成后向用户展示核心内容摘要（模块列表 + 页面清单 + 接口映射）。

> ⏸ **等待用户确认后继续**
> 若有问题请指出，修正后再生成 tasks.md。

---

### Step 8：生成 tasks.md

在 `spec/changes/<change-id>/tasks.md` 生成实现任务清单：

```markdown
# <功能名称> 实现任务

## 任务清单

### <子包名>/<页面名>

#### 1. 文件结构
- [ ] 创建 `packages/<sub>/src/pages/<Page>/index.tsx`
- [ ] 创建 `packages/<sub>/src/pages/<Page>/components/<Component>.tsx`
- [ ] 创建 `packages/<sub>/src/api/<feature>.ts`

#### 2. 类型 & 接口
- [ ] 定义 `<TypeName>` 接口（`api/<feature>.ts`）
- [ ] 实现 `<apiFunc>()` 请求函数（使用 bizAxios）

#### 3. UI & 业务逻辑
- [ ] 实现 <区域名> 区域
  - 使用组件：`<AntdComponent>`，关键 props：`xxx`
  - 关键逻辑：`<描述>`
- [ ] 处理加载态 / 空态 / 错误态

#### 4. 路由配置
- [ ] 在 `packages/<sub>/src/router/index.tsx` 添加路由（懒加载）

#### 5. Mock 数据（开发阶段）
- [ ] 在 `packages/shared/src/mocks/` 新增 handler

---
完成所有任务后将 `- [ ]` 改为 `- [x]`
```

输出完成后告知用户文件路径，并提示可以用 `/code-gen` 开始逐文件实现。

---

## 实现阶段

### Step 9：前置检查

确认 change-id，检查 `spec/changes/<change-id>/design.md` 和 `tasks.md` 是否存在。

若缺失：询问用户是否先生成文档，或直接进入实现（用户自有方案时）。

---

### Step 10：收集参考代码（强制交互节点 ③）

在开始写代码前，询问用户是否有可参考的存量代码，以确保生成代码与项目已有风格、工具链保持一致。

**主动询问以下内容**（按优先级排列，用户有则利用，没有不强求）：

| 优先级 | 参考内容 | 用途 |
|--------|---------|------|
| 🔴 高 | 后端框架示例（Express 路由、中间件、错误处理结构） | 复用项目约定的代码组织方式 |
| 🔴 高 | 前端项目结构示例（Webpack 配置、入口、路由写法） | 避免重复配置，风格统一 |
| 🟡 中 | 认证/身份方案（token 存储、localStorage key、请求头格式） | 与存量项目保持兼容 |
| 🟡 中 | OSS / 文件上传封装（如已有） | 直接复用，避免重复实现 |
| 🟢 低 | 前端监控接入方式（如已有 SDK） | 在新页面中统一接入 |

**用户提供方式**：
- `@文件路径` 或 `@目录路径` — AI 自动读取
- 粘贴关键代码片段到对话中
- 告知项目路径，AI 主动读取

收到参考代码后：
1. 提取关键约定（命名规范、工具函数、配置模式）并记录
2. 告知用户已读取哪些内容、将如何复用
3. 用户确认或补充后，进入 Step 11

若用户明确表示无参考代码，直接进入 Step 11。

> ⏸ **等待用户提供参考代码或确认跳过后继续**

---

### Step 11：询问补充材料

询问是否有设计稿截图等补充材料。

---

### Step 12：分析 UI 图（如有）

执行 `.catpaw/skills/spec-analyze-ui-images/SKILL.md` 分析用户提供的 UI 截图。

---

### Step 13：按 tasks.md 逐步实现

- 每次实现一个页面，完成后等用户确认再继续下一个
- 严格遵守项目 Rules（bizAxios、usePermission、子包边界等）
- 优先复用 Step 10 中收集到的参考代码风格与工具封装
- 实现完成后在 tasks.md 中将对应任务标记为 `- [x]`

---

### Step 14：完成确认

所有任务完成后：
1. 确认 tasks.md 全部勾选
2. 告知用户功能已实现完毕
3. 提示下一步：联调 / Mock 验证 / `/note` 记录踩坑
