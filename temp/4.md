# CoWatch 录屏音频同步后录制时长异常问题记录

## 一、问题概述

在引入 `audio_capture.exe`（WASAPI Loopback）实现系统声音录制后，录制时长出现异常：

| 实际录制时长 | 最终视频时长 | 现象 |
|-------------|-------------|------|
| 12秒 | 10秒 | 最后一片丢失 |
| 15秒 | 10秒 | 最后一片丢失 |
| 18秒 | 20秒 | 多了一片（静音/噪音频） |
| 16秒 | 10秒 | 最后一片丢失 |

**关键线索**：问题只在引入音频后出现，之前无音频时（仅视频 gdigrab）录制时长完全正常。

## 二、当前架构

```
audio_capture.exe (WASAPI Loopback)
        ↓ stdout (PCM s16le, 48kHz, 2ch)
        ↓ pipe:0
ffmpeg (gfxcapture + pipe:0)
        ↓ HLS segments
        seg000.ts, seg001.ts, ...
```

**FFmpeg 命令行参数**：
```bash
-f s16le -ar 48000 -ac 2 -i pipe:0 \
-f lavfi -i gfxcapture=window_title=xxx:max_framerate=30,fps=30,hwdownload,format=bgra,scale=... \
-af aresample=async=1:min_hard_comp=0.100:first_pts=0 \
-map 0:a -map 1:v \
-c:v h264_qsv -global_quality 28 \
-c:a aac -b:a 128k \
-g 300 \
-f hls -hls_time 10 -hls_list_size 0 \
-seg%03d.ts index.m3u8
```

## 三、尝试过的停止顺序

### 方案1：先写 'q'，再停 audio_capture（原始逻辑）
```javascript
ffmpegProcess.stdin.write('q', () => {
  audioCaptureProcess.kill('SIGINT');
  ffmpegProcess.stdin.end();
});
```
**结果**：录制18秒→视频20秒，多了一片（静音）

### 方案2：先停 audio_capture，再写 'q'
```javascript
audioCaptureProcess.kill('SIGINT');
ffmpegProcess.stdin.write('q');
ffmpegProcess.stdin.end();
```
**结果**：录制12秒→视频10秒，最后一片丢失

### 方案3：先写 'q'，等待500ms，再停 audio_capture
```javascript
ffmpegProcess.stdin.write('q');
ffmpegProcess.stdin.end();
setTimeout(() => {
  audioCaptureProcess.kill('SIGINT');
}, 500);
```
**结果**：录制18秒→视频20秒，多了一片

### 方案4：添加 -shortest 参数
```bash
-shortest  # 当任一输入流结束时停止编码
```
**结果**：录制18秒→视频8.49秒，音频延迟导致视频被截断

### 方案5：先停 audio_capture，等待200ms，再写 'q'
**结果**：录制12秒→视频10秒，最后一片丢失

## 四、问题根因分析

### 核心矛盾

ffmpeg 有两个输入源：
1. **音频**：`pipe:0`（来自 audio_capture.exe）
2. **视频**：`gfxcapture`（lavfi 滤镜，无限流）

当 ffmpeg 收到退出命令（'q'）时，需要等待**所有输入流结束**才能退出。但 `gfxcapture` 是 lavfi 滤镜，会一直提供数据，所以：

- **方案1（先写 'q'）**：ffmpeg 收到 'q' 后等待所有输入结束，但 gfxcapture 不会结束，所以继续录制直到 audio_capture 停止，此时已经多录了一段时间
- **方案2（先停 audio_capture）**：pipe:0 关闭，ffmpeg 收到 EOF，但此时写 'q' 可能已经无效（stdin 已关闭），导致 ffmpeg 立即退出，未完成最后一片写入

### HLS 切片机制

```
hls_time=10 → 每片10秒
录制12秒 → 应该生成：seg000.ts(10s) + seg001.ts(2s)

实际情况：
- 最后一片（seg001.ts）未生成或未上传
- 原因：ffmpeg 退出时未完成最后一片的写入和 m3u8 更新
```

### 与无音频时的对比

**无音频时（gdigrab）**：
```bash
-f gdigrab -i title=xxx  # 单个输入源
```
写 'q' 后 ffmpeg 立即退出，完成最后一片写入。

**有音频时（pipe:0 + gfxcapture）**：
```bash
-f s16le -i pipe:0 -f lavfi -i gfxcapture=xxx  # 两个输入源
```
写 'q' 后 ffmpeg 需要等待两个输入都结束，但 gfxcapture 不会结束。

## 五、可能的解决方案

### 方案A：使用 SIGTERM 强制终止（不推荐）
```javascript
ffmpegProcess.kill('SIGTERM');
```
**问题**：Windows 上 SIGTERM 等于 SIGKILL，会强制终止进程，导致数据丢失。

### 方案B：修改 gfxcapture 为有限流
```bash
-f lavfi -i gfxcapture=xxx:duration=10  # 但录制时长不确定
```
**问题**：录制时长是用户控制的，无法预先确定。

### 方案C：使用 -t 参数
```bash
-t 12  # 录制12秒
```
**问题**：录制时长是用户控制的，无法预先确定。

### 方案D：不使用 pipe，改为文件中间存储
```javascript
// audio_capture 输出到文件
audio_capture.exe --output audio.raw
// ffmpeg 从文件读取
ffmpeg -f s16le -i audio.raw ...
```
**问题**：需要同步两个进程的启动和停止，复杂且可能引入新问题。

### 方案E：使用 -shortest 并修复音频延迟
```bash
-shortest
# 同时优化 audio_capture 的启动延迟
```
**问题**：音频延迟是 WASAPI Loopback 的固有问题，难以完全消除。

### 方案F：恢复 gdigrab + 外部音频文件
```bash
# 录制时：
audio_capture.exe --output audio.wav  # 单独录制音频
ffmpeg -f gdigrab -i title=xxx ... video.mp4  # 单独录制视频

# 停止后：
ffmpeg -i video.mp4 -i audio.wav -c:v copy -c:a aac output.mp4  # 合并
```
**问题**：需要额外的合并步骤，增加复杂度。

### 方案G：使用 Media Foundation Capture
```bash
-f dshow -i audio="麦克风阵列"  # 但无法录制系统声音
```
**问题**：dshow 无法录制系统声音（缺少 AUDCLNT_STREAMFLAGS_LOOPBACK）。

## 九、根本原因

本质是**进程间信号的时序竞争（Inter-Process Race Condition）**。

FFmpeg 内部维护一个多路输入的 demuxer，两个输入流（`pipe:0` 音频 + `lavfi` 视频）在独立线程中并发读取。当 `audio_capture` 被 kill 后，`pipe:0` 产生 EOF 信号，该信号需要经过以下路径才能真正影响 muxer 的状态：

```
audio_capture 进程退出
  → OS 关闭管道写端
    → FFmpeg 读线程读到 EOF（fd 层）
      → FFmpeg demuxer 标记音频流 finished
        → FFmpeg muxer 感知到所有流已结束（lavfi 不会结束，仅音频）
```

这条链路在 OS 调度下是**异步**的，延迟约 0~50ms。若在此期间立即发送 `q`，FFmpeg 收到退出命令时音频流尚未被标记为 finished，muxer 的状态机处于不一致的中间态：

- **lavfi 仍在产生帧**：FFmpeg 不会因为 `q` 立刻停止采集，而是等当前 GOP 写完
- **音频 EOF 未消化**：muxer 不知道该在哪里截断，随机多写或少写一个 HLS 分片

这不是 FFmpeg 的 bug，而是多路输入架构下停止语义本身的模糊性：**`q` 只是请求退出，不是强制截断点**。

## 十、修改方案

在 `cleanup()` 的 Windows 分支中，将两步操作之间插入 200ms 延迟：

```typescript
// 步骤1：关闭 audio_capture，触发 pipe:0 EOF
audioCaptureProcess.kill('SIGINT');
audioCaptureProcess = null;

// 步骤2：等待 FFmpeg 消化音频 EOF，再触发优雅退出
setTimeout(() => {
  ffmpegProcess?.stdin?.write('q');
  ffmpegProcess?.stdin?.end();
}, 200);
```

**为什么是 200ms**：FFmpeg 读线程通常在 1~2 个调度周期（约 10~30ms）内完成 EOF 处理，200ms 留出 6~20 倍裕量，覆盖系统高负载场景，同时对用户感知的停止延迟无影响（总延迟在 `cleanup` 的 15s 超时兜底范围内）。

**为什么不用更大的值**：200ms 已足够，更大值只会延长停止时间，不带来额外收益；更小值（如 50ms）在 CPU 高负载时可能仍有竞争。

## 十一、技术启示

**这严格属于竞态问题，但与前端常见的竞态不同，属于进程间（IPC）层面。**

| 维度 | 前端异步竞态 | 本文的进程间竞态 |
|------|-------------|----------------|
| 竞争主体 | 同一进程内的多个 Promise / 事件循环任务 | 跨进程的 OS 信号（pipe EOF）与 stdin 写入 |
| 调度者 | JS 事件循环（单线程，可预测） | OS 进程调度器（多核，不可预测） |
| 可见性 | 同一内存空间，可用锁/标志位协调 | 不同地址空间，只能通过信号/管道/延时协调 |
| 典型修复手段 | `AbortController`、`useEffect` 清理、`isFresh` 标志 | 信号顺序控制 + 时间裕量（本方案） |
| 复现稳定性 | 通常可稳定复现（相同事件顺序） | 依赖 OS 调度，表现为"偶发、方向随机" |

前端竞态（如 React 请求竞争）的根因是**逻辑顺序与响应顺序不一致**，修复方式是取消/忽略过期响应。本问题的根因是**信号传递路径跨越了进程边界，延迟不可控**，修复方式是在发送第二个信号前主动等待足够的时间，让第一个信号的副作用在接收方完成传播。
