\## 架构改动评价

改动核心：



\- 拆分渲染线程（固定节拍产帧）和编码线程（异步 NVENC submit + tryLock）

\- StagingPool 3 slot ring + FrameQueue SPSC（对齐 OBS gpu\_encoder\_queue）

\- bitstream ring 与 staging 一一对应

\- 渲染目标纹理与 NVENC 输入纹理分离（对齐 OBS 不变量）

这个改动 正确解决了原问题3 （冻结帧重发压缩包）——现在无新帧时不编码不发包，不再重发 NAL。但引入了新的 P0 问题。



\## 新引入的严重问题

\### N1. tryLockPacket 在 kBusy 时 unmap input（P0 崩溃/编码失败）

nvenc\_encoder.cpp:248-254 ：



NVENC 编码是异步的： nvEncEncodePicture 提交后编码在后台进行， LockBitstream 才是等待完成。 input resource 必须保持 mapped 直到 LockBitstream 成功返回 。中途 UnmapInputResource 是非法操作——NVENC 后台编码可能还在读这个纹理。



返回 kBusy 后编码线程 main.cpp:721-722 只是 break 等待重试，但 input 已经被 unmap 了。重试时 m\_mappedRegistered\[bitstreamIndex] 为 null，不会重新 map。NVENC 内部状态混乱，后续帧大概率全部失败 → consecutiveFail > 30 → 退出码 2。



对比 OBS 正确做法 （obs-nvenc.c）：MapInputResource 后保持 mapped，LockBitstream 成功后才 UnmapInputResource。Lock busy 时 只重试 Lock，不动 input 。



修复 ：kBusy 分支不能 unmap，只 return kBusy。unmap 只在 kReady/kError 时做。



\### N2. VFR 帧率与 muxer 固定 fps 假设冲突（P1 播放速度失真）

main.cpp:672-692 renderLoop 在 hasNew=false 时不编码不发包。而 mux\_target.cpp:111-112 muxer 用 -r <fps> 固定帧率：



raw H.264 流无时间戳，ffmpeg -r 30 假设每帧间隔 1/30s。当 WGC 帧率低于目标（游戏卡顿时 WGC 可能降到 15fps），exe 实际只送 15fps，但 muxer 按 30fps 生成 PTS → 播放速度加快 2 倍 。



之前"冻结帧重发"虽是错误实现，但至少保证了帧数 = 目标 fps。现在双线程模型在无新帧时不发包，帧率波动直接传导到输出，与 muxer 的 CFR 假设冲突。



修复方向 （三选一）：



1\. 无新帧时复用上一 staging 纹理重新编码（OBS 做法，生成正确 P 帧，码率低）

2\. exe 输出带时间戳的容器（mkv/ts），muxer 按 PTS 排列

3\. 渲染线程固定节拍补帧：无新帧时 CopyResource 上一 staging 到新 slot 提交编码

\### N3. convertLatestInto 持 m\_texMutex 粒度过粗（P2 性能）

main.cpp:679-685 ：



整个 lambda 在 winrt\_capture.cpp:359 的 m\_texMutex 下执行。包含 converter.convert（D3D11 绘制两 pass）+ flush（GPU 命令刷新）+ copyInto（CopyResource）。持锁时间 = 整个 GPU 管线执行时间。



WGC 回调线程 onFrameArrived 也要获取 m\_texMutex，会被阻塞整个渲染管线时间。双线程退化回接近串行。



对比 OBS ：回调线程只持锁 CopyResource 到 latestTexture（极短），渲染线程从 latestTexture 取纹理后释放锁再做 convert/flush/copy。



修复 ：convertLatestInto 应该只持锁取 src 纹理引用（或 CopyResource 到中间纹理），释放锁后再做 convert/flush/copy。



\## 之前问题未修复清单

\### 仍存在的 P0

问题1：onFrameArrived 自死锁



winrt\_capture.cpp:401-404 仍在持锁状态下调 ensureLatestTexture ，后者 第233行 内部再次 lock(m\_texMutex) 。std::mutex 不可重入， 死锁 。目前未触发仅因 init 阶段已建好纹理。



问题2：窗口缩放后录制卡死



winrt\_capture.cpp:234-241 ensureLatestTexture 尺寸不同时不重建。 第407-410行 尺寸不匹配跳过本帧。用户调整窗口大小后所有帧被丢弃，录制冻结。FramePool 也缺 Recreate 调用。



\### 仍存在的 P1

问题4：LOW\_LATENCY + lookahead 语义矛盾



nvenc\_encoder.cpp:87 NV\_ENC\_TUNING\_INFO\_LOW\_LATENCY + 第129-132行 enableLookahead=1, lookaheadDepth=20 。LowLatency 设计目标就是减延迟，lookahead 增延迟，语义冲突。头文件注释说"B-frames NOT disabled... LOW\_LATENCY"，但没解释为何又加 lookahead。



录制场景应对齐 OBS 用 NV\_ENC\_TUNING\_INFO\_HIGH\_QUALITY ，或用 ULTRA\_LOW\_LATENCY + 去掉 lookahead。



问题5：bitstream buffer 可能不足



nvenc\_encoder.cpp:166 bs.size = width \* height \* 4 。720p = 3.5MB，场景切换 IDR 帧可达 5-10MB。SDK 12+ 允许 size=0 让 SDK 自动决定。

\## 修复优先级

优先级 问题 状态 P0 N1 kBusy 时 unmap input 新引入，必须修 P0 问题1 onFrameArrived 自死锁 未修 P0 问题2 窗口缩放卡死 未修 P1 N2 VFR 与 muxer fps 不匹配 新引入 P1 问题4 LowLatency+lookahead 矛盾 未修 P1 问题5 bitstream buffer 不足 未修 P2 N3 m\_texMutex 持锁过粗 新引入，性能 P2 问题7 PATH 回退 未修 P3 问题8-14 冗余 未修



核心结论：双线程架构方向正确，但 N1（kBusy unmap）会在实际录制中导致 NVENC 状态崩溃，是当前最紧急的 bug。N2（VFR/fps 不匹配）会导致录制视频播放速度异常。这两个新问题加上未修的问题1、2，当前 exe 仍无法正常用于生产。
