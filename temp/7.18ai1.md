关键 ：PeekMessage 泵驱动 dispatcher queue → WGC 的 on\_frame\_arrived 在这个 PeekMessage 循环中被分发。所以 OBS 的 on\_frame\_arrived 和 output\_frames （渲染+编码）在 同一线程同一循环 里执行。



winrt-capture.cpp:141 on\_frame\_arrived 里 obs\_enter\_graphics() 只是为了保护 graphics 子系统状态（多源场景），单 WGC 源时同线程不会竞争—— 实际无跨线程互斥 。



\## 当前 exe 的凭空偏离

对照 OBS，当前 exe 引入了 三处不必要的线程分离 ：



\### 偏离 1：DQTYPE\_THREAD\_DEDICATED 专用 dispatcher 线程

winrt\_capture.cpp:100 ：



```

DispatcherQueueOptions opt1{ sizeof(DispatcherQueueOptions), 

DQTYPE\_THREAD\_DEDICATED, DQTAT\_COM\_NONE };

```

OBS 用 DQTYPE\_THREAD\_CURRENT 在图形线程建 dispatcher，图形线程的 PeekMessage 泵驱动回调。当前 exe 用 DQTYPE\_THREAD\_DEDICATED 另起专用线程，该线程自泵消息—— WGC 回调跑在专用线程，渲染跑在 renderLoop 线程，两者跨线程 。这是所有跨线程复杂度的根源。



\### 偏离 2：独立渲染线程 + m\_texMutex 抢 immediate context

当前 exe 有三个线程访问同一个 D3D11 immediate context：



\- WGC 回调线程（dispatcher 专用线程）：onFrameArrived 的 CopyResource

\- 渲染线程（renderLoop）：convertLatestInto 的 convert/flush/copyInto

\- （编码线程不直接访问 immediate context）

用 m\_texMutex 串行化。而 OBS 单线程 访问 immediate context，无锁。



\### 偏离 3：独立编码线程 + StagingPool ring + FrameQueue

当前 exe 把编码分离到 encodeLoop 线程，用 SPSC 队列 + staging ring 衔接。OBS 的 output\_frames 在图形线程同步调编码器（NVENC 内部异步缓冲）。



\## 为这些偏离买单的补丁清单

补丁 为哪个偏离买单 OBS 是否需要 问题1 ensureLatestTextureLocked 分层 m\_texMutex 不可重入 ❌ OBS 单线程无锁 N1 kBusy 不 unmap 编码线程异步 tryLockPacket ❌ OBS 同步编码 N3 持锁粒度（误报回退） m\_texMutex 覆盖 GPU 管线 ❌ OBS 无锁 F-1 tryPopReady 签名 FrameQueue SPSC ❌ OBS 无队列 F-2 consecutiveFail 位置 encodeLoop 异步计数 ❌ OBS 同步失败即退 P1 buf\_count=4 死锁 staging ring + B帧重排 ❌ OBS 无 ring N2 CFR 每 tick 产帧 muxer -r 30 假设 + VFR ❌ OBS video\_sleep + texture\_written 问题2 窗口缩放跳帧 固定首帧尺寸设计 ❌ OBS Recreate 纹理+FramePool 问题8 诊断探针 DQTAT\_COM\_NONE 失败兜底 ❌ OBS 直接 DQTAT\_COM\_STA



9 个补丁全部是为凭空引入的三处线程偏离买单。 OBS 的对应代码里这些补丁一个都不存在，因为单线程模型根本不会产生这些问题。



\## OBS 可完全复用的部分

OBS 的捕获→纹理处理→编码流程，剥离 libobs graphics 层后可直接复用：



1\. dispatcher 初始化 ： winrt-dispatch.cpp 全文 56 行， DQTYPE\_THREAD\_CURRENT + DQTAT\_COM\_STA

2\. WGC 初始化 ： winrt-capture.cpp:345-432 winrt\_capture\_init\_internal ，FramePool.Create + Session.StartCapture

3\. on\_frame\_arrived ： winrt-capture.cpp:128-195 含尺寸变化时 gs\_texture\_destroy + gs\_texture\_create + frame\_pool.Recreate （问题2 的正确解法）

4\. 主循环 ： obs-video.c:1097-1159 PeekMessage + output\_frames + video\_sleep

5\. NVENC 编码 ：obs-studio 的 nvenc.c 同步编码（ nvEncEncodePicture + LockBitstream 阻塞），无需 tryLockPacket 非阻塞

需要替换的 libobs 依赖仅：



\- gs\_texture\_create/destroy/get\_obj → 原生 CreateTexture2D （当前 exe 已有）

\- obs\_enter/leave\_graphics → 删除（单线程不需要）

\- gs\_get\_device\_obj → 传入的 ID3D11Device（当前 exe 已有）

\## 当前 exe 凭空实现的不合理逻辑

1\. m\_texMutex 整个锁机制 ——单线程模型下完全多余，是问题1/N3/持锁粒度争议的根源

2\. StagingPool ring + FrameQueue SPSC ——单线程同步编码不需要，是 F-1/N1/P1/F-2 的根源

3\. tryLockPacket 非阻塞 + kBusy 轮询 ——OBS 用阻塞 LockBitstream ，简单且无状态机

4\. 每 tick 产帧复用上一帧（N2 修复） ——OBS 用 texture\_written 标志，无新帧跳过编码，编码器原生 VFR

5\. 固定首帧尺寸（问题2 设计） ——OBS 在 on\_frame\_arrived 里重建纹理 + Recreate FramePool

6\. DQTAT\_COM\_NONE → STA 双重尝试 + 诊断探针 ——OBS 直接 DQTAT\_COM\_STA

\## 结论

你的逻辑完全正确：



1\. 屏幕抓取、帧写入、纹理处理、初次编码的全部流程，OBS 可以完全复用 ，代码几乎不用改（仅替换 libobs graphics 层的 \~100 行 API 为原生 D3D11）。

2\. 差异仅在成片 ：OBS 用 obs\_output 写 FLV/MP4，CoWatch 需要 HLS 切片。这部分通过 ffmpeg-mux 管道对接即可（当前 exe 的 mux\_target.cpp 这部分是对的）。

3\. 当前所有 Bug 都在为凭空生成的跨线程代码买单 ：三处线程分离（专用 dispatcher 线程 + 渲染线程 + 编码线程）引入了 9 个补丁，每个补丁又可能引入新问题（N3 甚至修了又回退）。4 轮 QA 复核本质上是在给一个不该存在的复杂度擦屁股。

4\. 正确做法 ：推倒当前 winrt\_capture.cpp 的 dispatcher/线程模型 + main.cpp 的双线程编排 + nvenc\_encoder.cpp 的异步 tryLock，回到 OBS 的单线程图形线程模型。主线程 = 图形线程，PeekMessage 驱动 WGC 回调，同线程同步 convert + 编码，无锁、无队列、无 ring。这样问题1/N1/N3/F-1/F-2/N2/问题2/问题8 全部消失 ，只剩下 ffmpeg-mux HLS 对接（已正确）+ 真机验证。

这是为什么"补丁越打越多仍然有 Bug"——根因是架构偏离，补丁只能治标。
