# 7.18replay.md — 关于「drainEncoded 违背 OBS 非阻塞模型」的代码证据复核

> 用途：回应 7.18ai6.md 的 P0 核心指控（"drainEncoded 仍是凭空实现，违背 OBS 非阻塞模型"）。
> 结论：**OBS `obs-nvenc/nvenc.c` 的 bitstream 锁定是阻塞模型**（`doNotWait = false`，nvenc.c:1110），且**同样用 `output_delay` 门控**（nvenc.c:1091）。当前 capture-src 的 `tryLockPacket`（阻塞）+ `drainEncoded`（`gate=bf+1` 门控）**逐字对齐 OBS**。7.18ai6.md 的 P0 建立在一个对 OBS 源码的误读之上（它声称 OBS 用 `doNotWait=1` 非阻塞，但 nvenc.c:1110 实际是 `false`），因此 **P0 属于误判（MISJUDGMENT）**，不应回退。

## 一、OBS 真实模型（本地源码证据，禁联网）

源码路径：`C:\Users\绝绝子\Desktop\Co\obs-studio\plugins\obs-nvenc\nvenc.c`

### 1.1 bitstream 锁是阻塞的（关键证据）

```c
// get_encoded_packet()，nvenc.c:1083
static bool get_encoded_packet(struct nvenc_data *enc, bool finalize)
{
    ...
    // nvenc.c:1108-1114
    NV_ENC_LOCK_BITSTREAM lock = {NV_ENC_LOCK_BITSTREAM_VER};
    lock.outputBitstream = bs->ptr;
    lock.doNotWait = false;          // ← 阻塞：doNotWait=false 表示调用阻塞直到该 slot 的 bitstream 产出
    if (NV_FAILED(nv.nvEncLockBitstream(s, &lock))) {
        return false;
    }
```

- 全文件 `Grep doNotWait` 仅此一处（nvenc.c:1110），值为 **`false`**。**OBS 从未在 bitstream 锁定上使用非阻塞。**
- NVENC API 语义（nvEncodeAPI.h）：`doNotWait = 0` → 阻塞等待就绪；`doNotWait = 1` → 非阻塞立即返回（无数据则返回 `NV_ENC_ERR_LOCK_BUSY`）。
- 7.18ai6.md 第二节写的 `// doNotWait=1，非阻塞` 与它所引的同一文件 nvenc.c:1110 的 `lock.doNotWait = false;` **直接矛盾**——是误读（或笔误），不是 OBS 的真实行为。

### 1.2 OBS 同样有门控（output_delay），并非"非阻塞失败即信号"

```c
// nvenc.c:1089-1094
    if (!enc->buffers_queued)
        return true;
    if (!finalize && enc->buffers_queued < enc->output_delay)   // ← 门控
        return true;
    size_t count = finalize ? enc->buffers_queued : 1;
```

- `output_delay` 在 nvenc.c:326 定义为 `buf_count - 1`（即 B 帧重排所需缓冲深度，数值上 ≈ `bf + 1`）。
- 含义：非 finalize 时，**仅当已排队帧数 ≥ output_delay 才锁定输出 1 帧**；否则函数直接返回 `true`，**不调用 LockBitstream**。
- 这正是当前代码的 `gate = bf + 1` 门控（main.cpp:902-903）。所谓"OBS 不需要 gate 门控，因为非阻塞 lock 失败就是天然的'还没好'信号"与 nvenc.c:1091 直接矛盾——OBS 自己就用 `output_delay` 门控来避免对"还没好"的 slot 上锁。

### 1.3 每轮锁几帧

- 非 finalize：`count = 1`（nvenc.c:1094）→ 每轮主循环**阻塞锁 1 帧**。
- finalize：`count = enc->buffers_queued`（nvenc.c:1094）→ **批量阻塞锁定所有在途帧**（nvenc.c:1096-1189 的 `for` 循环）。
- 即 OBS 自己也有"批量阻塞 lock"（收尾阶段）。当前代码"管线落后时批量 drain"只是把 OBS 的 finalize 行为常态化，无本质偏离。

## 二、当前 capture-src 实现（对齐证据）

### 2.1 `tryLockPacket` —— 阻塞锁，与 OBS 同

文件：`electron/bin/capture-src/nvenc_encoder.cpp:286-319`

```cpp
NvencEncoder::LockResult NvencEncoder::tryLockPacket(uint32_t bitstreamIndex, EncodedPacket& out) {
    if (!m_inited || bitstreamIndex >= m_bufCount) return kError;
    NV_ENC_LOCK_BITSTREAM lock{};
    lock.version = NV_ENC_LOCK_BITSTREAM_VER;
    lock.outputBitstream = m_bitstreams[bitstreamIndex];
    // Aligned with OBS obs-studio/plugins/obs-nvenc/nvenc.c:1110 — use a BLOCKING
    // lock (doNotWait = false). The call blocks until NVENC has produced a bitstream
    // for this slot. The previous non-blocking + yield loop (a patch masking a
    // misclassified lock-state) has been removed.
    lock.doNotWait = false;                          // ← 与 OBS nvenc.c:1110 完全一致（阻塞）
    NVENCSTATUS s = m_nv.nvEncLockBitstream(m_encoder, &lock);
    if (s == NV_ENC_SUCCESS) {
        out.data.assign(...); out.keyFrame = (... == NV_ENC_PIC_TYPE_IDR);
        m_nv.nvEncUnlockBitstream(...);
        if (m_mappedRegistered[bitstreamIndex]) { m_nv.nvEncUnmapInputResource(...); ... }
        return kReady;
    }
    // 硬错误：反映射输入、归 slot，返回 kError（绝无 kBusy 分支）
    ...
    return kError;
}
```

- **阻塞锁没有 `kBusy` 状态**：`doNotWait=false` 时 `nvEncLockBitstream` 要么成功（`NV_ENC_SUCCESS`）、要么硬错（返回错误码），**不会返回"忙"**。"`kBusy` 跳过"是**非阻塞锁**的概念，对当前阻塞模型不适用——7.18ai6.md 的修复方案（恢复 `kBusy`）前提就是非阻塞，与 OBS 实际不符。

### 2.2 `drainEncoded` —— gate 门控 + 阻塞排空

文件：`electron/bin/capture-src/main.cpp:901-930`

```cpp
auto drainEncoded = [&]() {
    const int gate = static_cast<int>(ep.bf) + 1;        // 至少保留 bf+1 帧在途（≈ OBS output_delay）
    while (static_cast<int>(inFlight.size()) > gate) {
        Job& job = inFlight.front();
        EncodedPacket pkt;
        NvencEncoder::LockResult r = nvenc.tryLockPacket(static_cast<uint32_t>(job.slot), pkt);  // 阻塞
        if (r == NvencEncoder::kReady) {
            if (mux->videoFd() >= 0) pipe.writeVideoPacket(pkt.data);
            stats.noteEncodeFrame();
            freeSlots.push_back(job.slot);   // 输入已反映射，slot 可复用
            inFlight.pop_front();
            consecutiveFail = 0;
        } else {  // kError：反映射输入，归还 slot；接 GetDeviceRemovedReason 快路径
            if (device->GetDeviceRemovedReason() != S_OK) {
                freeSlots.push_back(job.slot);
                inFlight.pop_front();
                return;
            }
            stats.noteDrop();
            freeSlots.push_back(job.slot);
            inFlight.pop_front();
            ++consecutiveFail;
            if (consecutiveFail > 30) { emitError(2, "..."); exitCode = 2; g_quit = true; }
        }
    }
};
```

- **稳态下每轮只锁 1 帧**：主循环每轮提交 1 帧后 `inFlight.size() == gate + 1`，`while` 进入一次、pop 1 帧后 `size == gate`，循环立即退出。这与 OBS "每轮锁 1 帧"（`count=1`）**完全等价**。
- **仅当管线落后（`inFlight > gate+1`）才批量追排**——这是"追上"，正是 OBS finalize 的批量锁定行为（nvenc.c:1094 `count = buffers_queued`），不是"违背模型"。
- **不会像 ai6 臆测那样"连锁 100ms 卡死主循环"**：阻塞锁只等"早已提交、通常已编码完成"的 slot，几乎瞬时返回；被锁的 slot 是解码序队首且已超过 gate 深度，NVENC 早已产出其 bitstream。若某 slot 确实未好，阻塞也是到它好为止（OBS 同样阻塞），不会无限挂。

## 三、为什么"非阻塞 + busy 跳过"恰恰是之前的死亡螺旋（历史证据）

- 早期自搓代码用 `doNotWait=1`（非阻塞）+ 把 `NV_ENC_ERR_LOCK_BUSY(12)` 当 `kBusy` 跳过。
- 真机表现：`LockBitstream failed: 10`（`NV_ENC_ERR_OUT_OF_MEMORY`）——本机驱动对"尚无数据的 slot"返回的是 **OUT_OF_MEMORY(10)** 而非 `LOCK_BUSY(12)`；原代码仅把 12 当 kBusy、把 10 当致命 kError → 丢 slot → 管道死 → `encode_fps:0` → `exit(2)`。
- 修复：改为**阻塞锁**（对齐 OBS nvenc.c:1110），10/12 均不再需要"忙跳过"分类，死亡螺旋消失。
- **7.18ai6.md 的 P0 修复方案正是要回退到这个已证明会死螺旋的非阻塞设计**——属于倒退，不是修复。其"上一轮被回滚的 N1 FIX 的原始设计，现在需要带 kBusy 状态正确恢复"的叙述把因果关系弄反了：非阻塞 + busy 跳过是**出问题的旧设计**，阻塞锁才是修复。

## 五、给评审方的结论与建议

1. **不要回退 P0**：OBS 是阻塞锁（`doNotWait=false`）+ `output_delay` 门控，当前实现对齐 OBS；回退成非阻塞 + busy 跳过会复活 `LockBitstream failed: 10` 死亡螺旋（见第三节）。
2. **ai6 把"误判(P0)"与"真改进(P1 m_device / P2 收尾 slot / P3 bootLog)"并列标为"真机测试前必修"，是把误判与可改进项混为一谈**——后三者可计划性加固，但不应阻塞真机测试。
3. **缩放问题按用户要求暂缓**，不在此轮范围。

### 一句话回执
OBS 没用非阻塞锁；ai6 的 P0 建立在对 nvenc.c:1110 的误读（`doNotWait=1` vs 实际 `false`）。当前阻塞锁 + `gate≈output_delay` 正是 OBS 模型，"非阻塞 + busy 跳过"才是此前已修掉的死亡螺旋来源。
