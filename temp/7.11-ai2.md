现在你对obs录制层方案有基本了解了，基于Obs的源码重新开始，是否真的还需要8-11天？

诚实重新评估， 5-7 天更合理 ，之前估的 8-10 天偏保守。

## 重新评估
OBS 的 WGC 核心代码只有 ~600 行，逻辑清晰：

### 代码编写（2-3天）
工作 量 性质 剥离 libobs 依赖 ~100行替换 机械替换（gs_texture → ID3D11Texture2D） staging texture + Map/Unmap ~50行 标准 D3D11 模式 stdout 二进制写入 ~20行 参考 audio_capture.exe 主循环 + 冻结帧 ~30行 简单逻辑 窗口最小化/关闭检测 ~30行 参考 window-capture.c 命令行参数解析 ~20行 标准工作 合计 ~250行新代码

### 编译环境（0.5天）
VS Build Tools + Windows SDK + cppwinrt NuGet 包，一次性配置。

### 调试（2-3天）
这是真正的不确定性来源：

- WinRT 公寓模型（STA 初始化）
- 回调时序（FrameArrived 是否正确触发）
- 管道阻塞（stdout 写满时 FFmpeg 读取慢）
### 集成测试（1天）
recording/index.ts 改动 + 端到端验证。

## 之前高估的原因
1. 过度估计了 libobs 依赖剥离难度 ：实际上只有 5-6 个 API 需要替换，都是 1:1 映射
2. 没有充分认识 OBS 代码的可移植性 ：winrt-capture.cpp 的 WGC 部分几乎不依赖 OBS 业务逻辑，只依赖 graphics 抽象层
3. 把"从零设计"和"移植已验证代码"混为一谈 ：OBS 的 WGC 集成已在数百万用户上验证，不需要设计决策
## 真实风险只有两个
1. WinRT STA 初始化 ：如果回调不触发，需要调试公寓模型（1-2天）
2. staging texture 带宽 ：1280×720×4×30 = 105MB/s，需要验证管道不阻塞（0.5天）
其他都是机械工作，不会卡住。

修正后估算：5-7 天 。如果 WinRT 回调顺利触发，可能 4-5 天就够。
