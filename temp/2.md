# Windows 系统音频录制技术方案

## 背景

CoWatch 当前录制架构（`electron/handlers/recorder.ts`）：
- 视频：Windows 用 FFmpeg `ddagrab`（全屏）/ `gfxcapture`（窗口），macOS 用 `avfoundation`
- 音频：Windows 依赖 `cachedAudioDeviceInfo` 探测 WASAPI/dshow 设备，探测失败时 `-an` 静音录制
- 输出：HLS（`seg*.ts` + `index.m3u8`），切片上传至后端再转存 COS

**核心痛点**：FFmpeg 的 `wasapi` 输入模块源码中缺少 `AUDCLNT_STREAMFLAGS_LOOPBACK` flag，
无法录制系统播放的声音（Loopback）。BtbN / gyan.dev 等主流预编译版本均受此影响。

---

## 方案选型

### 候选方案对比

| 方案 | 原理 | 音画同步 | 实现复杂度 | 跨平台 | 额外依赖 |
|------|------|---------|----------|--------|---------|
| A. 自编译 FFmpeg（改 wasapi 源码） | 加 AUDCLNT_STREAMFLAGS_LOOPBACK + 重编译 | ✅ FFmpeg 内部统一 | ❌ 高（需 MSVC/MinGW 环境） | 仅 Win | 无 |
| B. naudiodon2 + FFmpeg pipe | Node.js WASAPI 绑定 → stdin pipe → FFmpeg | ⚠️ 需调优 | ❌ 中高（Native Addon + Node ABI 绑定） | 仅 Win | naudiodon2 |
| C. audio-capture + FFmpeg pipe | 独立可执行文件 WASAPI Loopback → pipe → FFmpeg | ✅ FFmpeg 内部统一 | ✅ 低 | 仅 Win（macOS 静音） | 打包 exe |
| D. Electron desktopCapturer + MediaRecorder | Chromium 内置 API，音画同一 MediaStream | ✅ 天然同步 | ✅ 极低 | 仅macOS | 无 |

### 推荐方案：**方案 C — audio-capture + FFmpeg pipe**

**选型理由：**
1. **音画同步可靠**：PCM 通过 pipe 进入 FFmpeg stdin，两路流（音频 stdin + 视频 ddagrab）在同一个 FFmpeg muxer 内由 PTS 对齐，与 FFmpeg 原生多输入等价
2. **零 Native Addon 风险**：audio-capture 是独立可执行文件，不绑定 Node.js ABI 版本，Electron 升级不影响
3. **有预编译版本**：[GitHub Releases](https://github.com/huxinhai/audio-capture/releases) 提供 `audio_capture-windows-x64`，下载即用，无需编译
4. **macOS 保持静音**：macOS 继续用现有 `avfoundation:none` 静音方案，不引入 audio_capture，降低复杂度
5. **对现有代码改动最小**：只需改 `spawnFfmpeg` 的输入参数和启动逻辑，其余上传/切片/crash 重启逻辑完全不动

## 技术方案详细设计

### 架构变更

```
【当前架构（Windows）】
FFmpeg(ddagrab 视频 + wasapi/dshow 音频) → HLS 切片 → 上传
  问题：FFmpeg wasapi 模块缺少 loopback flag，无法录系统声音

【新架构（Windows）】
audio_capture.exe (WASAPI Loopback) ──→ pipe:0 ──┐
                                                   ├→ FFmpeg muxer → HLS 切片 → 上传
FFmpeg filter: ddagrab (视频) ────────────────────┘

【macOS 不变（静音）】
FFmpeg(avfoundation:${idx}:none) → HLS 切片 → 上传
  静音录制，audio_capture 不参与
```

### 音画同步策略

**问题**：audio_capture 和 FFmpeg 是两个独立进程，启动时间有 50~300ms 偏差。

**解法：同时启动 + `aresample=async`**

```
1. 在同一个 event loop tick 里同时 spawn audio_capture 和 FFmpeg
2. audio_capture.stdout pipe 到 FFmpeg.stdin
3. FFmpeg 音频参数加 -af "aresample=async=1:min_hard_comp=0.100:first_pts=0"
   → FFmpeg 自动拉伸/压缩音频流以匹配视频时间线
   → 50ms 以内偏移完全无感知，100ms 以内可接受
```

预期效果：游戏音效、背景音乐场景下音画偏移 < 50ms，满足 100ms 内要求。

### FFmpeg 命令行变更

**当前（有 dshow/wasapi 设备时）：**
```bash
ffmpeg \
  -f lavfi -i "ddagrab=output_idx=0:framerate=30,..." \
  -f wasapi -i "audio=xxx" \
  -c:v h264_nvenc ... -c:a aac -b:a 128k \
  -f hls ... output.m3u8
```

**新方案：**
```bash
# 同时启动：
audio_capture.exe --sample-rate 48000 --channels 2 --bit-depth 16 --chunk-duration 0.1
# 输出 PCM 通过 pipe 写入 FFmpeg stdin

ffmpeg \
  -f s16le -ar 48000 -ac 2 -i pipe:0 \              # 音频：来自 audio_capture pipe
  -f lavfi -i "ddagrab=output_idx=0:framerate=30,..." \  # 视频：ddagrab
  -af "aresample=async=1:min_hard_comp=0.100:first_pts=0" \  # 自动音画对齐
  -c:v h264_nvenc ... -c:a aac -b:a 128k \
  -map 0:a -map 1:v \                                # 显式 map：0=音频pipe, 1=视频lavfi
  -f hls ... output.m3u8
```

注意：音频作为 input 0（`-i pipe:0`），视频作为 input 1（`-i lavfi`），需要 `-map 0:a -map 1:v` 显式映射，因为 lavfi 输入没有音频流。

### 二进制文件打包策略

```
electron/bin/
  ffmpeg.exe              # 现有，Windows 视频录制
  audio_capture.exe       # 新增，Windows 音频录制（来自 huxinhai/audio-capture Releases）
  # macOS 不需要 audio_capture，继续静音录制
```

electron-builder `extraResources` 配置无需改动，已配置整个 `electron/bin/` 目录打包。

### `recorder.ts` 改动范围

#### 1. 新增模块级变量

```typescript
/** audio_capture 子进程（Windows/macOS 音频录制） */
let audioCaptureProcess: ChildProcess | null = null;
```

#### 2. 新增 `getAudioCapturePath()` 工具函数

**仅 Windows**，macOS 始终返回 null（走 `-an` 静音）。

```typescript
function getAudioCapturePath(): string | null {
  // macOS 不使用 audio_capture，直接返回 null（静音录制）
  if (process.platform !== 'win32') return null;

  const binName = 'audio_capture.exe';
  // dev 模式
  const devPath = path.join(app.getAppPath(), 'electron', 'bin', binName);
  if (fs.existsSync(devPath)) return devPath;
  // packaged 模式
  const bundledPath = path.join(process.resourcesPath, 'bin', binName);
  if (fs.existsSync(bundledPath)) return bundledPath;
  return null;
}
```

#### 3. 修改 `spawnFfmpeg` 启动逻辑

在 `spawnFfmpeg` 内部：
- 移除对 `cachedAudioDeviceInfo` 的依赖（Windows 音频参数）
- 若 `getAudioCapturePath()` 返回有效路径，启动 audio_capture 进程，将其 stdout 作为 FFmpeg 的 `pipe:0` 输入
- macOS 同样接入（替换原来 `avfoundation:none` 方案）

```typescript
// 启动音频进程
const audioCaptureBin = getAudioCapturePath();
let audioInputArgs: string[] = ['-an']; // 兜底：无音频
let audioPipeProcess: ChildProcess | null = null;

if (audioCaptureBin) {
  audioPipeProcess = spawn(audioCaptureBin, [
    '--sample-rate', '48000',
    '--channels', '2',
    '--bit-depth', '16',
    '--chunk-duration', '0.1',
  ], { stdio: ['ignore', 'pipe', 'ignore'] });
  audioCaptureProcess = audioPipeProcess;

  audioInputArgs = [
    '-f', 's16le', '-ar', '48000', '-ac', '2', '-i', 'pipe:0',
  ];
}

// FFmpeg 启动
const proc = spawn(ffmpeg, [
  ...audioInputArgs,    // pipe:0 音频（或 -an）
  ...videoInputArgs,    // lavfi/avfoundation 视频
  ...(audioPipeProcess ? ['-af', 'aresample=async=1:min_hard_comp=0.100:first_pts=0'] : []),
  ...(audioPipeProcess ? ['-map', '0:a', '-map', '1:v'] : []),
  ...encodeArgs,
  ...(audioPipeProcess ? ['-c:a', 'aac', '-b:a', '128k'] : ['-an']),
  ...hlsArgs,
], { stdio: ['pipe', 'ignore', 'pipe'] });

// pipe 音频流到 FFmpeg stdin
if (audioPipeProcess) {
  audioPipeProcess.stdout!.pipe(proc.stdin!);
}
```

#### 4. 修改 `cleanup()` 函数

新增 audio_capture 进程的清理：
```typescript
if (audioCaptureProcess) {
  try { audioCaptureProcess.kill('SIGTERM'); } catch (_) { /* 已退出 */ }
  audioCaptureProcess = null;
}
```

#### 5. 移除/简化的逻辑

- 移除 `detectWasapiAvailable()` 函数（不再需要枚举 dshow/wasapi 设备）
- 移除 `cachedAudioDeviceInfo` 变量
- 移除 `testDshowDefaultDevice()` 函数（已在上个版本删除）
- macOS 的 `avfoundation` inputArgs 保持 `${avfIndex}:none` **完全不变**（继续静音）

## 实施步骤

### Step 1：下载 audio_capture 预编译版本

从 https://github.com/huxinhai/audio-capture/releases 下载：
- `audio_capture-windows-x64` → 重命名为 `audio_capture.exe` → 放入 `electron/bin/`

**macOS 不需要下载**，继续沿用静音方案。

### Step 2：验证 audio_capture 可用

在 Windows 测试机上：
```bash
# 播放任意音频，然后执行：
.\electron\bin\audio_capture.exe --chunk-duration 0.1 2>/dev/null | ffmpeg -f s16le -ar 48000 -ac 2 -i pipe:0 -t 5 test.wav
# 检查 test.wav 是否有系统声音
```

### Step 3：修改 recorder.ts

按上述改动范围实施，重点验证：
- `-map 0:a -map 1:v` 显式流映射正确
- `aresample=async=1` 不影响 HLS muxer 的时间戳
- `cleanup()` 里 audio_capture 进程被正确终止，不产生僵尸进程

### Step 4：兜底策略

若 `getAudioCapturePath()` 返回 null（用户删除了 bin 文件 / 旧版本包），
降级为 `-an` 静音录制，不影响视频录制功能，与现有行为一致。

## 风险与注意事项

| 风险 | 概率 | 缓解措施 |
|------|------|---------|
| macOS 录制无声音 | 已知，设计如此 | macOS 静音为当前阶段既定策略，后续有需求再单独处理 |
| pipe 积压导致 audio_capture 阻塞 | 低（`chunk-duration 0.1` 小块输出） | 监听 `audioCaptureProcess.stderr` 检测异常 |
| crash 重启时 audio_capture 未重启 | 中 | `handleFfmpegCrash` 里同步重启 audio_capture |
| pipe 关闭时机不对导致 FFmpeg stdin 错误 | 低 | audio_capture 退出时 pipe 自动关闭，FFmpeg 会收到 EOF 正常处理 |
| Windows 打包后 audio_capture.exe 被杀毒软件误报 | 中 | 提示用户添加白名单；长期方案是对 exe 代码签名 |

---

## 不改动范围

以下逻辑**完全不需要改动**：
- HLS 切片上传逻辑（`uploadSegment` / `triggerRetryQueue` / `abortRecording`）
- crash 重启逻辑主体（仅需在重启时同步重启 audio_capture）
- 编码器检测（`detectEncoder`）
- 窗口列表获取（`getSources`）
- 前端播放侧（hls.js 播放 HLS 完全不变）
- 后端接口（`/recording/finish`、切片上传接口）
