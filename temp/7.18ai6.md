\## 二、P0 核心偏差：drainEncoded 仍是凭空实现，违背 OBS 非阻塞模型



这是当前代码\*\*最严重的剩余问题\*\*，且会直接导致真机测试时的帧丢失。



\### 问题定位



\*\*nvenc\_encoder.cpp:296\*\* —— `tryLockPacket` 改成了\*\*阻塞\*\* lock：

```cpp

lock.doNotWait = false;  // 阻塞

NVENCSTATUS s = m\_nv.nvEncLockBitstream(m\_encoder, \&lock);

```



\*\*main.cpp:901-934\*\* —— `drainEncoded` 用 `gate = bf+1` 门控 + \*\*批量阻塞 lock\*\*：

```cpp

auto drainEncoded = \[\&]() {

&#x20; const int gate = static\_cast<int>(ep.bf) + 1;

&#x20; while (static\_cast<int>(inFlight.size()) > gate) {

&#x20;   Job\& job = inFlight.front();

&#x20;   NvencEncoder::LockResult r = nvenc.tryLockPacket(...);  // 阻塞 lock

&#x20;   ...

&#x20; }

};

```



\### 与 OBS 真实模型的对比



\*\*OBS 的真实做法\*\*（obs-nvenc/nvenc.c:1083-1114 + obs-video.c:output\_frames）：

```c

// 每帧只 submit 1 次 + lock 1 次，都是非阻塞

nvEncEncodePicture(encoder, \&pic);              // 非阻塞 submit

nvEncLockBitstream(encoder, \&lock);              // doNotWait=1，非阻塞

// lock 失败（BUSY/NOT\_READY）→ 保留 input mapped，跳过这一帧的输出

// 等下一轮主循环再试

```



OBS \*\*不需要 gate 门控\*\*，因为非阻塞 lock 失败就是天然的"还没好"信号。OBS \*\*每轮主循环只 lock 1 次\*\*，绝不批量。



\*\*当前代码的偏差链条\*\*：

1\. 把 `tryLockPacket` 改成阻塞 lock（doNotWait=false）

2\. 阻塞 lock 在 `inFlight.front()` 还没产出时会挂死 → 发明 `gate=bf+1` 门控规避

3\. gate 门控保证 `inFlight.size() > bf+1` 时 front() 一定已产出（依赖 B 帧重排语义）

4\. drainEncoded 在 `while (size > gate)` 里\*\*批量阻塞 lock\*\* 多帧



\### 这个偏差的真机风险



\*\*场景\*\*：GPU 被游戏占满，NVENC 编码一帧需要 50ms。



\- 当前代码：drainEncoded 阻塞 lock 帧 0（50ms）+ 阻塞 lock 帧 1（50ms）= \*\*100ms 卡住主循环\*\*

\- 期间 PeekMessage 不泵，WGC FrameArrived 堆积，FramePool 满后丢弃旧帧

\- 30fps 帧预算 33ms，60fps 帧预算 16ms——\*\*100ms 阻塞 = 丢 3-6 帧\*\*



\*\*OBS 在同样场景下\*\*：

\- 非阻塞 lock 立即返回 BUSY，跳过输出，主循环继续 PeekMessage + 消费新帧

\- NVENC 编码完成后下一轮主循环再 lock 成功

\- 主循环每轮 <5ms，WGC 不丢帧



\### 修复方案（对齐 OBS 真实模型）



\*\*nvenc\_encoder.cpp\*\* —— 改回非阻塞 + kBusy 状态：

```cpp

NvencEncoder::LockResult NvencEncoder::tryLockPacket(uint32\_t bitstreamIndex, EncodedPacket\& out) {

&#x20; ...

&#x20; lock.doNotWait = 1;  // 非阻塞，对齐 OBS nvenc.c:1110

&#x20; NVENCSTATUS s = m\_nv.nvEncLockBitstream(m\_encoder, \&lock);

&#x20; if (s == NV\_ENC\_SUCCESS) {

&#x20;   // ... 成功路径不变

&#x20;   return kReady;

&#x20; }

&#x20; if (s == NV\_ENC\_ERR\_LOCK\_BUSY || s == NV\_ENC\_ERR\_OUT\_OF\_MEMORY) {

&#x20;   return kBusy;  // 不 unmap，保留 mapped，下一轮重试

&#x20; }

&#x20; // 硬错误才 unmap

&#x20; ...

&#x20; return kError;

}

```



\*\*main.cpp\*\* —— drainEncoded 改为只 lock front() 一次，删除 gate：

```cpp

&#x20; Job\& job = inFlight.front();

&#x20;     inFlight.pop\_front();

&#x20;   }
```

\## 三、P1 问题：窗口缩放时编码管线不重建



\### 问题定位

```cpp

```



\### 真机风险



窗口缩放时：

1\. onFrameArrived 重建 m\_latestTexture 为新尺寸（比如 1920×1080 → 1280×720）

2\. tryConsumeFrame 把新尺寸的 m\_latestTexture 交给 render\_encode\_one

3\. render\_encode\_one 调 `converter.convert(latest, renderNv12Tex.get())`——renderNv12Tex 是旧尺寸（1920×1080）

4\. \*\*BgraToNv12::recordConvert 第 272-274 行\*\* `else if (W != m\_w || H != m\_h) return false;`——尺寸不符返回 false

5\. convert 失败 → 丢帧 → freeSlots.push\_back → 继续

6\. \*\*持续丢帧直到窗口尺寸恢复或 exe 重启\*\*



虽然不会崩溃，但用户体验是"窗口一缩放录制就卡住"。这是 project\_memory 里已识别的 P1 问题的延续——FramePool.Recreate 修了，但 main 侧的编码管线重建没接。



\### 修复方案（v1 最小改动）



main.cpp 在 wgc.start 后挂回调：

```cpp

wgc.setResizeCallback(\[\&](UINT newW, UINT newH) {

&#x20; // v1 最小处理：emitError 提示 + g\_quit，让 Electron 重启 exe 用新尺寸

&#x20; char buf\[256];

&#x20; \_snprintf\_s(buf, sizeof(buf), \_TRUNCATE,

&#x20;             "{\\"type\\":\\"RESIZE\\",\\"w\\":%u,\\"h\\":%u}", newW, newH);

&#x20; emitJson(buf);

&#x20; // 不立即 g\_quit——让 Electron 决定是否重启（v2 才做管线热重建）

});

```



v2 再做完整的热重建（重建 renderNv12Tex + encInputs + NVENC profile + re-register）。

\## 四、P1 问题：wgc.m\_device 在 rebuild 期间悬空



\### 问题定位



\*\*winrt\_capture.cpp:60\*\* —— `m\_device = device;` 裸指针，不 AddRef。



\*\*main.cpp:730-761\*\* —— rebuildDevice 时序：

```cpp

// 1) release all

for (auto\& cb : g\_lossCallbacks) {

&#x20; if (cb.release) cb.release(cb.data);  // wgc.releaseResources() —— 不清 m\_device

}

// 2) 新设备

device = newDev;  // ← 旧 device com\_ptr 释放，wgc.m\_device 悬空

// 3) rebuild all

&#x20; if (cb.rebuild) cb.rebuild(newDev.get(), cb.data);  // wgc.rebuild() → setDevice(newDev)

}

```



\*\*步骤 2 和 3 之间，wgc.m\_device 指向已释放的旧 device\*\*。



\### 真机风险



当前悬空但不被访问（rebuildDevice 步骤 2-3 之间不访问 wgc.m\_device），\*\*不会立即崩溃\*\*。但：

\- 任何后续维护者在 rebuildDevice 步骤 2-3 之间加访问 wgc.m\_device 的代码 → UAF

\- nvenc 的 lossRebuild 在步骤 3 执行，如果 nvenc 的 rebuild 内部失败抛异常，wgc.rebuild 可能不被调用 → wgc.m\_device 永久悬空



\### 修复方案



\*\*winrt\_capture.cpp:265-271\*\* —— releaseResources 里清 m\_device：

```cpp

void WinrtCapture::releaseResources() {

&#x20; while (m\_inFlight.load(std::memory\_order\_acquire) != 0) Sleep(1);

&#x20; releaseSession();

&#x20; m\_latestTexture = nullptr;

&#x20; m\_device = nullptr;  // ← 新增：release 后 device 已失效，置空避免悬空

```


\## 五、P2 清洁度问题（可选修）



\### 1. m\_inFlight 自旋等待冗余



\*\*winrt\_capture.cpp:225, 267\*\* —— `while (m\_inFlight != 0) Sleep(1);`



单线程模型下，onFrameArrived 在 DispatchMessage 返回时已 fetch\_sub，inFlight 一定已归零。自旋等待是 future-proofing，当前不必要。可删可留，保留作防御性编程也 OK。



\### 2. 收尾 drain 的从未提交 slot 风险



\*\*main.cpp:980-992\*\* —— 收尾时遍历所有 slot 调 tryLockPacket，但从未 submitFrame 的 slot 调阻塞 LockBitstream 行为未定义（NVENC 可能返回错误或阻塞）。当前 `kError → drained\[i]=true` 兜底，但依赖 NVENC 实现细节。



建议加 `slotEverSubmitted` 标记数组，只对提交过的 slot 调阻塞 lock。



\### 3. bootLog 写 C:\\



\*\*main.cpp:471\*\* —— `fopen\_s(\&bootLog, "C:\\\\cowatch\_boot.log", "w")` 仍尝试写 C 盘根目录。非管理员会失败，回退到 TEMP。建议直接写 TEMP，删掉 C:\\ 尝试。

\## 八、一句话总结



上一轮的 8 项对齐目标已全部落地，\*\*但 drainEncoded + tryLockPacket 的阻塞 lock + gate 门控是凭空发明的新补丁\*\*，违背了 OBS 的非阻塞 lock 模型，会在 GPU 高负载时阻塞主循环导致 WGC 丢帧。这是当前代码与 OBS 真实模型的核心剩余偏差，\*\*必须在真机测试前修掉\*\*。修复方式是改回非阻塞 doNotWait=1 + drainEncoded 只 lock front() 一次 + 删除 gate 门控——这恰恰是上一轮被回滚的 N1 FIX 的原始设计，现在需要带 kBusy 状态正确恢复回来。
