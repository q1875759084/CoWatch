\# 对齐 OBS 主循环模型的复杂度与测试风险评估



\## 结论先行



\*\*整体更简单\*\*，且\*\*测试风险明显更轻松\*\*。但有一处需要重点验证的时序耦合点（main 既是图形线程又承担收尾），需要在实现时一次性处理到位，不能照搬。

\## 二、线程数与跨线程交互点



| 维度 | 当前架构 | 对齐 OBS 后 |

|---|---|---|

| 线程数 | 3（图形 WGC 回调 + 编码 + main 协调） | 2（main=图形线程 + stdin 控制） |

| 跨线程共享状态 | g\_quit + SPSC + StagingPool + m\_newFrame + m\_frameCbReady + pending deque + 原子屏障 | 仅 g\_quit（stdin 线程读 → main 线程读） |

| 锁/原子原语 | std::atomic × 5 + SPSC 内部原子 + std::promise/future | std::atomic<bool> × 1（g\_quit） |

| D3D11 立即上下文访问者 | 图形线程（convert）+ 编码线程（CopyResource 出 staging）→ 需要保证不并发 | 仅 main 线程 → 天然独占，无并发风险 |



\*\*关键收益\*\*：当前架构里编码线程要对 staging 纹理做 `CopyResource`（main.cpp:copyInto），这本质是在第二个线程上操作 immediate context 的命令队列——D3D11 规范禁止 immediate context 跨线程并发提交。当前靠 SPSC 的所有权转移"规避"了真并发，但任何时序错位都会撕裂。对齐后 immediate context 只归 main 线程，这条规范约束\*\*自动满足\*\*，无需靠设计纪律维持。

\## 三、测试可验证性：从"无法对照"到"逐行对照"



这是最关键的收益，直接决定测试风险等级。



| 模块 | 当前架构 | 对齐后 |

|---|---|---|

| dispatcher 创建 | 自己的双重尝试逻辑，OBS 源码无对应物 → 只能黑盒测 | 逐行对照 winrt-dispatch.cpp:13 |

| onFrameArrived | convert+flush+copyInto+push 混在回调里，OBS 无对应物 | 逐行对照 winrt-capture.cpp:128-195 |

| 主循环 | 无主循环（main 只 Sleep 协调），OBS 无对应物 | 逐行对照 obs-video.c:1097-1159 |

| NVENC 编码 | 非阻塞 lock + kBusy 退让，OBS 用阻塞 → 行为分叉 | 逐行对照 obs-nvenc/nvenc.c:1083 |

| 尺寸变化 | ensureLatestTexture 重建纹理，\*\*缺 FramePool.Recreate\*\*（P1 未修） | 逐行对照 winrt-capture.cpp:178（含 Recreate） |



当前架构下，任何一个 bug 都要"从并发时序 + SPSC 边界 + kBusy 重试 + COM 公寓不确定性"四个维度排查，无法用 OBS 的已知正确行为做参照系。对齐后，bug 的排查范围收敛到"我的实现哪一行偏离了 OBS"，可以二分对照。

\## 四、潜在新风险：只有一个，且 OBS 已验证可行



\### 风险点：同步编码阻塞 WGC 回调的风险



NVENC 的 `nvEncLockBitstream` 阻塞模式下，如果编码未完成会阻塞调用线程。若 main 线程 = 图形线程 = dispatcher 线程，阻塞期间 PeekMessage 不转，WGC 的 `onFrame\_arrived` 投递进来的消息会堆积。



\*\*但这不是真风险\*\*，原因有二：



1\. \*\*OBS 就是这么跑的\*\*（obs-video.c:output\_frames → nvenc\_encode\_base → nvEncLockBitstream 阻塞），且 OBS 在数百万用户环境下稳定运行。NVENC 编码一帧 1080p 通常 <2ms，远小于一帧的 33ms（30fps）预算，阻塞不会累积。



2\. \*\*WGC FramePool 本身有去重\*\*：`TryGetNextFrame` 在没新帧时返回空，堆积的消息在主循环恢复后只会触发一次有效 CopyResource，不会爆队列。



\### 真正要注意的：收尾时序



当前架构：main 等 g\_quit → stop WGC → join 编码线程 → stop mux（编码线程的 EOS drain 在自己的循环里）。



对齐后：main 就是图形线程，\*\*main 不能直接 `while(!g\_quit) Sleep(100)`\*\*，否则主循环不转、WGC 回调不投递、帧不产出。收尾时：

\- g\_quit=true 后，主循环要跑完最后一轮 PeekMessage 排空 + submitEos + 阻塞 drain（30s 预算）

\- 然后才能 break 出主循环，进入 stop WGC → stop mux



这个时序 OBS 已经验证过（obs\_graphics\_thread\_loop 返回 false 后才进收尾），照搬即可，但\*\*不能省略\*\*——省略就是回退到当前的协调者模型。

\## 五、测试风险对比总表



| 测试维度 | 当前架构风险 | 对齐后风险 |

|---|---|---|

| 跨线程竞态 | 高（SPSC 边界 + 原子屏障顺序 + kBusy 重试） | 无（单线程串行） |

| COM 公寓类型 | 中（DQTAT\_COM\_NONE→STA 不确定） | 无（DQTAT\_COM\_STA 确定） |

| D3D11 上下文并发 | 中（靠纪律维持，规范禁止） | 无（天然单线程） |

| 窗口缩放 | 高（P1 未修，缺 FramePool.Recreate） | 低（顺便修掉，对照 OBS） |

| NVENC 异步时序 | 中（NEED\_MORE\_INPUT + kBusy 组合状态机） | 低（阻塞 LockBitstream，状态机扁平） |

| 收尾 EOS drain | 中（编码线程 drain + main join 时序） | 低（主循环内 drain，无 join） |

| 与 OBS 行为分叉排查 | 极高（无参照系） | 低（逐行对照） |



\*\*唯一新增的测试点\*\*：PeekMessage 消息泵在 WGC 高频回调下是否稳定——这一点 OBS 已在生产环境验证，且我们的窗口捕获频率（30fps）远低于 OBS 的高负载场景，风险可忽略。

\## 六、建议



\*\*值得改，且应该一次改到位\*\*。理由：



1\. \*\*净删除 250 行 + 删除的全是难验证的并发逻辑\*\*，符合你一贯的"根治方案 over 补丁方案"原则。

2\. \*\*P1（FramePool.Recreate）顺手修掉\*\*，不需要单独排期。

3\. \*\*后续所有 bug 都能对照 OBS 排查\*\*，测试和调参成本断崖式下降——你 pending 里的"真机验证 + 调参 1-2 天"大概率能压缩到 0.5-1 天。

4\. \*\*改的时机最好在 Electron 集成之前\*\*：现在改，Electron 侧 recording/index.ts 调用的 CLI 参数、stdin 协议、stderr 协议都不变（exe 对外接口稳定），集成层零返工。



\*\*唯一前提\*\*：实现时严格照搬 obs-video.c:1097-1159 的主循环结构（PeekMessage → output\_frames → video\_sleep），不要在主循环里再加自己的"优化"（比如非阻塞 lock、跳帧退让），否则又会回到凭空实现的老路。



预估工时：\*\*1 天改 + 0.5 天自测\*\*，比继续在当前架构上修 P1 + 调参更省时。
