## ddagrab vs gfxcapture 的底层 API

### 拉模式 vs 推模式（帧率问题的根源）
```
ddagrab（拉模式）：
  你：AcquireNextFrame()
  OS：给你一帧（即使桌面没变化也给重复帧）
  你：等33ms
  你：AcquireNextFrame()
  OS：又给你一帧
  → 稳定30fps，你说了算

gfxcapture（推模式）：
  你：注册回调 OnFrameArrived
  DWM：有新帧了 → 回调你
  DWM：没新帧 → 不回调
  DWM：窗口被遮挡 → 减少回调频率
  DWM：窗口最小化 → 可能停止回调
  → 帧率不受你控制，DWM 说了算
```
这也解释了为什么 gfxcapture 的参数是 max_framerate=30 （上限）而不是 ddagrab 的 framerate=30 （目标值）——WGC 只能限制最大帧率，不能保证最低帧率。

### 为什么两种 API 都存在
场景 适合的 API 屏幕录制/直播推流 DXGI Desktop Duplication（ddagrab） 单窗口录制（精准捕获） WGC（gfxcapture） 远程桌面 DXGI 截图工具 WGC 或 BitBlt

Microsoft 设计 WGC 就是为了解决"只截一个窗口"的需求，但它的推模式在游戏高负载下递帧不稳定，这是 WGC 的已知限制。OBS 也是同时支持两种 API，用户可以在"显示器捕获"（DXGI）和"窗口捕获"（WGC）之间选择。

## 这对我们的启示
ddagrab 之所以稳定，是因为它也是"拉模式"——FFmpeg 每33ms调用 AcquireNextFrame() ，有帧给帧，没变化给重复帧。节奏由 FFmpeg 控制。

gfxcapture 不稳定，是因为它是"推模式"——节奏由 DWM 控制，FFmpeg 只能被动等待。

ddagrab + crop 方案本质上是让 FFmpeg 用拉模式（自己控制节奏）捕获，然后裁到窗口区域。 这就是为什么它能稳定30fps。

### OBS 为什么不受影响
OBS 不走 FFmpeg 的 lavfi 架构。它的 WGC 集成是：

WGC 回调线程（独立于渲染线程）：

```
OnFrameArrived() {
    lock(frame_mutex);
    wgc_latest_frame = 新帧;   // 覆盖旧帧
    unlock(frame_mutex);

```
OBS 用双线程 + 最新帧覆盖 + 主动复用 ，完全不受 WGC 递帧节奏影响。

FFmpeg gfxcapture 是单线程 + 阻塞等待 + 被动补帧 ，递帧节奏直接决定输出节奏。
