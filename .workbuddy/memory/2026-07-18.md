## 真机 LockBitstream:10 真因回修（编码循环死亡螺旋，#21/#22 那轮未命中）
- **现象**：上轮（buf_count 3→4 + NEED_MORE_INPUT 当在途 + 补 pic 几何）重编后，真机 STILL 立刻刷 `LockBitstream failed: 10`、encode_fps 2.0→0.0、ctrl+c 需多次。说明上轮对 #10 的"几何/排队语义"归因未命中，注释 nvenc_encoder.cpp:171 早写过 "real hardware still reports LockBitstream failed: 10" 但没修。
- **真因（官方 SDK 13.0 头坐实）**：`tryLockPacket` 用 `doNotWait=1` 非阻塞锁**尚未产出数据**的 bitstream（B 帧重排期 EncodePicture 返回 NEED_MORE_INPUT 的 slot）。NVENC 非阻塞锁"无数据"返回的是 **OUT_OF_MEMORY(10)**（本机驱动不返回 LOCK_BUSY(12)）。原代码仅把 12 当 kBusy、把 10 当致命 kError → 丢 slot → 管线死。
- **SDK/OBS 依据**：nvEncodeAPI.h:2674(doNotWait=1 非阻塞就绪轮询)、:576-582(LOCK_BUSY 非致命、几 ms 重试)、:607-614/:3393-3404/:3716-3730(NEED_MORE_INPUT 不得锁该缓冲、续喂帧、按提交序锁)；官方样例 NvEncoder.cpp:644-647 用 doNotWait=false 仅锁有输出的缓冲；OBS nvenc.c:1089-1112 仅锁 buffers_queued>0 且 doNotWait=false。
- **修复（工程师落地，QA 静态 NoOne）**：`nvenc_encoder.cpp:275` 非阻塞路径条件扩为 `s == NV_ENC_ERR_LOCK_BUSY || s == NV_ENC_ERR_OUT_OF_MEMORY` → 同视 kBusy（保持 mapped、drain 在 kBusy break、不 pop、不 releaseSlot）；`bs.size=0` 保持（OBS 自动 sizing，非根因，未启用 DEGRADE PATH 固定 size）；blocking(finalize) 路径 10 仍当 kError（边界可接受）。顺手修注释 LOCK_BUSY 数值 (12)→(13)（SDK 头实际枚举 13）。
- **ctrl+c 调查（独立核实）**：grep 证实 capture-src 仅 `main.cpp:117-125` 一处 ConsoleCtrlHandler，首次任意 CTRL 信号即 `g_quit=true`、无信号计数；日志 "Received > 3 system signals, hard exiting" 是 **ffmpeg 子进程自身的信号计数消息**（ffmpeg 收 3 次 SIGINT 强退）。旧死螺旋使 encodeThread 在 finalize 阻塞 drain 挂死→收尾 join 不返回→我方进程不退→ffmpeg 反复收 ctrl+c 累计 3 次自打印；修复后管线流动、join 正常返回、首次 ctrl+c 干净退出（ffmpeg stdin 关→EOF→ENDLIST）。信号逻辑保持现状正确。
- **待真机验证**：清 build 重编 → 不再刷 "LockBitstream failed: 10"、encode_fps≈30、首次 ctrl+c 即退出、seg 非0/m3u8 有 ENDLIST。

## 高见远 delta/risk register（capture-src vs OBS，除线程模型外）
- **你的直觉部分对**：OBS 确实把脏活做完；但"忠实搬完只剩调参"在当前为**假**——除线程模型外还有结构性差异（非参数）：
  - **P0 色彩**：本工程 `BgraToNv12` 手写 shader 用 **BT.601** 且对 B8G8R8A8 SRV 误把 `.r` 当红（实际 `.r`=蓝）→ **每张 HD 帧颜色都错**（红蓝反 + 601 vs 709）。OBS 用 BT.709（video-matrices.c:43-49、nvenc.c:773）。
  - **P0 缩放**：OBS 尺寸变 `frame_pool.Recreate`；我们固定首帧尺寸→用户一缩放即冻结/黑屏（已知暂缓）。

  - **P2**：Optimus 跨 GPU（我们强制单 N 卡反而消除了 OBS 的跨 GPU 黑屏 P0，代价无 iGPU 兜底）；DPI 已对齐；GOP 默认 300 vs 250；PTS 用 frameIndex 非显示序。

## 集成边界决策（用户：本地HLS落盘仅诊断用，生产应直推服务器）
- 用户 point 正确：本地 .ts/.m3u8 落盘只是独立测试/错误归因的**控制实验面**，非生产路径。生产应直推服务器——而 OBS HLS 本就 `method=PUT` 推远端、从不本地落盘，印证生产=对齐 OBS push 模式、**无本地-file 风险**。
- **决策**：保留 `--mux-target file` 作为诊断/控制模式（独立跑 exe 验证 fps/色彩/HLS/ENDLIST，用于 exe-vs-Electron 归因）；生产用 `--mux-target push`（ffmpeg `-method PUT`/RTMP 直推 CoWatch 服务器），复用 OBS HLS-PUT 模式。
- **mux_target 应抽象 OutputTarget 接口**（FileTarget/PushTarget，均 ffmpeg-pipe 支撑），sink 切换是配置非重写。
- **错误归因策略**：① exe 已吐结构化 STATS(LOG/READY/STATS/ERROR)+退出码；② 独立 file 模式是 control：file 模式产出可播且含 ENDLIST 的 m3u8 → exonerate exe，集成模式故障归 Electron/网络/服务器；③ ffmpeg stderr 须透传进 exe 的 LOG/ERROR 流，区分 capture 失败 vs mux 失败。
- 结论：不绕过本地落盘（否则失去控制实验无法归因）；生产路径无本地-file 风险（对齐 OBS PUT）。
