# 2026-07-15 CoWatch 方案2a 排错（file 模式空目录真因 + 设计漂移）

## file 模式空目录真因（推翻前几轮"Ctrl+C/建目录"假设）
- 前几轮修的 Ctrl+C 优雅退出 + 自动建目录（A/B/C/D/E 五处）逻辑正确，但**不是 file 模式空输出的真因**。
- 真因：`mux_target.cpp:139` file 模式命令行用 `-i pipe:3` / `-i pipe:4`，要求子进程 fd3/4 被绑定到继承的管道 HANDLE。此绑定只有 OBS 的 `ffmpeg-mux.exe` 会做（`_dup2(_open_osfhandle(h),3)`）。`bin/` 只有普通 `ffmpeg.exe`（gyan.dev 全量版），**不会自动把继承 HANDLE 映射成 fd3/4** → ffmpeg 打开 `pipe:3` 失败直接退出 → 目录空。父进程因 `CreateProcess` 成功误以为 mux 起来了，照写管道（故 `out_bps>0`）但无人读。
- `C:\tmp\rec` 实际已被 `createDirRecursive` 成功创建且为空 → 目录修复有效，但非阻塞点。
- **结论：不要重编 ffmpeg-mux**。用现有 `ffmpeg.exe` 即可修：① 匿名管道读端接子进程 stdin + `-i -`；② 或命名管道 `\\.\pipe\cw_v` 当 `-i`。纯进程/管道接线，不碰 NVENC/D3D/驱动，无新兼容性坑。

## 游戏实测（7.15终端1.txt，--mux-target file 录游戏 PID 19108）
- 关键结论：**capture_fps 钉在 ~21（游戏内 60fps），但 21 不是 WGC/DWM 上限，是主循环消费上限。**
- 证据：`onFrameArrived` 心跳每 300 帧打印一次，日志里 `#300..#3000` 每隔 5 条 STATS（STATS 采样窗口 `Sleep(1500)`，即 ~1.5s）出现 → 300 帧 / ~7.5s ≈ **WGC 回调 ~40fps 投递**（游戏 60fps 下 WGC 基本跟得上，未塌）。`capture_fps` 只是主循环 `consumeNewFrame` 的吞吐率，被单线程循环（consume→GPU BGRA→NV12 转换→NVENC encode 串行）限在 ~21。
- `m_newFrame` 是 bool：WGC 多投的 ~19 帧/s 被静默丢弃（只留最新一帧），故录制视频会是以 21fps 而非 60fps。
- **好消息**：capture_fps 在游戏负载下稳定 ~21（不塌到 5-8），推翻了"游戏高负载 capture 帧率塌"的担忧（那是 DWM 门控仅在极端场景才显，且记事本测试 0-15 是 WGC 变更驱动 + 静态窗口所致，非游戏场景）。
- **异常点**：`cpu_pct` 全程 100（单核跑满）。对 WGC+GPU 管线异常——大概率来自 ① file 模式损坏的 mux 管道写（writeVideoPacket 反复尝试写无人读的 pipe，out_bps 仅计"尝试字节"非"成功字节"）；② 或 encode 开销。属独立问题，且 file mux 当前本就坏（见上"空目录真因"），修好 mux 后重测再定。
- **目标对比**：READY 报 fps:30（目标），实测 capture_fps~21 < 30 目标 < 60 游戏。21 是循环吞吐瓶颈，非捕获缺陷；后续若要达标须解耦 consume 与 encode（独立编码线程/队列）或调 tickMs。
- 用户当前问题：① 21 是否正常（答：循环上限非 WGC 缺陷，但 < 目标需优化）；② 本地看视频调试是否麻烦（答：本地 mux 修=命名管道/ stdin 接现有 ffmpeg.exe，~15 行无 ffmpeg-mux，不麻烦；"接到 CoWatch 看上传视频"反而是更大工程=替换 recorder.ts 捕获层）。

## file 模式 stdin 改造后仍 seg000.ts 为 0 字节（7.15终端2.txt）
- 前序 stdin 改造（spawnFfmpegMux + file 分支 + writeV 继承标志清理）已让 ffmpeg 正常启动并打开 seg000.ts/index.m3u8，但 seg 大小为 0。
- ffmpeg 报错：`Timestamps are unset in a packet for stream 0` / `first pts and dts value must be set` / `Error submitting a packet to the muxer` / `Conversion failed`。
- 根因：NVENC 输出的是**无时间戳的 raw H.264 AnnexB 码流**，ffmpeg `-c copy` 写 HLS/mpegts 要求每帧有 PTS/DTS；原命令行 `-fflags +genpts` 对 raw H.264 输入不足。
- 修复（静态已落盘，QA PASS）：
  1. `mux_target.h` `MuxTargetConfig` 新增 `uint32_t fps = 30;`
  2. `main.cpp` 在 `mux.init(mc)` 前加 `mc.fps = a.fps;`
  3. `mux_target.cpp` file 模式 ffmpeg 命令行在 `-f h264 -i -` 前插入 `-r <cfg.fps>`，让 demuxer 按固定帧率为每帧生成时间戳。
- 命令行变为：`-y -fflags +genpts -r 30 -f h264 -i - -c copy -f hls -hls_time 10 ...`
- 用户战略质疑：方案2a 一开始没按 OBS 完整复刻，导致 21fps 瓶颈；CoWatch 是游戏复盘网站，21fps 不足，需要按 OBS 渲染线程解耦提升性能。已建任务 #14 跟进。
- 待真机重编验证：确认 seg000.ts 非空、index.m3u8 末尾有 `#EXT-X-ENDLIST`。
