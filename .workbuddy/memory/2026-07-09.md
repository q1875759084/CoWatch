## CoWatch 录屏卡顿问题 - 根因分析与方案评审（进行中）

### 已核实事实（来自 temp/终端.txt + electron/handlers/recorder 源码）
- 用户报告：每 ~10s 出现操作迟滞感；一旦某点开始卡，后续全程卡且不自愈。
- 终端实测：`dup=3212` / 2:09 时长（约 3870 帧）→ ~83% 帧为复制帧，`drop=0`。每次 seg 转码脉冲 dup 突发增长；多次 `窗口未找到` 事件。
- 实际运行 filter 链用的是 **CPU `scale=`**（`hwdownload,format=bgra,scale=...,format=nv12,hwupload_cuda`），非 scale_cuda；日志误标"CPU scale_cuda"。对应 111.md 第三轮失败尝试。
- 转码层无条件开启（coordinator start() 中 startTranscodingWatcher 无开关），每 10s chokidar 触发 spawn 全新 ffmpeg（NVDEC+NVENC p5），与录制层 NVENC/磁盘争抢。
- 录制层写死 `-vsync cfr -r 30`（recording/index.ts:331）→ 跟不上实时时 dup 单调累加、永不回落 = "一旦卡顿全程不自愈"的机理。

### ai.md 真伪初步结论
- ai.md 称"scale_cuda 管线 29fps 稳定 1.01x"可信度低：与 111.md（团队实测 scale_cuda 在 gfxcapture 场景因 CUDA↔D3D11 context 冲突 + -vf 破坏帧节拍而不可行，约束4）及终端实测（实际跑 CPU scale）矛盾。疑似仅在合成源 testsrc 验证后过度外推。
- hwdownload 不可去、单/双显卡均需保留的判断与 111.md 一致（属实）。

### 修订轮（用户推翻 D1，给新硬约束）
- 用户：三层架构必须保留——录制须无 B 帧/无 lookahead 轻量参数避免抢游戏 GPU，但导致 720p30 码率≈1080p60，浪费 CDN 且上传无法兼顾游戏带宽 → 转码层不可替代。**D1（录制即成品/删转码层）已否决**。
- 仅考虑独显用户；三目标：游戏不卡 / 上传不占游戏带宽 / 停止即可复盘（用户放宽到 30s~1min 可接受，近直播切片上传无同步推流）。
- **架构师主推荐 R0**：录制期彻底不转码（仅令牌桶限速上传轻量中间件）→ stop 后单个常驻 ffmpeg 进程 concat 批量转码成低码率高画质生产件（p5/cq30/有 B/lookahead）逐片上传覆盖服务端同 key。根除 10s 脉冲对 NVENC/复制引擎/PCIe/磁盘/冷启动的争抢。三层结构基本不动。
- **单帧 33ms 时序瓶颈**：抓屏(GPU)→hwdownload(复制引擎)→CPU scale(最重)→hwupload(复制引擎)→NVENC(争抢时爆)→写盘。常态 5–10ms，转码脉冲使共享资源排队超 33ms→CFR dup。
- **NVENC session 误区**：session 是驱动/授权并发数上限，非硬件并行车道；消费级 N 卡通常 1 物理编码引擎（少数旗舰 2 个共享总吞吐），多 session 时分复用 → 录制+转码同刻编码互抢使每帧延迟翻倍超 33ms。

### 再修订轮（用户戳穿 R0 三漏洞 + 直播模型对照）
- **R0 三个问题均成立（高见远量化）**：
  - 问题1 成立：轻量件 10Mbps > 上传 cap 7Mbps → 净积压 3Mbps=0.375MB/s；1h=1.35GB、2h=2.7GB 残留，停后 @50Mbps 排空 3.6~7.2min → "即复盘"不成立。
  - 问题2 成立：2h 素材 10x 转码 ~12min + 上传 ~7min = ~19min 停等；若提前复盘 CDN serv 原片(10M) → 3.3x 成本窗口（9~19min 高码率 serving）。
  - 问题3（直播）：OBS 单遍实时 NVENC 编码(CBR 直传，含 B/lookahead)无第二阶段 → 无转码脉冲/积压/二次上传；输出码率=上行可承受值→无积压；单份最终码率→无翻倍。
- **关键前提挑战**："录制须无 B/lookahead 才不拖游戏"大概率错误——NVENC 是 GPU 上与 3D 引擎物理分离的独立硬件块，B 帧只吃编码引擎时片与少量帧缓冲，不抢游戏渲染。真凶实为 CPU libswscale scale / 磁盘 I/O / 并发第二转码进程抢 NVENC/PCIe。
- **新主推 E0（直播单遍模型，取代 R0）**：录制即按最终质量单次 NVENC 编码（B 帧/lookahead/中等 preset/CBR≈上行 X%），实时令牌桶限速上传，无转码阶段。四目标全满足；改动中低（录制参数+删 transcoding 批处理+上传限速固化）。E0 ≠ D1（D1 当年因"无 B/lookahead→高码率"失效，E0 允许 B 帧且输出即成品）。
- **退守 E1**：若"无 B/lookahead"前提被坚持不可推翻 → 录制期不上传，stop 后单进程转码(12min/2h)+限速上传(3~7min)，接受 12-19min 停等但 CDN 始终单份 3M 无翻倍窗口，严格优于 R0。

### T0 真机复测：黑屏（~20:59，用户）

### 用户关键转向：B 帧/lookahead 实时性 + 无自修复（晚 22:21）

- **用户核心论断（主理人判定：方向正确）**：
  - 「原本无 B 帧/无 lookahead 录制，大部分时候没问题；一旦某帧追不上后续全卡」→ 印证当前录制编码器（`recording/index.ts:427-429` = `h264_nvenc -rc vbr -cq 26 -b:v 0 -preset p4 -tune ll -rc-lookahead 0`，无 -bf、lookahead=0）正是「原本」配置。
  - 「在录制层加入 B 帧、lookahead 后，基本全是从一开始就塌陷」→ 用户手动加了 B 帧/lookahead 测出的。机理精修：**B 帧重排缓冲 + lookahead 缓冲都是有界小缓冲（<1s），真正杀手是单帧编码延迟被抬高超过 33ms(@30fps)实时预算 → 编码器追不上源 → lavfi 捕获源被背压 → inferredCaptureFps 从一开始就掉**。`-tune ll -rc-lookahead 0`（无 B 帧）是 pass-through 低延迟，故原本大部分能跟上。
  - **结论：录制层绝不能有 B 帧/lookahead**。B 帧/lookahead 只配留在**离线转码层**（transcoding/index.ts、external-transcode/index.ts 的 `-bf 2 -rc-lookahead 20` 是对的，因为批量不绑实时预算）。

- **用户更深洞察（真方向）**：「无 B 帧大部分时候没问题，区别在于没有自修复系统，一旦某帧没追上后续全卡」→ 结合 inferredCaptureFps 从 25 平滑单调塌到 5~8 不反弹，真模型 = **无 B 帧低延迟（已满足，必要不充分）+ 缺掉队后自动追平/反压 drain 机制**；偶发瞬时抖动（系统调度/磁盘IO/DWM 抢占）填了一点缓冲后**再也 drain 不回来** → 正反馈 → 逐步滑落稳态低值。完整修法 = 无 B 低延迟 + 加自修复/反压 drain。
- **当前复测基线（已还原）**：`shared.ts` → SKIP_TRANSCODE_IN_MODE_A=true / USE_VFR_RECORDING=true / CUDA_DIRECT_ENCODE=false / RECORD_MINIMAL_FILTER=false；录制编码器无 B 帧低延迟。用户用 ddagrab 全屏录 4min+，读 `diag-<sessionId>.log` 看 inferredCaptureFps 是否仍有平滑单调下滑（即「无自修复锁死」现象），作为下一步设计自修复机制的输入。
