## 2026-07-14 · window_capture.exe 第三道坎 + 编译问题全部闭环（真机验证通过）
- 用户构建机重编（`[this, &]`→`[&, this]` λ 语法修复已生效）后，实跑 `--pid 5820 --mux-target null --stats` **全链路跑通**：
  - `d3d11 device created (NVIDIA)` → `winrt init` → `[diag] apt=1 sizeof=12` → DQTAT_COM_NONE 失败、DQTAT_COM_STA 兜底成功。
  - **`FrameArrived registered on tid=1696`（≠ 主线程 tid=35960）** → 证明 WGC 会话已确认运行在 dispatcher 专用 STA 线程（带消息泵），**第三道坎 `no frame captured` 收口**。
  - `onFrameArrived #1 ~ #221` 刷帧 → `nvenc init done` → `{"type":"READY",...h264_nvenc,hasAudio:0}` 握手成功 → `out_bps` 有编码字节。
- **`--mux-target null` = 丢弃，不落盘、无录屏文件**（仅验证管道用）。三态：pipe（默认，交 Electron 主进程）/ file（私起 ffmpeg-mux 封装 HLS 到 `--out <dir>`，产出 index.m3u8 + segNNN.ts）/ null。
  - 看真实录屏：`--mux-target file --out <目录>`，用 VLC/hls.js 开 index.m3u8。默认 outDir 为空会写到驱动器根（需管理员），**必须显式 `--out`**。
- **`capture_fps` / `cpu_pct` 语义澄清（重要，纠正上轮误判）**：
  - `capture_fps` = 主循环每 33ms 调 `winrt.consumeNewFrame()`，**仅当真正收到"新一帧"才 +1**（main.cpp L674-676）。WGC 是**变更驱动**：目标窗口 DWM 仅在画面真正变化时才 present 新帧。故**静态窗口（如静止的记事本、用户未打字/滚动）capture_fps 贴近 0 是正确行为，不是 bug**（上轮"fps 应回 ~30"的判断错误）。日志里 0↔21 的起伏对应用户无意识操作（鼠标划过/点击/焦点变化）触发的重绘。
  - `cpu_pct`（stats.cpp L86-105）= **本进程 `window_capture.exe` 自己的 CPU 占用，按"占满一个逻辑核心 = 100"计量**（非整机%、非 GPU%），`GetProcessTimes` 取内核+用户态时间增量 / 墙钟，1.5s 采样窗平均。`gpu_pct` 是 NVENC/GPU 占用（NVML 退路）。
  - 静态窗口下偶发 `cpu_pct=100`：最大概率是**操作突发**（capture_fps 冲高那段每帧做 BGRA→NV12 转换 + NVENC + onFrameArrived fprintf 探针）和**启动初期** D3D11/NVENC 初始化一次性开销，被 1.5s 平均窗平滑。若"capture_fps 连续多秒=0 且 cpu_pct 仍持续 100%"才真反常（主循环没 sleep / 某线程空转），须另查。
  - 结论：`onFrameArrived` 每帧 fprintf 探针**不是**帧率上不去的根因（根因是静态源），但它确实是无谓 stderr 噪声 + 操作突发时的 CPU 开销，清理无害、可保留单行 `FrameArrived registered` 日志。
- **控制台中文乱码**（"锛屽皾璇?"等）是 stderr UTF-8/GBK 编码不匹配的纯显示问题，不影响功能；原文 = "CreateDispatcherQueueController(DQTAT_COM_NONE) failed: hr=0x80070057，尝试 DQTAT_COM_STA 兜底" / "用 DQTAT_COM_STA 成功"。

## 2026-07-14 · "无视频输出" 排错：用法 + 两处真实代码缺陷闭环
- 用户跑 `window_capture.exe --pid <记事本> --mux-target null --stats` 报"没有视频输出"。
  - **根因是用法**：`--mux-target null` 模式把写端 fd 置 -1（`mux_target.cpp` / `pipe_output.cpp`），所有 `writeVideoPacket` 直接 no-op，**设计如此不落盘任何字节**。"无视频"非 bug，正解是 `--mux-target file --out <dir>`（私起 ffmpeg 封装 HLS 到 index.m3u8 + segNNN.ts）或 `--mux-target pipe`（交 Electron 主进程）。
  - 静止记事本用 WGC 是变更驱动，capture_fps 贴近 0 正常（见上条），不要因此误判。
- **两处真实代码缺陷已修（工程师静态改 + QA 静态评审全 PASS，判定 NoOne，沙箱无 C++ 工具链未编译）**：
  1. `main.cpp` 主循环（约 L673-709）：原每 tick 末尾 `if (!lastVideoPacket.empty()) pipe.writeVideoPacket(...)` **无条件重发上一帧**，导致"hasNew 且编码成功"的同一 tick 新帧被写两次 → muxer 给两相同帧连续 PTS → HLS 重复帧抖动。修复：引入 `bool wroteFresh=false`，仅当 `!wroteFresh && !lastVideoPacket.empty()` 才回放（冻结帧保活逻辑保留）。
  2. `winrt_capture.cpp` `onFrameArrived`（约 L384-389）：调试遗留每帧 `fprintf(stderr,...)`，30fps 热路径每秒刷 30 行 + 占 CPU。修复：节流为 `n==1 || n%300==0` 才打印（首帧信号 + 每 ~10s 心跳），噪声降 ~300×。
- 用户真机待重编验证：`rmdir /s /q electron\bin\capture-src\build` → `powershell -ExecutionPolicy Bypass -File .\electron\bin\capture-src\build.ps1` → `.\electron\bin\window_capture.exe --pid <PID> --mux-target file --out C:\tmp\rec --stats`。

## 2026-07-14 · "file 模式 Ctrl+C 终止后输出目录为空" 根因修复闭环
- 用户跑 `--mux-target file --out C:\tmp\rec --stats` 录记事本（中途最小化/被遮挡各一次），Ctrl+C 终止后 `C:\tmp\rec` 空文件夹。日志 `out_bps>0`/`encode_fps>0` 证明编码在产码，但目录空。
- **根因（两叠加）确诊**：
  1. exe 未注册 Ctrl+C 处理器（`main.cpp` 仅 stdin 读 'q' + 窗口关闭回调能置 `g_quit`）。终端按 Ctrl+C → Windows 默认 `TerminateProcess` 直接杀 exe → 主循环来不及 `mux.stop()` → 私有 spawn 的 ffmpeg 被打断未 finalize HLS → 目录空。
  2. file 模式未建 `--out` 目录（`mux_target.cpp` 直接把 `C:\tmp\rec\seg%03d.ts` 交 ffmpeg，ffmpeg HLS 不自动建目录 → 目录缺失败静默落空）。
- **修复（工程师静态改 + QA 静态评审全 PASS，判定 NoOne，沙箱无工具链未编译）**：
  - `main.cpp` 匿名 namespace 新增 `BOOL WINAPI ConsoleCtrlHandler(DWORD)` 置 `g_quit=true`，在 `main()` 启动诊断后 `SetConsoleCtrlHandler(ConsoleCtrlHandler, TRUE)` 注册（早于 init_apartment / 主循环）。与 Electron stdin 'q' 退出路径不冲突（都只置 g_quit，汇入同一清理）。
  - `mux_target.cpp` 文件级匿名 namespace 新增 `createDirRecursive(dir)`（逐分隔符 CreateDirectoryW + 末 GetFileAttributesW 校验）。
  - `init()` File 分支在 outW 计算后、拼 segFile/m3u8 前调 `createDirRecursive`，失败则清理已建管道句柄（QA 第一轮发现早返回漏关 readV/writeV/readA/writeA 四句柄 → 工程师补 CloseHandle 后复核 PASS，handle-leak 消除）再 `return false`。
  - `stop()` 把 `WaitForSingleObject(m_muxProc.hProcess, 5000)` 改带超时判定，超时 `TerminateProcess` 强杀兜底，避免 ffmpeg 卡 finalize 拖挂主进程。
- **结论**：修复后 Ctrl+C 走优雅退出 → g_quit → 主循环退出 → mux.stop() 关写端 → ffmpeg 收 EOF finalize HLS 落盘。`C:\tmp\rec\index.m3u8` + `seg000.ts` 应正常产出。用户真机重编验证中。
