# CoWatch 项目记忆 2026-07-11

## 本日关键决策
- **sentinel 技术路线拍板为 Python**：用户确认本机无 Rust 环境且不会编译，放弃 Rust/Cargo 路线。改用 **Python 3 + ctypes（零第三方运行时依赖）+ PyInstaller 单文件打包**，产出同名 `electron/bin/window_sentinel.exe`。原因：① 互联网无现成等价 exe（Cmdow/winmote 是查询工具非事件钩子；AHK 需另装环境）；② Python 已装（managed 3.13.12），PyInstaller 纯 Python 包无需 C 编译；③ 规避"另一个 AI 写的 Rust 源码靠不靠谱"隐患，Python 版我们自己从零写完全可控；④ 产出 exe 走完全一致 stdout 协议（RECT/PAUSE/RESUME/STOP MOVED/STOP CLOSED/NOT_FOUND），sentinel-client.ts / recording 层 / UI 全不改。
- **v2.1 设计行为模型已闭环（用户拍板，四种行为由 SetWinEventHook 全可区分）**：
  - 移动（LOCATIONCHANGE，前台可见，去抖确认）→ END（stop 干净结束，非续录）
  - 最小化（MINIMIZESTART）→ PAUSE
  - alt+tab/切走（FOREGROUND hwnd≠目标）→ PAUSE
  - 遮挡/toast 重叠（无 FOREGROUND 变化）→ **照常录制**（决策2）
  - 关闭/销毁（DESTROY）→ END
  - 最小化恢复/切回（MINIMIZEEND/FOREGROUND==目标）→ RESUME（续号续录，复用 crash-restart 的 -hls_start_number）
  - 单屏（决策4，暂不考虑多屏）；段间隙由固定 Electron webview 播放器按 EXT-X-DISCONTINUITY/段列表跳放（决策3，确定可验证）
- **sentinel vs koffi/zeromq vs OBS 对比结论**（架构师评估）：
  - koffi=NAPI addon 须 @electron/rebuild 对齐头文件 + Node 主线程阻塞消息泵须自建 worker；zeromq.js 带原生二进制；且决策1-4 已消灭动态 crop 需求→两者完全不必要。
  - OBS 注入（DLL hook swap-chain + 反作弊兼容）工程量/封号风险 10x 以上，DDA 已根治根因，否决。
  - sentinel 编译只是给现有小工具加事件→最优解；Python 版进一步免去 Rust 工具链门槛。

## 7.11 下午：结束录制无法退出 BugFix（已闭环 ✅）
- **现象**：用户 7.11-2.md 日志——点击结束录制后 UI 已切停止态，但 ffmpeg 仍在输出、转码器反复重新转码（日志冒出第三个 ffmpeg 重写 seg009.ts）。
- **根因（两段，已定位）**：
  - A=协调层 `stop()` 守卫 `if (!isRecording() && !isUserStopped) return;` 依赖 `isRecording()`（= `ffmpegProcess!==null && !isUserStopped`）。当 `PAUSE` 与 `STOP` 几乎同时到达时 `pauseRecording` 已同步把 `ffmpegProcess` 置空 → `isRecording()`=false → `stop()` 直接 return，stopSentinel/stopRecording/tmpdir 清理全被跳过，ffmpeg 变孤儿（UI 因 `autoStopped` 事件先发已切停止态）。
  - B=recording `stopRecording()` 仅通过 `ffmpegProcess` 杀进程（含 15s SIGKILL 兜底），pause 置空后杀不到真实进程；且 pause 先杀 audio_capture 使 ffmpeg stdin(pipe:0) 关闭、延迟 `q` 失效。
- **修复（寇工，IS_PASS:YES）**：
  - `recording/index.ts` 新增 `let liveFfmpeg`（始终指向真实 ffmpeg 进程）；`spawnFfmpeg` 末尾 `liveFfmpeg=proc`；`attachFfmpegHandlers` close handler 补 `if (liveFfmpeg===proc) liveFfmpeg=null`。
  - `stopRecording()` 改 `const proc = ffmpegProcess ?? liveFfmpeg`，win32 尝试优雅 `q`（try/catch），幂等 `finish()`（`proc.on('close',finish)` + 15s `SIGKILL` 兜底用闭包 `proc`，`resolved` 防重复 resolve 并清空 liveFfmpeg/ffmpegProcess）。
  - `pauseRecording()` 200ms 定时器 `old.stdin.write('q')` 包 try/catch。
  - 协调层 `stop()` 守卫改 `if (isUserStopped) return; if (!recordingLaunched && !sentinelActive) return;`（不依赖 isRecording，in-flight pause 不再 bypass）。
- **QA 回归（重要教训）**：第 1 轮 QA 子代理误报"只有单体 1365 行 index.ts、无 recording/ 子目录、修复未落盘"，路由 Engineer——**经主理人直接 `ls`/Read 磁盘核实，模块化结构真实存在、改动已 `git status` M 落盘，第 1 轮 QA 建立在虚假前提上，路由无效**。第 2 轮 QA 用正确路径重跑：6 处改动全 PASS、tsc 无新增错误、路由 NoOne。**教训：子代理若报"文件不存在/修复未应用"，主理人必须先亲自查磁盘确认，不可直接采信其路由。**
