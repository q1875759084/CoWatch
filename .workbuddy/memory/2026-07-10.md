# 2026-07-10 续：录制卡顿根因再排查（GPU 争用 / 捕获机制）

## 关键转折：fps=30 强制使 inferredCaptureFps 指标失效
- 用户让寇豆码把 gfxcapture 加回 `fps=30`（回退到 6c0772e 旧值），实测：**inferredCaptureFps 恒为 ~30，但视频仍卡顿**。
- **机理**：lavfi 源被钉 30fps PTS 节奏 → WGC 在游戏负载下交付稀时，gfxcapture 每次请求都回吐"最新一帧"（30 次取、18 次内容重复）→ ffmpeg 收到 30 个帧对象 → `dup=0`、指标盲、但**内容只更新 ~12fps → 视频卡**。即 `inferredCaptureFps` 在全强制 fps 下完全不反映真实捕获率。
- **结论**：这次"加回 fps=30 仍卡"**不能用于判因果**——指标被钉死，测试被污染。回归假设（5255422/6002da7 删 fps=30 导致退化）**未被证实也未被证伪**，需无强制 fps 才能测。
- **致命连带事实**：旧版(6c0772e) gfxcapture **也带 fps=30**。所以"旧版没这么糟"的记忆可能是**假象**——旧版同样 mask 了捕获饥饿，真实捕获率未必高；当时"顺"可能只是负载轻或用户未察觉（游戏帧率与捕获帧率解耦）。真正对照必须在**去掉 fps=30** 后测 inferredCaptureFps 才能见真实捕获率。

## 真根因（收敛到架构级）
- 编码侧已彻底排除非瓶颈（terminal5: speed≈1x, dup=0, drop=0, 编码fps=收到fps）。
- 真瓶颈 = **捕获源在游戏 GPU 负载下被节流**：WGC(gfxcapture)/DDA 经 DWM，呈现率随游戏负载降 → 捕获帧率从低起点单调下滑、负载松即回弹（终端5 终点 29fps 爆发）。单 GPU 下 CoWatch 复制引擎往返 + NVENC + 采集本身与游戏共享功耗/热/显存带宽预算，热节流→游戏呈现降→WGC 采集降。
- **为什么 OBS 直播不卡**：OBS Game Capture 挂钩游戏 D3D11/D3D12/Vulkan swap-chain，直接从后缓冲读帧**绕过 DWM**；CoWatch 走 WGC 被 DWM 门控。差异在捕获机制，不在硬件编码（两边都用 NVENC 实时编码+推送）。
- **根解 = 捕获机制重写**：① 轻量验证先试 DDA(ddagrab) 干净对照（不同采集路径争用曲线或不同）；② 根治是引入 swap-chain 级游戏捕获（DLL 注入挂钩 Present，读后缓冲，绕过 DWM），属架构级重构（Rust/C++ 注入模块 + 共享内存/pipe 喂 ffmpeg 或直连 NVENC SDK）。
