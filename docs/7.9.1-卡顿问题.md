# 录屏卡顿问题

## 现象

1. **10 秒周期迟滞感**：录制过程中，每 ~10 秒（GOP 间隔）出现一次操作迟滞感。
2. **累积性卡顿**：一旦从某个时间点开始卡顿，后续全流程持续卡顿，不会自愈。
3. **无上传积压**：录制结束时上传队列完全排空，无 pending 切片。

## 环境

- Windows 高性能电源模式
- NVENC 硬件编码
- 录制层 + 转码层 + 上传层全开

## 可疑根因（待隔离确认）

### 假设 A：转码层 per-segment spawn 架构

当前转码架构每 10 秒一次：

```
录制层: I帧编码 + 关闭 segN.ts + 打开 segN+1.ts  ← 自身就有 CPU/I/O burst
转码层: chokidar检测 → spawn新FFmpeg → 解码segN → NVENC初始化 → 再编码
         ↑ CPU burst + I/O burst 和录制层在切片边界重合
```

**验证方式**：关掉转码层，只录制，观察 10 秒周期迟滞感是否消失。

### 假设 B：录制层自身 GOP 边界开销

录制层每 10 秒编码 I 帧（算力最大），加上文件切换（close segN / open segN+1），二者叠加是否导致丢帧。

**验证方式**：若假设 A 排除，检查录制层 FFmpeg stderr 帧率。

### 假设 C：GPU 共享资源争抢

虽 NVENC 是独立 ASIC、支持多 session，但：
- CPU 解码 + scale filter 不是 NVENC 做的，走的是 GPU 的 compute 或 CPU
- 两个 FFmpeg 进程在同时读/写同一磁盘、同时做 filter
- 可能不一定是 NVENC 芯片本身饱和，而是 NVENC 外围（内存带宽、PCIe 带宽、CPU 调度）在边界处形成瓶颈

**验证方式**：任务管理器观察 GPU 利用率、显存带宽。

## 分析思路

"累积性不可自愈" + "无上传积压" → 排除上传瓶颈、磁盘满。

10 秒间隔 = GOP 间隔 → 和分段机制强相关。

两个现象（周期迟滞 + 累积性卡顿）大概率同源：录制是实时流，丢一帧补不回来 → 后续帧错位 → 永久卡顿。

## hwdownload：根本瓶颈

录制层 filter 链：

```
ddagrab/gfxcapture → hwdownload → format=bgra → scale(CPU) → format=yuv420p → NVENC
                         ↑
                    帧拷贝到 CPU 内存（~8MB/帧 × 30fps = 240MB/s PCIe）
```

**每帧做完一个 GPU → CPU → GPU 的 PCIe 往返。**

而 OBS / N 卡回放走的是一套零拷贝管线：

```
GPU surface → NVENC（直接编码，帧不离开显存）
```

对比：

| | CoWatch 当前 | OBS / N 卡回放 |
|---|---|---|
| 帧传输 | GPU → CPU → GPU（PCIe 往返） | GPU → NVENC（零拷贝） |
| scale | CPU | GPU（CUDA/VAAPI） |
| format 转换 | CPU | GPU |
| PCIe 带宽占用 | ~240 MB/s + 编码后回传 | 仅编码后输出 |

`hwdownload` 是为了 libx264 软编兜底加的（需要 CPU 才能跑 x264），但用 NVENC 时它是纯开销。每 10 秒 I 帧边界算力需求最大、PCIe 吞吐峰值最高，刚好打穿带宽 → 丢帧 → 永久卡顿。

## 可行性验证（ffmpeg 8.1，gyan.dev Windows 构建版）

### 结论：GPU scale 可行，零拷贝不可行

| 测试 | 结果 | 原因 |
|------|------|------|
| `hwmap=derive_device=cuda` (D3D11→CUDA) | ❌ `-40: Function not implemented` | 此构建版不支持 D3D11→CUDA hwmap |
| `-init_hw_device cuda=cuda:0` + ddagrab | ❌ `Selected output not supported` | CUDA 和 D3D11 device context 冲突 |
| `hwupload_cuda` 自动初始化 CUDA | ✅ 无需 `-init_hw_device` | `hwdownload → hwupload_cuda` 自动建立 CUDA context |
| `scale_cuda` (bgra→nv12) | ❌ 不支持 bgra→nv12 | 此构建版 scale_cuda 不支持该像素格式转换 |
| `hwdownload → format=nv12 → hwupload_cuda → scale_cuda → NVENC` | ✅ 29fps 稳定 | CPU bgra→nv12 + GPU scale + GPU 编码 |

### 可实现的最佳管线

```bash
# 双显卡/笔记本通用方案（仅 hwdownload 是 CPU 路径，其余 GPU）
ffmpeg \
  -f lavfi -i "ddagrab=output_idx=0:framerate=30" \
  -vf "hwdownload,format=bgra,format=nv12,hwupload_cuda,scale_cuda=w='min(iw,1280)':h=-2:format=nv12" \
  -c:v h264_nvenc -preset p4 -tune ll ...
```

对比当前管线：

| 步骤 | 当前 | 改后 |
|------|------|------|
| hwdownload (GPU→CPU) | ✅ | ✅（双显卡必须） |
| scale | CPU | **GPU (scale_cuda)** |
| format 转换 | CPU yuv420p | CPU nv12（更轻量，NVENC 原生格式） |
| NVENC 编码 | GPU | GPU |
| 预期改善 | — | scale 开销从 CPU 移到 GPU，减轻 10s 边界 CPU 争抢 |

## 全链路 33ms 帧预算（修正版）

每帧 30fps = 33.3ms 时间窗口。当前 CPU scale 管线：

```
ddagrab GPU 捕获 (2560×1600 RGBA, ~16MB)
  → hwdownload [GPU→CPU DMA, 单次 API 调用, ~2.5ms]
     └── D3D11 CopySubresourceRegion → 内核态 → GPU 驱动 → DMA 引擎 → PCIe 传输 → 中断 → 返回
     └── 没有独立的 IPC 开销，GPU 驱动本身就是内核模块，一条 API 走完
  → format=bgra [CPU, ~5ms]
  → scale 2560→1280 [CPU libswscale 单线程逐像素, ~8ms]
  → format=yuv420p [CPU RGB→YUV 转换, ~5ms]
  → NVENC 隐式上传 [CPU→GPU DMA, 1280×720 YUV420p ~1.4MB, ~1ms] ← 少算了这一步
  → NVENC 编码 [GPU ASIC, 0ms CPU]
```

**帧走了 GPU → CPU → GPU 完整往返**：去 16MB 原始帧，回 1.4MB 压缩后帧。

每 10 秒 GOP 边界额外叠加：

| 额外开销 | 说明 | ~耗时 |
|---------|------|------|
| 关闭 segN.ts + 打开 segN+1.ts | 文件系统操作 | ~3ms |
| I 帧编码 | NVENC 独立芯片，不占 CPU | 0ms |
| chokidar spawn 转码进程 | 新 FFmpeg 进程创建 + NVENC 初始化 | ~10ms |

**边界帧 CPU 预算：**

```
                    CPU scale（当前）     GPU scale（改后）
                    ──────────────       ──────────────
hwdownload DMA         ~2.5ms              ~2.5ms
format(CPU)             ~5ms               ~3ms  (bgra→nv12 比 yuv420p 轻)
scale                    ~8ms (CPU)         0ms  (scale_cuda on GPU)
NVENC 隐式上传           ~1ms               0ms  (hwupload_cuda 显式上传后帧已在 GPU)
close/open seg           ~3ms               ~3ms
I 帧编码(NVENC)          0ms                0ms
chokidar spawn          ~10ms              ~10ms
────────────────────────────────────────────────────
CPU 合计                ~29.5ms            ~18.5ms
余量                     ~3.8ms ← 危险     ~14.8ms ← 安全
```

边界帧 CPU 预算超 33ms → 丢帧。录制是实时流，丢一帧永不补回 → 累积性卡顿。

## GPU scale 跨厂商方案

此 FFmpeg 构建版同时支持三种 GPU scale filter：

| 编码器 | GPU scale filter | 适用显卡 |
|--------|-----------------|---------|
| `h264_nvenc` | `scale_cuda` | NVIDIA |
| `h264_qsv` | `scale_qsv` 或 `scale_vulkan` | Intel Arc / 核显 |
| `h264_amf` | `scale_vulkan` | AMD |

`scale_vulkan` 是跨厂商通用方案，但需要额外的 Vulkan device 初始化。当前 `detectEncoder` 已有编码器检测逻辑，GPU scale filter 选择可直接挂载在同一 switch 里。

hwdownload **不能**在此构建版中去掉（D3D11→CUDA hwmap 不支持，双显卡笔记本必须过 system memory），但它是 DMA 操作（不烧 CPU 算力），不是瓶颈。瓶颈是 CPU 上的 scale + format 转换。
