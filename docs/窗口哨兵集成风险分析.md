# window_sentinel.exe 集成风险分析

> 分析对象：通过 Rust 工具链编译的 `window_sentinel.exe` 集成到 CoWatch Electron 主进程  
> 通信模式：`spawn()` + stdout pipe（对标 `audio_capture.exe`）  
> 监听机制：`SetWinEventHook(EVENT_OBJECT_DESTROY)` + hwnd 精确匹配  
> 日期：2026-06-30

## 一、进程间通信（IPC）风险 — LOW

### 通信机制

```
Electron 主进程 (Node.js)          window_sentinel.exe (Rust)
        │                                  │
  spawn() ←──── stdio ────────→  SetWinEventHook
        │                                  │
  readline ←── stdout pipe ←── "CLOSED\n"
        │                                  │
  stderr ←── stderr pipe ←── 日志/错误
        │                                  │
  close   ←── exit code    ←── 退出
```

### 为什么 LOW

| 对比维度 | audio_capture.exe | window_sentinel.exe | 结论 |
|---------|------------------|--------------------|----|
| stdout 输出量 | 连续 PCM 流（48kHz × 2ch × 16bit = ~1.5MB/s） | **1 行文本 "CLOSED\n"（7 bytes）** | sentinel 的 stdout 量是 audio_capture 的百万分之一 |
| 通信持续时间 | 整个录制过程持续输出 | 窗口关闭后输出 1 行即退出 | 极短生命周期 |
| Node.js 侧处理 | `audioPipe.stdout.pipe(proc.stdin)` — 双向 pipe | `readline` — 单行读取 | 更简单的 IPC 模式 |
| 已验证的稳定性 | audio_capture PCM pipe 已在生产环境稳定运行 | stdout readline 是 Node.js 最基础的 IPC | 复用已验证模式 |

**关键事实**：项目已有两套 stdout/stderr pipe IPC（ffmpeg stderr 解析 + audio_capture PCM 流），**两者都比 sentinel 的 IPC 复杂得多**。sentinel 只输出 1 行文本，是整个项目中最简单的 IPC 通道。

### 潜在问题与对策

| 问题 | 可能性 | 影响 | 对策 |
|------|-------|------|------|
| stdout 缓冲未 flush 进程就退出 | 极低（Rust stdout 自动 flush on exit） | 丢失 CLOSED 信号 | sentinel 在输出后显式 `flush()` + sleep 100ms 再退出 |
| Node.js readline 在进程 close 后才收到 data | 极低（Node.js 在 close 事件前 drain stdout buffer） | 延迟 <1ms | 无需额外处理，Node.js 保证顺序 |
| Windows 管道缓冲区溢出 | 不可能（7 bytes vs 4KB 默认缓冲） | N/A | N/A |

## 二、进程间竞态风险 — MEDIUM

### 竞态场景 A：用户手动 stop vs 窗口关闭同时发生

```
时间线：
  t0: 用户点击停止按钮 → stop() → isUserStopped = true
  t1: 窗口恰好同时关闭 → sentinel 输出 "CLOSED"
  t2: Node.js readline 收到 "CLOSED" → 调用 stop()
  t3: stop() 检查 isUserStopped === true → 直接 return
```

**结论：安全**。现有代码 `stop()` 第 1135 行 `if (isUserStopped) return` 是幂等守卫，双重调用无副作用。

但有一个微妙的时序问题需要关注：

```
时间线（反向）：
  t0: 窗口关闭 → sentinel 输出 "CLOSED" → readline 收到 → 调用 stop()
  t1: stop() 设置 isUserStopped = true → 开始 cleanup → kill ffmpeg + sentinel
  t2: 用户恰好也点击停止 → stop() → isUserStopped = true → return
```

**结论：同样安全**。无论谁先触发，`isUserStopped` 守卫都保证只有一个 `stop()` 流程完整执行。

### 竞态场景 B：ffmpeg crash restart 期间窗口关闭

```
时间线：
  t0: ffmpeg crash → handleFfmpegCrash() → 重启 ffmpeg
  t1: 窗口关闭 → sentinel 输出 "CLOSED" → readline 收到
  t2: 调用 stop() → isUserStopped = true → cleanup → kill 新 ffmpeg + sentinel
  t3: handleFfmpegCrash() 后续代码检查 isUserStopped → return（不再重启）
```

**关键：sentinel 不应被 crash restart 重启**。原因：
1. ffmpeg crash 是编码器问题，与目标窗口无关
2. 目标窗口还在 → sentinel 应继续监听
3. 如果重启 sentinel，会出现短暂的无监听窗口（新 sentinel EnumWindows → hook 安装 → 消息循环，约 100ms）

**对策**：`handleFfmpegCrash()` 中**不 kill sentinel**，仅重启 ffmpeg。sentinel 在整个录制会话中只启动一次，只在 `cleanup()` 或窗口关闭时退出。

### 竞态场景 C：sentinel 输出 CLOSED → 同时 cleanup 正在 kill sentinel

```
时间线：
  t0: 用户点击 stop → cleanup() → sentinel.kill()
  t1: Windows 向 sentinel 发送 SIGINT/SIGTERM
  t2: sentinel 还未退出 → 此时窗口恰好关闭 → SetWinEventHook 回调触发
  t3: sentinel 输出 "CLOSED" → stdout pipe 仍然活跃
  t4: Node.js readline 收到 "CLOSED" → 调用 stop() → isUserStopped = true → return
  t5: sentinel 收到 SIGTERM → 正常退出
```

**结论：安全**。`isUserStopped = true` 在 `stop()` 的 1141 行就设置了，比 cleanup 更早。即使 readline 在 cleanup 期间收到 CLOSED，`stop()` 的幂等守卫也会忽略。

### 竞态场景 D：sentinel 进程异常退出（非窗口关闭）

这是最需要注意的竞态。sentinel 可能因为自身 bug 崩溃，此时需要区分：

| sentinel 退出原因 | exit code | stdout 输出 | Node.js 侧应做什么 |
|-----------------|-----------|------------|------------------|
| 窗口关闭 → 正常退出 | 0 | "CLOSED\n" | 调用 `stop()` |
| sentinel 自身崩溃 | 1 或非 0 | 无或部分输出 | **不应调用 stop()，应 fallback 到方案 A（轮询）** |
| sentinel 被 kill（cleanup） | SIGTERM (15) | 无 | 无操作（已在 stop 流程中） |

**对策**：Node.js 侧同时监听 sentinel 的 **stdout data** 和 **close** 事件：
- `stdout readline` 收到 "CLOSED" → 调用 `stop()`（窗口关闭，业务逻辑触发）
- `close` 事件 且 未收到 "CLOSED" 且 `!isUserStopped` → **不调用 stop()**，仅打印警告，启动方案 A 的 desktopCapturer 轮询兜底

```typescript
// recorder.ts 集成伪码
sentinelProcess.stdout.on('data', (line) => {
  if (line.trim() === 'CLOSED' && !isUserStopped) {
    stop(); // 窗口关闭 → 优雅停止录制
  }
});

sentinelProcess.on('close', (code) => {
  // sentinel 退出但未输出 CLOSED → sentinel 自身问题，不是窗口关闭
  if (!isUserStopped && code !== 0 && !receivedClosed) {
    console.warn('[recorder] window_sentinel 异常退出，启动轮询兜底');
    startPollingFallback(displayTitle);
  }
});
```

## 三、窗口关闭监听可靠性 — LOW（正常/崩溃） / HIGH（假死）

### 3.1 窗口正常关闭 — RISK: LOW

**机制**：用户点击窗口 X 按钮 → WM_CLOSE → WM_DESTROY → Win32 DestroyWindow() → `EVENT_OBJECT_DESTROY` 触发。

sentinel 在 hook 回调中检查 `hwnd == targetHwnd` → 输出 "CLOSED" → 退出。

| 场景 | EVENT_OBJECT_DESTROY 是否触发 | sentinel 能否检测 |
|------|------|------|
| 用户点击关闭按钮 | ✅ | ✅ |
| Alt+F4 | ✅ | ✅ |
| 系统关机/重启 | ✅（系统向所有窗口发 WM_CLOSE） | ✅ |
| 任务栏右键关闭 | ✅ | ✅ |

### 3.2 窗口异常崩溃 — RISK: LOW

**关键事实**：Windows 操作系统在进程崩溃/被杀时，会自动清理该进程的所有窗口对象（DestroyWindow），触发 `EVENT_OBJECT_DESTROY`。

| 场景 | Win32 行为 | EVENT_OBJECT_DESTROY | sentinel 能否检测 |
|------|-----------|------|------|
| 目标进程 segfault | OS 终止进程 → 清理所有 hwnd | ✅ | ✅ |
| Task Manager 结束进程 | OS 终止进程 → 清理所有 hwnd | ✅ | ✅ |
| 目标进程 access violation | OS 终止进程 → 清理所有 hwnd | ✅ | ✅ |
| 进程被 `taskkill /F` | OS 终止进程 → 清理所有 hwnd | ✅ | ✅ |
| 目标进程 OOM 被 OS 杀死 | OS 终止进程 → 清理所有 hwnd | ✅ | ✅ |

**结论**：所有"进程异常退出"场景，Windows 都保证 DestroyWindow 被调用，`EVENT_OBJECT_DESTROY` 必然触发。这是 Win32 API 的核心保证，不是灰色地带。

### 3.3 目标进程假死（挂死但窗口仍在） — RISK: HIGH

这是唯一的**真正高风险**场景。

| 场景 | Win32 行为 | EVENT_OBJECT_DESTROY | sentinel 能否检测 |
|------|-----------|------|------|
| 目标进程 UI 线程死锁（窗口无响应） | 窗口 hwnd 仍存在 | ❌ 不触发 | ❌ **无法检测** |
| 目标进程无限循环但未崩溃 | 窗口 hwnd 仍存在 | ❌ 不触发 | ❌ **无法检测** |
| 目标进程 GPU hang（画面冻结） | 窗口 hwnd 仍存在 | ❌ 不触发 | ❌ **无法检测** |

**但这是原问题不变**：在当前代码中，窗口假死时 gfxcapture 会停止产生新帧，ffmpeg 最终也会异常退出，走 crash restart 循环。加入 sentinel **不改善也不恶化**这个问题。

**对策**：方案 A（desktopCapturer 轮询）作为 fallback：
- sentinel 正常监听 → 窗口关闭时 ~50ms 响应
- sentinel 异常退出 → fallback 到每 2s 轮询窗口列表
- 窗口假死 → 两种方案都无法检测 → ffmpeg crash 重启兜底（现状不变）

### 3.4 hwnd 精确匹配的边缘情况

| 边缘情况 | sentinel 处理方式 | 风险 |
|---------|------------------|------|
| 窗口标题动态变化（如浏览器切换标签） | sentinel 初始 EnumWindows 匹配 title → 获取 hwnd → 后续只按 hwnd 匹配，不按 title | ✅ 安全（hwnd 不随标题变化） |
| 同标题多窗口 | sentinel 启动时 EnumWindows 取第一个匹配 → 获取其 hwnd → 精确跟踪 | ✅ 安全（hwnd 唯一） |
| 窗口内部子控件 destroy（如按钮销毁） | `EVENT_OBJECT_DESTROY` 也会触发 → 但 hwnd ≠ targetHwnd → 被过滤 | ✅ 安全 |
| 窗口最小化 → 还原 | `EVENT_OBJECT_HIDE/SHOW` 触发 → 不等于 DESTROY → 被过滤 | ✅ 安全 |
| 窗口被其他窗口覆盖 | 无事件触发 | ✅ 安全（不影响录制） |

## 四、综合风险评估

### 总体风险：**可控，显著低于现状**

| 维度 | 当前无 sentinel | 加入 sentinel 后 | 变化 |
|------|----------------|----------------|------|
| 窗口关闭 → ffmpeg 行为 | 误判为 crash → 无意义重启 3 次 → 暴力报错 | sentinel 检测 → 优雅 stop() → 调用 finish 接口 | ✅ 核心改善 |
| 窗口崩溃 → ffmpeg 行为 | 同上（同误判） | sentinel 检测 → 优雅 stop() | ✅ 核心改善 |
| 窗口假死 → ffmpeg 行为 | crash restart 3 次 | 无改善（但也不恶化） | ↔ 不变 |
| 尾片丢失 | 不调用 stop() → 尾片丢失 | 优雅 stop() → 尾片完整 | ✅ 改善 |
| finish 接口未调用 | 不调用 → 后端无结束标记 | stop() → finish 接口调用 | ✅ 改善 |

### Rust 工具链编译 vs C 编译的额外风险

| 维度 | Rust 编译 | C 编译 (MSVC) |
|------|----------|-------------|
| exe 大小 | ~200KB（含 Rust runtime + windows-rs 绑定） | ~15KB（纯 Win32） |
| 内存安全 | ✅ Rust 编译器保证（无 buffer overflow、无 dangling pointer） | ⚠️ 需人工保证 |
| ABI 稳定性 | ✅ Rust exe 是独立二进制，不受 Electron ABI 影响 | ✅ 同 |
| 编译工具链 | 需要 Rust (rustup + cargo) | 需要 MSVC 或 MinGW |
| 跨平台编译 | ✅ `cargo build --target x86_64-pc-windows-msvc` | ⚠️ 需交叉编译环境 |
| 未来 Arm64 | ✅ `cargo build --target aarch64-pc-windows-msvc` | ⚠️ 需要 Arm64 MSVC |

**结论**：Rust 编译的 exe 比 C 编译的 exe **内存安全更好**，大小差异（200KB vs 15KB）对 electron-builder 打包无实质影响。唯一额外"风险"是需要安装 Rust 工具链——但这是一次性操作，编译后只分发 exe。

### 最终结论

window_sentinel.exe 集成的 bug 风险**整体可控**：

1. **IPC 风险极低** — stdout 1 行文本是项目中最简单的 IPC，比现有 audio_capture PCM 流简单百万倍
2. **竞态风险中等但已守卫** — `isUserStopped` 幏等守卫防止双重 stop，sentinel crash 通过 close 事件 + exit code 区分
3. **监听可靠性** — 正常关闭和异常崩溃均可靠检测（Win32 API 保证），唯一盲区是进程假死（原问题不变）
4. **Rust 工具链** — 编译产物是独立 exe，与 Electron 进程隔离，不受 Electron 版本升级影响

**建议组合**：sentinel（方案 C）作为主检测 + desktopCapturer 轮询（方案 A）作为 sentinel crash fallback。
