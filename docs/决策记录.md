## [已关闭] 视频压缩工具 — H.265 vs H.264

**背景：**
复盘视频为 1080p 60fps 录屏，半小时约 3GB。为降低 CDN 流量和上传耗时，需用户在本地用 ffmpeg 转码压缩后再上传。转码工具以 `.bat` 脚本形式分发，通过网站下载页获取，替代手动打包发送。

H.265（HEVC）相同画质文件大小减少约 40-50%，具有明显优势。2026 年 Chrome 已部分支持 H.265，但支持情况依赖硬件解码器，存在"API 报告支持但实际无法播放"的风险。

**决策：只用 H.264（Option C），永久关闭 H.265 讨论。**

**依据：**

1. **"浏览器支持"≠"设备支持"**：`canPlayType` 检测的是浏览器层面的能力声明，不代表实际硬件可以解码。H.265 在浏览器中依赖 GPU 硬件解码器，老机器可能报告 `"maybe"` 或 `"probably"`，但实际播放时卡顿、黑屏或静默失败。

2. **8人同时支持的概率过低**：复盘要求房间内每一个人都能正常播放同一个视频文件。假设单人设备支持 H.265 的概率为 0.9（已属乐观估计），8人全部支持的概率为 0.9^8 ≈ **43%**，超过一半的场景会有至少 1 人无法播放，导致整个房间不得不换回 H.264 版本重新转码上传。

**被否定的方案：**
- Option A（自动检测动态生成）：可靠性约 85-90%，误判代价过高
- Option B（手动选择）：用户需要理解编码格式，认知负担过重

## [已决策] 转码参数配置 — 位置、范围与交互

**背景：**
不同游戏画面复杂度不同，最优转码参数（主要是 CRF）有差异。需要一套参数配置机制，方便房间成员按需选择档位并下载对应转码脚本。

**决策汇总：**

| 维度 | 决策 | 备注 |
|---|---|---|
| 配置入口 | 右侧控制面板折叠区"编码设置" | 全员可展开，档位选择为纯本地状态 |
| 档位是否落库 | 否 | 非敏感配置，无多端同步价值，各人自选各人下载 |
| 权限校验 | 无 | 非敏感资源，恶意修改无实际危害 |
| WS 广播 | 无 | 档位不需要多端同步 |
| 一期暴露参数 | 只有 CRF（画质档位下拉框） | 分辨率、帧率字段展示但置灰，二期占位 |
| CRF 交互形式 | 预设档位下拉：高画质（CRF 23）/ 均衡（CRF 26）/ 小体积（CRF 28） | 隐藏技术细节，使用语义标签 |
| 下载入口位置 | 房间内参数配置区"下载转码脚本"按钮 | 全员可用，点击下载当前本地选中档位对应 .bat |
| .bat 生成方式（一期） | 三个静态文件，按 query 参数返回 | `GET /api/bat?preset=xxx` |
| .bat 生成方式（二期） | 后端接口动态生成，支持自定义参数 | 参数增多后迁移 |

**新增后端接口（一个）：**
- `GET /api/bat?preset=high|balanced|small` — 无需鉴权，返回对应静态 .bat 文件（`Content-Disposition: attachment`）

**无数据库变更，无 WebSocket 事件变更。**

**二期扩展方向：**
- 解锁分辨率（1080p / 720p）和帧率（60fps / 30fps）字段
- 后端动态生成 .bat，支持自定义参数组合
- 支持 Mac/Linux 用户（生成 .sh 脚本）
- 如有需要，将档位落库并同步给房间成员

## [已决策] 转码参数 — `-preset` 与关键帧间隔

**背景：**
用户反馈 5 分钟 500MB 的视频，服务端 HLS 切片需要 1 分多钟，体验极差。排查后发现两个独立原因：

**问题一：bat 缺少关键帧参数导致服务端被迫重编码**

libx264 默认使用"自适应关键帧间隔"，游戏录屏画面变化小时关键帧间隔可达 30~60 秒。服务端执行 `ffmpeg -c copy` 切片时，若切割点不在关键帧上，ffmpeg 会解码整段视频并重新编码插入关键帧，等同于重转一遍，与文件大小无关。

**修复：** 4 个 bat 均新增以下 3 个参数：

| 参数 | 作用 |
|---|---|
| `-g 120` | 60fps 视频每 2 秒强制插入一个关键帧 |
| `-keyint_min 120` | 禁止 2s 窗口内插入额外关键帧，保证间隔严格一致 |
| `-sc_threshold 0` | 关闭场景切换自动关键帧（游戏场景切换频繁，不加此参数会破坏严格间隔） |

效果：5 分钟视频服务端切片时间从 1 分多钟降到 **1~2 秒**。

**问题二：`-preset fast` 转码速度偏慢**

`-preset` 控制 libx264 在编码时搜索最优预测块的范围和深度，影响转码速度与输出文件大小：

| preset | 相对转码速度 | 文件大小（同 CRF） | 适用场景 |
|---|---|---|---|
| `ultrafast` | ~5x fast | +40-50% | 不推荐，文件膨胀过大 |
| `superfast` | ~3x fast | +30-40% | — |
| `veryfast` | ~2x fast | +15-20% | **当前选择** |
| `fast` | 1x（旧值） | 基准 | — |
| `medium` | ~0.7x fast | -5-10% | — |
| `slow` | ~0.3x fast | -10-20% | — |

**决策：将所有 bat 的 `-preset fast` 改为 `-preset veryfast`。**

依据：转码速度提升约 2 倍，文件体积只增加 15-20%（30 分钟视频约多 0.5-0.6GB），CDN 流量增量在可接受范围内。`ultrafast` 虽更快但文件膨胀 40-50%，CDN 流量代价过高，不采用。

## [已决策] 视频切片架构 — 方案选型与演进路径

**背景：**
CoWatch 需要支持视频的 seek、多人同步播放和第二次复盘 0 流量。不同切片方案在复杂度、流量成本、seek 体验上差异显著。

### 各方案对比

**方案 A：纯 SW 缓存（原方案，已废弃）**
- 描述：SW 拦截浏览器 Range 请求，拼装完整 mp4 后缓存
- 缺点：Cache API 不支持 206 响应，必须用 TransformStream 流式切片模拟，约 300 行复杂逻辑，存在并发 bug；整个文件下载完才能缓存，seek 到未缓存区域需重新拉完整文件

**方案 B：IDB 分块缓存（评估，未采用）**
- 描述：SW 将视频按固定大小（4MB）分块存 IndexedDB，按需拉取
- 优点：seek 精度高，只拉实际观看的分块
- 缺点：CDN 签名 URL 每次变化，cache key 设计复杂；跨天复盘签名过期需要重新拉取；IDB 存储有浏览器配额限制（通常数百 MB 到几 GB）；实现复杂度依然较高

**方案 C：服务端 HLS 切片 + SW cache-first（当前方案）**
- 描述：用户上传 mp4 后，服务端用 `ffmpeg -c copy` 切成 15s 的 `.ts` 片段存 COS；前端用 hls.js 播放；SW 拦截 `.ts` 请求做 cache-first
- 优点：
  - SW 逻辑从 ~300 行降到 ~80 行，所有 Range/并发 bug 自然消除
  - 每个 `.ts` 片段是完整 200 响应，Cache API 原生支持，无需特殊处理
  - seek 只需下载目标片段（~7.5MB），不拉整个文件
  - 第二次播放 0 流量（SW 命中缓存）
  - 跨天复盘：前端重新请求 `/m3u8` 接口刷新签名，SW 缓存的 `.ts` 片段 key 已剥离签名参数，仍命中缓存
- 代价：服务端需要存储 `.ts` 片段（COS 存储费用）；上传后有切片等待时间（修复关键帧参数后 < 5s）

**方案 D：inFlight 去重（一期临时方案，已被方案 C 取代）**
- 描述：在旧 SW 基础上用 Map 记录进行中的请求，同一 URL 的并发请求复用同一个 Promise
- 意义：作为向 HLS 架构迁移前的最小修复，验证并发问题根因；已被方案 C 完全取代

### 当前架构关键参数

- 切片时长：**10 秒**（1 小时视频约 360 片，每片 ~5MB @ 1080p60 CRF30；seek 平均多下载 5s，较 15s 减少约 33% 流量浪费）
- 关键帧间隔：**2 秒**（`-g 120 -keyint_min 120` at 60fps），确保 `ffmpeg -c copy` 切割时无需重编码（关键帧间隔 ≤ 切片时长即满足条件，无需两者相等）
- m3u8 动态生成：每次播放实时生成，片段签名有效期 2h，签名不落库
- SW cache key：剥离 CDN TypeA `sign` 参数和 COS `q-sign-*` 参数，同一片段签名轮换后仍命中缓存

### 部署依赖说明

**容器内需要系统 ffmpeg**（非 `ffmpeg-static`）。

背景：`ffmpeg-static` 提供的是预编译静态二进制，在 Apple Silicon 上走 Rosetta 模拟，5 分钟视频切片需要 1 分钟；在 Linux x86_64 容器内虽无 Rosetta 问题，但版本停在 6.0（2023 年），缺少部分优化。

**解法：Dockerfile runner 阶段加 `apk add --no-cache ffmpeg`**，构建镜像时自动安装系统 ffmpeg（Alpine 6.x，原生编译），`hlsService.ts` 直接调用 `'ffmpeg'`。

层缓存说明：ffmpeg 单独为一层（位于 `npm ci` 之前），只有首次构建会下载，后续代码变更不会重建此层。

---

**COS Bucket 必须与服务器同地域，且 CDN 回源地址须同步更新。**

背景：服务器位于上海（`ap-shanghai`），若 Bucket 在广州（`ap-chengdu`），上传走跨地域公网，实测带宽约 4 Mbps；360 个 .ts 片段（~1.8GB @ 1080p60 CRF30）串行上传需约 60 分钟，并发 5 也需约 12 分钟，体验极差。

**完整迁移清单（必须三处同步改，缺一不可）：**

| 改动点 | 操作 | 说明 |
|---|---|---|
| **腾讯云 COS 控制台** | 在上海地域新建 Bucket（或迁移现有数据） | 旧广州 Bucket 可保留一段时间，确认无流量后再删除 |
| **腾讯云 CDN 控制台** | 将加速域名的回源地址改为上海 Bucket 的域名 | CDN → 域名管理 → 回源配置 → 主源站；改完后 CDN 边缘节点缓存未过期的内容仍会命中，不影响旧内容播放 |
| **服务器环境变量** | `COS_REGION=ap-shanghai`，`COS_BUCKET=新 Bucket 名` | 部署时通过 `.env` 或容器环境变量注入；不需要改代码 |

**同地域后可开启内网加速：**

将 `COS_USE_INTERNAL=true` 写入环境变量，`ossService.ts` 会将 COS SDK 的 `Domain` 设置为 `{Bucket}.cos-internal.{Region}.tencentcos.cn`，服务器→COS 的上传走腾讯云内网，带宽从 ~4 Mbps 提升到 ~500 Mbps，360 个片段并发 5 上传预计 < 30 秒。

> ⚠️ 内网域名仅在服务器与 Bucket **同地域**时可用；跨地域开启会导致请求失败（DNS 解析到内网 IP，路由不通）。

## [二期 TODO] SW 视频缓存 — 按需分片缓存（V4）

**背景：**
当前 V3 方案在首次遇到视频请求时，会拉取完整文件后缓存。实际使用中，复盘通常只观看视频的 1/5 以内，导致每次首次访问仍产生大量不必要的 CDN 流量。

**问题量化（以 320MB / 8 人为例）：**
- V3（当前）：观看 1/5 仍拉取完整 320MB × 8 人 = **2.56GB**
- V4（分片）：只拉实际观看的 ~70MB × 8 人 = **~560MB**，节省约 78%

**方案设计：**

以固定大小（4MB）为单位将视频分块，SW 拦截 Range 请求时只拉覆盖该区间的 chunk，存入 Cache Storage（key 为 `videoUrl?_chunk=N`），后续相同区域命中缓存不再产生流量：

```
CHUNK_SIZE = 4MB

Range: bytes=5_000_000–5_131_071
  → 计算覆盖 chunk_1（bytes 4194304–8388607）
  → cache.match('videoUrl?_chunk=1') 未命中
  → fetch Range: bytes=4194304–8388607（完整 chunk_1，得到 206）
  → 将 chunk_1 的 ArrayBuffer 存为自定义 200 Response，key = 'videoUrl?_chunk=1'
  → 从 chunk_1 中切出目标字节，构造 206 返回给播放器
```

**注意事项：**
- Cache API 不能存 206 响应，chunk 须以自定义 200 Response 形式存储
- 一次播放器 Range 请求通常只跨 1–2 个 chunk，跨 chunk 时需并发拉取后拼接
- 改动集中在 `sw.ts`，不涉及业务代码

**改动范围：** 仅 `src/sw.ts`
