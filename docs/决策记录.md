## [已关闭] 视频压缩工具 — H.265 vs H.264

**背景：**
复盘视频为 1080p 60fps 录屏，半小时约 3GB。为降低 CDN 流量和上传耗时，需用户在本地用 ffmpeg 转码压缩后再上传。转码工具以 `.bat` 脚本形式分发，通过网站下载页获取，替代手动打包发送。

H.265（HEVC）相同画质文件大小减少约 40-50%，具有明显优势。2026 年 Chrome 已部分支持 H.265，但支持情况依赖硬件解码器，存在"API 报告支持但实际无法播放"的风险。

**决策：只用 H.264（Option C），永久关闭 H.265 讨论。**

**依据：**

1. **"浏览器支持"≠"设备支持"**：`canPlayType` 检测的是浏览器层面的能力声明，不代表实际硬件可以解码。H.265 在浏览器中依赖 GPU 硬件解码器，老机器可能报告 `"maybe"` 或 `"probably"`，但实际播放时卡顿、黑屏或静默失败。

2. **8人同时支持的概率过低**：复盘要求房间内每一个人都能正常播放同一个视频文件。假设单人设备支持 H.265 的概率为 0.9（已属乐观估计），8人全部支持的概率为 0.9^8 ≈ **43%**，超过一半的场景会有至少 1 人无法播放，导致整个房间不得不换回 H.264 版本重新转码上传。

**被否定的方案：**
- Option A（自动检测动态生成）：可靠性约 85-90%，误判代价过高
- Option B（手动选择）：用户需要理解编码格式，认知负担过重

## [已决策] 转码参数配置 — 位置、范围与交互

**背景：**
不同游戏画面复杂度不同，最优转码参数（主要是 CRF）有差异。需要一套参数配置机制，方便房间成员按需选择档位并下载对应转码脚本。

**决策汇总：**

| 维度 | 决策 | 备注 |
|---|---|---|
| 配置入口 | 右侧控制面板折叠区"编码设置" | 全员可展开，档位选择为纯本地状态 |
| 档位是否落库 | 否 | 非敏感配置，无多端同步价值，各人自选各人下载 |
| 权限校验 | 无 | 非敏感资源，恶意修改无实际危害 |
| WS 广播 | 无 | 档位不需要多端同步 |
| 一期暴露参数 | 只有 CRF（画质档位下拉框） | 分辨率、帧率字段展示但置灰，二期占位 |
| CRF 交互形式 | 预设档位下拉：高画质（CRF 23）/ 均衡（CRF 26）/ 小体积（CRF 28） | 隐藏技术细节，使用语义标签 |
| 下载入口位置 | 房间内参数配置区"下载转码脚本"按钮 | 全员可用，点击下载当前本地选中档位对应 .bat |
| .bat 生成方式（一期） | 三个静态文件，按 query 参数返回 | `GET /api/bat?preset=xxx` |
| .bat 生成方式（二期） | 后端接口动态生成，支持自定义参数 | 参数增多后迁移 |

**新增后端接口（一个）：**
- `GET /api/bat?preset=high|balanced|small` — 无需鉴权，返回对应静态 .bat 文件（`Content-Disposition: attachment`）

**无数据库变更，无 WebSocket 事件变更。**

**二期扩展方向：**
- 解锁分辨率（1080p / 720p）和帧率（60fps / 30fps）字段
- 后端动态生成 .bat，支持自定义参数组合
- 支持 Mac/Linux 用户（生成 .sh 脚本）
- 如有需要，将档位落库并同步给房间成员

## [二期 TODO] SW 视频缓存 — 按需分片缓存（V4）

**背景：**
当前 V3 方案在首次遇到视频请求时，会拉取完整文件后缓存。实际使用中，复盘通常只观看视频的 1/5 以内，导致每次首次访问仍产生大量不必要的 CDN 流量。

**问题量化（以 320MB / 8 人为例）：**
- V3（当前）：观看 1/5 仍拉取完整 320MB × 8 人 = **2.56GB**
- V4（分片）：只拉实际观看的 ~70MB × 8 人 = **~560MB**，节省约 78%

**方案设计：**

以固定大小（4MB）为单位将视频分块，SW 拦截 Range 请求时只拉覆盖该区间的 chunk，存入 Cache Storage（key 为 `videoUrl?_chunk=N`），后续相同区域命中缓存不再产生流量：

```
CHUNK_SIZE = 4MB

Range: bytes=5_000_000–5_131_071
  → 计算覆盖 chunk_1（bytes 4194304–8388607）
  → cache.match('videoUrl?_chunk=1') 未命中
  → fetch Range: bytes=4194304–8388607（完整 chunk_1，得到 206）
  → 将 chunk_1 的 ArrayBuffer 存为自定义 200 Response，key = 'videoUrl?_chunk=1'
  → 从 chunk_1 中切出目标字节，构造 206 返回给播放器
```

**注意事项：**
- Cache API 不能存 206 响应，chunk 须以自定义 200 Response 形式存储
- 一次播放器 Range 请求通常只跨 1–2 个 chunk，跨 chunk 时需并发拉取后拼接
- 改动集中在 `sw.ts`，不涉及业务代码

**改动范围：** 仅 `src/sw.ts`
