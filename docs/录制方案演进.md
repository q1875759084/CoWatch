# CoWatch 录制方案演进

> 记录 CoWatch 客户端录制链路经历的三次架构转变：单 FFmpeg 直出 → 双 FFmpeg 三层架构 → window_capture.exe。
> 本文基于 git 历史、架构设计文档（`system_design.md` / `obs-wgc-capture-analysis.md`）、开发记忆（`.workbuddy/memory/2026-07-09.md`）与决策记录整理，力求保留每次转变的真实动机与被否决的尝试，避免后人重复踩坑。

---

## 0. 一句话演进线

```
v1 单FFmpeg直出（录制=交付，无B帧高码率）
   ↓ 痛点：录制须低延迟→码率高→CDN/带宽浪费；单文件难维护
v2 双FFmpeg三层（录制轻量→逐片转码提质→限速上传）
   ↓ 痛点：10s转码脉冲迟滞 + CFR dup放大 + 复制引擎往返饿死DWM致fps塌陷；CUDA直编被硬件死锁
v3 window_capture.exe（OBS WGC双线程解耦 + 零拷贝NVENC + 单遍HLS直传）
```

**核心驱动力**：始终是「游戏录制不能拖累游戏帧率」这一硬约束。每次转变都是因为前一方案在「实时性 / 画质 / 带宽」三角中失衡，被迫重新切分职责。

## 1. 阶段一：单 FFmpeg 直出（v1）

### 1.1 架构

```
gfxcapture(窗口) / ddagrab(全屏)
  → hwdownload(GPU→CPU) → CPU scale → hwupload_cuda(CPU→GPU)
  → h264_nvenc(单遍编码)
  → HLS 切片(.ts)
  → chokidar 监听 → net.fetch 直传后端
```

- **单文件协调器**：`electron/handlers/recorder/index.ts` 约 1344 行，录制、上传、窗口检测全塞在一个文件里。
- **录制即交付**：ffmpeg 一遍出 HLS，参数即最终交付参数，无转码阶段。
- **鉴权**：Token Push 模式（渲染进程 start 时传 JWT 到主进程，见决策记录「Electron 录制 — 主进程切片上传鉴权方案」）。

### 1.2 编码参数（git 6c0772e，被用户记得"没这么糟"的版本）

| 项 | 值 |
|----|----|
| 捕获源 | gfxcapture `...:max_framerate=30,fps=30,hwdownload,...` |
| 编码器 | `h264_nvenc -rc vbr -cq 30 -b:v 0 -maxrate 5000k -bufsize 10000k` |
| B 帧 / lookahead | **无**（无 `-bf`、无 `-rc-lookahead`） |
| preset / tune | 无 |
| 帧率模式 | CFR `-r 30` |

### 1.3 痛点（触发 v1→v2）

1. **录制参数 = 交付参数的矛盾**：实时录制为护游戏帧率必须低延迟（无 B 帧、无 lookahead），但无 B 帧的 NVENC VBR 码率显著高于有 B 帧的成品（720p30 的码率逼近 1080p60），既浪费 CDN 流量，又让上传带宽挤占游戏带宽。
2. **无法分别优化"录制实时性"与"交付画质/码率"**：两者绑死在同一遍 ffmpeg 里，调一个必伤另一个。
3. **单文件 1344 行难维护**：录制、上传、窗口检测、状态机耦合，改动风险高。

### 1.4 曾尝试：录制层加 B 帧 → 成片卡顿（解释 v1 为何不直接用 B 帧）

面对痛点 1「无 B 帧→高码率」最直觉的解法是给录制层加上 B 帧/lookahead 降码率。实测否决。

**实验**（memory 2026-07-09 22:21 段；在 v2 的 `SKIP_TRANSCODE_IN_MODE_A=true` 基线上手动加 B 帧——该基线关掉转码层，录制层行为等同 v1 单遍直出，用户当时明确说「此状态 = 最初没有分层架构的时候」）：
- 配置：录制层 NVENC 加 `-bf 2 -rc-lookahead 20`（沿用转码层的高质量参数）
- 结果：**fps 从一开始就塌陷**，`inferredCaptureFps`（ffmpeg 实收帧率）开局即低且单调下滑，录出来的成片卡顿无法看

**机理**（为什么 B 帧会塌捕获）：
- B 帧重排缓冲 + lookahead 缓冲都是有界小缓冲（<1s），本身不是吞吐瓶颈；
- 但 **B 帧编码的单帧延迟被抬高超过 33ms（@30fps 实时预算）** → 编码器消费慢于捕获源生产 → lavfi 捕获源（gfxcapture/ddagrab）被背压 → WGC/DDA 忠实交付更少帧 → `inferredCaptureFps` 从一开始就掉；
- `-tune ll -rc-lookahead 0`（无 B 帧）是 pass-through 低延迟，单帧延迟远低于 33ms，故原本大部分时候能跟上。

**结论**：录制层（实时捕获）绝不能有 B 帧/lookahead，这是 33ms 实时预算的硬约束；B 帧/lookahead 只能留给离线转码层（批量编码不绑实时预算）。这一结论直接催生 v2 的「录制层无 B 帧 + 转码层有 B 帧」职责切分。

> 注：此实验在 v2 时期基线上做出，但因 `SKIP_TRANSCODE=true` 使录制层退化为单遍直出（等同 v1 行为），结论同样适用于 v1——v1 若加 B 帧必塌。git commit 中 v1 录制层从未带过 `-bf`，正因如此。

> 本质问题：v1 把「捕获+编码+交付」三件事压在一遍 ffmpeg 里，没有给"低延迟录制"和"高质量低码率交付"各自留出独立优化空间。

## 2. 阶段二：双 FFmpeg 三层架构（v2）

> 落地 commit：`5255422 feat: 录屏方案变更`（把单文件协调器拆成 recording/transcoding/upload 三层模块，引入转码层）。

### 2.1 架构

```
录制层 recording/   : gfxcapture/ddagrab → hwdownload→CPU scale→hwupload→h264_nvenc
                      产出"轻量原始切片" segNNN.ts（无B帧/无lookahead，低延迟护游戏）
转码层 transcoding/  : chokidar 监听原始切片 → 逐片 spawn ffmpeg
                      NVDEC解码 + h264_nvenc(p5/cq30/有B帧/lookahead) → segNNN_opt.ts（高质量低码率）
上传层 upload/       : 串行队列 + 令牌桶限速(3~7Mbps) → net.fetch → 后端 → COS
                      (自适应限速 throttle.ts：游戏留 30% 带宽余量)
```

三层各自独立进程/队列，通过文件系统（原始切片→转码切片）和事件解耦。

### 2.2 设计动机（为什么引入转码层）

来自开发记忆 2026-07-09 的用户硬约束（推翻了"D1 录制即成品/删转码层"方案）：

> 「三层架构必须保留——录制须无 B 帧/无 lookahead 轻量参数避免抢游戏 GPU，但导致 720p30 码率≈1080p60，浪费 CDN 且上传无法兼顾游戏带宽 → 转码层不可替代。」

即把职责切分：
- **录制层**：低延迟（无 B 帧）护游戏，产出高码率原始件；
- **转码层**：有 B 帧/lookahead 高质量低码率提质，产出交付件；
- **上传层**：令牌桶限速，不抢游戏带宽。

这是 v2 的理论最优解：录制实时性与交付画质/带宽各得其所。

### 2.3 实际痛点（v2 的三重崩溃）

理论很美，实测崩溃。开发记忆 2026-07-09 完整记录了排查过程：

#### 痛点 A：每 10s 转码脉冲 → 操作迟滞

- **现象**：用户报告每 ~10s 出现操作迟滞感；一旦某点开始卡，后续全程卡且不自愈。
- **根因**：转码层无条件开启（每 10s chokidar 触发 spawn 全新 ffmpeg，NVDEC+NVENC p5），与录制层 NVENC/磁盘争抢。终端实测 `dup=3212`/2:09（约 3870 帧）→ ~83% 帧为复制帧，每次 seg 转码脉冲 dup 突发增长。
- **单帧 33ms 时序瓶颈**：抓屏(GPU)→hwdownload(复制引擎)→CPU scale(最重)→hwupload(复制引擎)→NVENC(争抢时爆)→写盘。常态 5–10ms，转码脉冲使共享资源排队超 33ms → CFR dup。
- **NVENC session 误区**：消费级 N 卡通常 1 物理编码引擎，多 session 时分复用 → 录制+转码同刻编码互抢使每帧延迟翻倍超 33ms。
- **A/B 实测坐实**：`SKIP_TRANSCODE_IN_MODE_A=true` 跳过转码后，每 10s 迟滞感消失、游戏顺滑。→ 转码脉冲是主因。

#### 痛点 B：CFR dup 放大器 → 不自愈

- **现象**：录制层写死 `-vsync cfr -r 30`，跟不上实时时 dup 单调累加、永不回落 = "一旦卡顿全程不自愈"。
- **缓解**：改 VFR（`-fps_mode vfr`）后 `dup=0` 全程为 0，推翻"CFR dup 放大器"是 fps 塌陷主因的假设——dup 只是症状。

#### 痛点 C：capture fps 塌陷 → 复制引擎往返饿死 DWM（v2 最致命问题）

- **现象**：`inferredCaptureFps`（反推 ffmpeg 实收帧率）从 ~25 单调、平滑、渐近跌到 5~8 且不回升。隔离实验证明：与游戏负载、捕获方式（gfxcapture 窗口 / ddagrab 全屏）、登录状态、窗口丢失均无关——**唯一共同点是 CoWatch 共享的录制/编码管道**。
- **根因定性**（高可信）：每帧两次占 GPU 复制引擎（`hwdownload` GPU→CPU + `hwupload_cuda` CPU→GPU）饿死 OS 合成器(DWM)的 present/复制引擎 → WGC/DDA 忠实交付更少帧 → fps 单调塌到 5~8 渐近。
- **架构师设计（system_design.md §1.2）的解法**：砍 GPU↔CPU↔GPU 来回 → `hwmap`(D3D11→CUDA 一次性映射) + GPU 内 `format=nv12` 直送 `h264_nvenc`；降分辨率用 `scale_npp`。

#### 痛点 C 的解法全部被硬件死锁否决（T0 决定性发现）

真机实测（开发记忆 2026-07-09 T0）：

```
[Parsed_hwmap_1] Failed to created derived device context: -40.   (-40 = -ENOSYS)
ffmpeg 异常退出 code=4294967256（连崩 4 次放弃重启）
```

- `hwmap=derive_device=cuda` → **-40 (-ENOSYS)**：本机 FFmpeg 构建/驱动不支持从 D3D11 捕获设备派生 CUDA 设备。
- `scale_npp` → gyan.dev full build **不含该 filter**（`No such filter: 'scale_npp'`）。
- `scale_cuda` → 依赖同一 CUDA 派生，同死。
- **结论**：本机"D3D11 捕获帧 → CUDA 编码"整条零拷贝路被同一硬件限制彻底堵死，**唯一可用路径仍是 CPU 往返** `hwdownload → CPU → hwupload_cuda → h264_nvenc`。即 v2 在 FFmpeg 框架内无法根治复制引擎往返问题。

### 2.4 v2 的妥协态（E0 单遍模型）

因零拷贝路死锁，v2 退守 `system_design.md §1.4` 的 E0 单遍模型：
- 删录制期转码脉冲（`SKIP_TRANSCODE_IN_MODE_A=true`）→ 治 10s 迟滞；
- 录制即最终质量单遍 NVENC 编码 + 令牌桶直传；
- VFR + stop 时一次性 finalize 收口播放。

但 E0 有内在矛盾：录制层若加 B 帧/lookahead 则"从一开始就塌"（用户实测，开发记忆 22:21 段）；不加则码率高、与"低码率交付"冲突。复制引擎往返根因仍在。→ v2 在 FFmpeg 框架内已达上限，必须换技术栈。

## 3. 阶段三：window_capture.exe（v3，当前）

> 起点 commit：`3a59f9e chore: 初始化 feat/obs-wgc-capture`（携带 OBS WGC 分析与 Python sentinel 源码）。
> 设计依据：`docs/obs-wgc-capture-analysis.md`。

### 3.1 架构

```
window_capture.exe（独立 headless 进程，基于 vendored OBS）
  WGC 回调线程(COM STA): DWM合成新帧 → on_frame_arrived → CopySubresourceRegion 到 gs_texture
  OBS 渲染线程(固定33ms): video_tick → video_render → 读取 gs_texture → obs_nvenc_h264_tex(零拷贝)
  → 内嵌 AAC 音频 → ffmpeg_muxer HLS封装(seq%05d.ts + index.m3u8)
  → stdout JSON 协议(READY/STATS/ERROR/EXIT)
CoWatch 侧: spawn exe → chokidar 监听 HLS 切片 → upload 层限速直传后端
```

- **录制层 = exe**：CoWatch 不再 spawn ffmpeg，而是 spawn `window_capture.exe`（OBS WGC headless）。
- **转码层废弃**：exe 单遍产出最终质量 HLS，直传 upload，无转码阶段。
- **两层架构**：exe（录制+编码+封装）+ upload（限速上传）。

### 3.2 解决 v2 的三大痛点

| v2 痛点 | v3 解法 | 机制 |
|---------|---------|------|
| 复制引擎往返饿死 DWM | **零拷贝 NVENC** `obs_nvenc_h264_tex` | D3D11 纹理原地映射送 NVENC，不经 `hwdownload`/`hwupload`，不占复制引擎，DWM 不被饿死 |
| 捕获不稳定（gfxcapture 单线程同步阻塞） | **双线程解耦** | WGC 回调线程只 CopySubResourceRegion 到纹理；渲染线程按 33ms 节奏读纹理（无新帧则复用上一帧）。捕获和渲染解耦，渲染线程控稳定帧率 |
| 10s 转码脉冲迟滞 | **单遍最终质量，无转码层** | exe 一遍出最终 HLS，不再 spawn 第二个 ffmpeg；NVENC session 单一常驻，无争抢 |

### 3.3 关键技术约束（来自 window_capture C++ 源码与开发记忆）

- 编码器强制 `obs_nvenc_h264_tex`（零拷贝 D3D11→NVENC），**禁止静默降级到 ffmpeg_nvenc**（铁律③：dist 必须收 `obs-nvenc-test.exe`）。
- `obs_encoder_set_video(venc_, obs_get_video())` 必须显式调用（铁律①）。
- `obs_reset_video`/`obs_reset_audio` 必须先于 `obs_load_all_modules`（铁律②）。
- 停止 exe 须 `GenerateConsoleCtrlEvent(CTRL_C)`，不能 SIGKILL（否则丢尾段、无 `#EXT-X-ENDLIST`）。
- 录制层禁 B 帧/lookahead（实时 33ms 预算）；转码/screen 外部转码才用 B 帧+lookahead。
- 录制 CQ26 < 转码 CQ30（源质量 > 交付质量，避免世代损失）。

### 3.4 OBS WGC vs FFmpeg gfxcapture 的根本差异（obs-wgc-capture-analysis.md §1.2）

| 维度 | OBS WGC | FFmpeg gfxcapture |
|------|---------|-------------------|
| 架构 | 双线程解耦（回调线程 + 渲染线程） | 单线程同步（request_frame 阻塞等回调） |
| 帧获取 | 回调异步写纹理，渲染时读最新 | request_frame 同步等 WGC 递帧 |
| 无新帧时 | 渲染线程复用上一帧 | 阻塞等待或返回空 |
| 帧率稳定性 | 渲染线程控制，稳定 30/60fps | WGC 递帧节奏决定，不稳定 |
| GPU 上下文 | OBS 自有 D3D11 device + gs_texture | FFmpeg lavfi 内部 hwframe |

**这就是 OBS 稳定而 gfxcapture 不稳定的根本原因**，也是 v3 选择重写而非继续修补 FFmpeg 管道的决定性依据。

### 3.5 当前双模式（v3 过渡态）

CoWatch 当前仍保留双模式（见 `refactor-recording-upload-plan.md`）：
- **window 模式**（v3 主路径）：spawn window_capture.exe → upload，已废弃转码层。
- **screen 模式**（v2 残留）：spawn ffmpeg + transcoding + upload，因 exe 尚未支持全屏捕获而保留。

终态目标：exe 扩展支持 screen 模式（WGC 全屏捕获），彻底废弃转码层，统一到 exe + upload 两层架构。

## 4. 三阶段对比

| 维度 | v1 单FFmpeg | v2 双FFmpeg三层 | v3 window_capture.exe |
|------|------------|----------------|----------------------|
| 录制引擎 | ffmpeg (gfxcapture/ddagrab) | ffmpeg (同左) | OBS WGC (双线程解耦) |
| 编码 | h264_nvenc (经 hwdownload/hwupload 往返) | 同左 | obs_nvenc_h264_tex (零拷贝 D3D11→NVENC) |
| 转码 | 无 | 逐片 spawn ffmpeg (NVDEC+NVENC, 有B帧) | 无 (单遍最终质量) |
| 上传 | 直传 | 令牌桶限速串行队列 | 同 v2 (复用 upload 层) |
| 帧率稳定性 | gfxcapture 单线程同步，不稳 | 同左 (根因未除) | 双线程解耦，渲染线程控帧率，稳定 |
| 复制引擎占用 | 每帧2次往返 (饿死DWM) | 同左 | 0 (零拷贝) |
| 实时性 vs 画质 | 绑死 (无B帧高码率) | 解耦 (录制低延迟/转码提质) 但转码脉冲伤游戏 | 单遍兼得 (零拷贝让出GPU + 无转码争抢) |
| 主要痛点 | 码率高/单文件难维护 | 10s迟滞 + fps塌陷 + CUDA直编死锁 | (当前) exe 仅支持窗口模式；freeze 待查 |
| 代码结构 | 单文件 1344 行 | 三层模块 (recording/transcoding/upload) | exe + upload 两层 (转码层待废弃) |

## 6. 被否决的尝试（避免后人重复踩坑）

| 尝试 | 否决原因 | 证据 |
|------|---------|------|
| CUDA 直编 `hwmap=derive_device=cuda` | -40 (-ENOSYS)，本机不支持 D3D11→CUDA 派生 | memory 2026-07-09 T0；system_design.md §9.1 |
| `scale_npp` 降分辨率 | gyan.dev full build 不含该 filter | memory 2026-07-09 T0 复测 |
| `scale_cuda` | 依赖同一 CUDA 派生，同死 | 同上 |
