## 2. gfxcapture 捕获帧率不稳：完整排查链（本文重点）

### 2.1 现象（用户最初报告）

1. **有音频时 gfxcapture 明显卡顿**：日志显示 `realInputFps` 抽搐、`encFps` 稳定、`audio discontinuity`。
2. **画面质量异常**：录屏出现「时间对不上（t1 直接跳 t2，中间过程缺失）+ 部分帧闪回」。
3. 全屏录制（走 ddagrab 路径）无此问题 → 锁定为**窗口捕获源 gfxcapture 特有**。

### 2.2 各阶段归因与猜测（**含被推翻的结论，务必区分**）

下面按时间线列出所有重大猜测，每条标注**最终判定**。

| # | 阶段/来源 | 猜测内容 | 最终判定 |
|---|----------|---------|---------|
| A | 7.9.1 旧归因 | 卡顿主因是录制侧 `hwdownload` 的 GPU→CPU→GPU PCIe 往返 + **CPU `libswscale` scale 抢 CPU**，单帧 CPU 预算 29.5ms 逼近 33ms → 卡。解法是换 `scale_cuda` GPU scale。 | ❌ **已推翻**。实测 `speed≈1x`、`dup=0`、`drop=0`、编码 fps=收到 fps，编码侧全链路有裕量，CPU scale 非主因。 |
| B | 外部 AI（`temp/ai.md`） | `scale_cuda` 管线 29fps 稳定。 | ❌ **不可信**。与「gfxcapture 场景 `scale_cuda` 不可行（CUDA↔D3D11 context 冲突 + 拆 `-vf` 破坏帧节拍）」及终端实测双重矛盾，系合成源 `testsrc` 过度外推。其 `hwdownload` 不可去、VFR 是对症解药两点可采信。 |
| C | 架构师挑战（7.9，高见远） | 「录制须无 B 帧/lookahead 才能不拖游戏」大概率**错误**——NVENC 是 GPU 上与 3D 引擎物理分离的独立硬件块，B 帧只吃编码引擎时片。真凶更可能是 ① CPU scale ② 磁盘 I/O ③ 并发第二转码进程抢 NVENC。 | ⚠️ **部分成立**。用户实测**反证**了「可加 B 帧」：加 B 帧即从一开始就塌（单帧编码延迟>33ms 实时预算），故录制层禁 B 帧/lookahead 被**保留为正确**。但「并发第二转码进程抢 NVENC」这一点在后续被实证为**部分正确**（见 D）。 |
| D | 7.10.1 实证（GPU 监控） | 真因 = **转码层每 10s 的 NVENC 脉冲**（打满 NVENC）+ 游戏 GPU 瞬时高峰 + 录制管道**无恢复机制**（CFR 只能 dup 补帧、无法追平 → 一旦掉队永久锁死）。 | ✅ **已实证确立**。用户回滚代码后 GPU 监控三段实证：纯游戏不录~20%不卡；游戏中途才录（本底低有余量）每10s有脉冲但不卡；游戏刚启动直接录（GPU打满）+10s脉冲打满→从该点起全程卡。 |
| E | gfxcapture 断供假设 | `gfxcapture`(WGC) 经 DWM，游戏高负载/渲染停滞时**呈现率下降甚至断供** → 目标不再交付新帧 → dup 填空/画面冻结。 | ✅ **是切换 ddagrab 的直接动因**。但 7.10 实证指出「WGC/DWM 门控是**敏感度放大器而非唯一主因**」，且「从低起点塌到 5~8fps」更可能是 10s 脉冲反复撞击 backlog 后被 CFR 锁死的表现。 |
| F | OBS 对照 | OBS 直播不卡，差异在 ① OBS 无录制期每 10s 转码脉冲；② OBS Game Capture 挂钩游戏 swap-chain 读后缓冲**绕过 DWM**，比 WGC 更抗门控。 | ✅ 作为根解优先级参考：**先消除 10s 脉冲 + 加恢复机制；若仍不足再考虑 swap-chain 捕获架构重构**。 |

### 2.3 关键纠偏：两个独立问题被「卡顿」一词混在一起

排查中最大的认知坑是：**用户口语里的「卡顿」其实混了两个独立根因**，必须分治：

```
问题① 捕获源不稳（gfxcapture/WGC 断供）
   → 表现：dup 填空/画面冻结/帧闪回/时间跳变
   → 解法：换 ddagrab（DDA 稳定 30fps，不依赖目标窗口呈现率）
   → 与转码无关

问题② 转码脉冲撞 GPU 高峰（10s NVENC 脉冲 + 无恢复机制）
   → 表现：游戏高峰起全程卡、掉帧、操作迟滞
   → 解法：恢复 `-re` 平摊脉冲 / 或 R0/E0/E1 架构调整
   → 与捕获源无关
```

这两者**叠加**时症状最严重，且曾互相掩盖（早期把②误归因为①的 CPU scale，见猜测 A）。最终方案对两者分别处理：脉冲用 `-re` 平摊、捕获源换 ddagrab。

### 2.4 最终根因模型（为什么 ddagrab 能根治「断供」）

```
WGC/DDA 都经 DWM 合成器读取帧缓冲：
  gfxcapture(WGC)  ← 读取"目标窗口的 DWM 呈现"，游戏渲染停滞/高负载时呈现率↓甚至无新帧
                       → ffmpeg 源喂不饱 → dup 补同帧（dup=0 但内容卡）→ 冻结/闪回
  ddagrab(DDA)      ← 直接抓取整屏桌面，30fps 由 DDA 自身节奏保证，不依赖目标窗口是否在前台活跃呈现
                       → 稳定 30fps → 根治"断供冻结"
```

加 `crop=<W>:<H>:<X>:<Y>` 把「全屏抓取」裁成「目标窗口区域」，从而**用全屏捕获的稳定性模拟出窗口录屏**。坐标顺序贯穿一致：`x,y,w,h` → `crop=W:H:X:Y`，DPI 仅在哨兵侧换算、TS 透传零换算。

> 注意：WGC 不如 OBS swap-chain 捕获鲁棒，但在「消除脉冲 + 加恢复」后，现有 DDA 路径已被判定为可接受（swap-chain 重构留作下轮）。

### 2.5 关于 `fps=30` 强制使监控指标失明

源被钉 `fps=30` 后，WGC 交付稀时只是**重复同帧**（`dup=0` 但内容卡）。因此 `inferredCaptureFps` 这类「看 dup/帧率」的埋点指标**会误判为正常**，导致很长一段时间排查被误导。结论：**测真实捕获率必须去掉 `fps=30`**。旧版 gfxcapture 也带 `fps=30`，所谓「旧版更顺」可能是 mask 假象。

## 3. 用户拍板的行为模型（四种行为，由 SetWinEventHook 全可区分）

| 用户动作 | 哨兵事件 | 行为 | 续录方式 |
|---------|---------|------|---------|
| 窗口**移动**（位置变化） | `LOCATIONCHANGE`（前台可见，去抖确认） | **END**（干净结束，非续录） | — |
| 窗口**最小化** | `MINIMIZESTART` | **PAUSE** | 复用 `-hls_start_number` 续号 |
| **alt+tab / 切走** | `FOREGROUND`（hwnd≠目标） | **PAUSE** | 同上 |
| **遮挡 / Toast 重叠**（无前台变化） | 无事件 | **照常录制**（裁区内出现啥录啥） | — |
| **关闭 / 销毁** | `DESTROY` | **END** | — |
| 最小化恢复 / 切回 | `MINIMIZEEND` / `FOREGROUND==目标` | **RESUME** | 续号续录 |

> 多屏暂不考虋；段间隙由固定 Electron webview 播放器按 `EXT-X-DISCONTINUITY`/段列表跳放。

## 4. 三次重大 BugFix 的「为什么」（避免新 AI 回退）

### 4.1 BugFix-1：停止录制无法退出（孤儿 ffmpeg）
- **现象**：点结束录制后 UI 已切停止态，但 ffmpeg 仍在输出、转码器反复重转。
- **根因**：① 协调层 `stop()` 守卫 `if (!isRecording() && !isUserStopped) return` 依赖 `isRecording()`（=`ffmpegProcess!==null`）；当 `PAUSE` 与 `STOP` 几乎同时到达时 `pauseRecording` 已同步把 `ffmpegProcess` 置空 → `stop()` 直接 return，整段清理被跳过。② `stopRecording()` 仅通过 `ffmpegProcess` 杀进程，pause 置空后杀不到；且 pause 先杀 audio 使 ffmpeg stdin 关闭、`q` 失效。
- **修法**：引入始终指向真实进程的 `liveFfmpeg`；`stop()` 守卫改 `if (isUserStopped) return; if (!recordingLaunched && !sentinelActive) return;`（不依赖 `isRecording`）。

### 4.2 BugFix-2：哨兵误触发 + 续录闪回
- **现象**：最简场景（用户称无切后台）出现时间跳变 + 帧闪回。
- **根因**：`EVENT_SYSTEM_FOREGROUND` 是**系统级全局前台事件**，CoWatch 自身窗口 / 中文输入法候选框 / 通知 Toast 短暂抢前台即误判切走 → 误 `PAUSE` → 音频崩溃 → `RESUME` → ffmpeg 重启（`-start_number 8`）→ 时间轴断裂 + 切片边界闪回。
- **修法（方案 C，ROI 最高）**：
  - 哨兵 `FOREGROUND` 分支 **500ms 去抖** + `--ignore-pid`（覆盖 CoWatch 主进程 pid）+ IME/Toast/任务栏类名过滤 → **误暂停根本不发生**。
  - 录制层加 `-force_key_frames "expr:gte(t,n_forced*10)"` 让每 10s 切片起点都是 IDR，消除重启边界闪回。
  - `ffmpegProcess` 引用竞态修复 + 音频自发崩溃重连（不重启 ffmpeg）。
  - **否决了「暂停时冻结上一帧」方案**：技术上可行但需双输入 filtergraph + sendcmd/loop 切换，复杂度高风险高、且只掩症状不除根（符合用户「实现更麻烦就不改」）。

### 4.3 BugFix-3：UI 提示简化 + 通信收敛（隐藏陷阱）
- **用户诉求**：去掉【开始录制】按钮旁的提示（"窗口移动停止录制"等），简化通信，优先功能闭环。
- **隐藏陷阱（务必记住）**：协调层 `stop()` **本身不发任何 UI 状态事件**，UI 原本全靠 `recorder:autoStopped` 才知道「录制结束」。若把自动停止的 UI 通知彻底删光，UI 会**卡在「录制中」无法回到「开始录制」**。
- **修法**：保留底层 ddagrab+crop 暂停/自动停止功能，仅删横幅与冗余 IPC——把「暂停横幅 + 自动结束横幅（均带 reason）」两条通道**收敛为一条无声的 `recorder:stopped`（无 payload）**；暂停改为完全静默；自动停止时 UI 直接 `updateState('ready')`。

## 6. 给新 AI 的「不要踩的坑」速记

1. **不要恢复「录制期每 10s 转码 NVENC 脉冲」**——那是卡顿独立真因，已用 `-re` 平摊。
2. **不要删除 `recorder:stopped` 或改成不发事件**——`stop()` 不发 UI 事件，删了 UI 卡死。
3. **不要动 `liveFfmpeg` 真实引用**——它是 stop 能杀掉 in-flight pause 孤儿进程的关键。
4. **子代理若报「文件不存在/修复未应用」，先亲自 `ls`/Read 磁盘核实**——曾有误报建立在虚假前提上。
5. **B 帧/lookahead 只留离线转码层**，录制层实测加 B 帧即从一开始塌。
6. **CUDA 零拷贝直编在本机物理不可行**（`-40 ENOSYS`），勿投入此方向。
