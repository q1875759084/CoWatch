# 三层架构下录制问题记录

> 最后更新：2026-07-08
> 关联：`electron/handlers/recorder/`、`docs/recorder-encoding-reference.md`

## 架构概述

2026-07-07 提交 `5255422` 将录制链路拆为三层解耦架构：

```
录制层 (recording/)  → FFmpeg ddagrab/gfxcapture 捕获 → 写 raw .ts 切片到磁盘
转码层 (transcoding/) → chokidar 监听 → 逐片 FFmpeg 重编码压缩 → 写 _opt.ts
上传层 (upload/)      → 串行队列 → electron.net.fetch → COS
```

解耦前：录制 FFmpeg 单进程完成全部编码（30fps, CQ30, 无转码），切片直接上传。

## 问题 1：HLS Seek 失败（乱序请求 + 加载卡死）

### 现象

- 自然播放正常，所有切片按序加载，画面流畅
- 拖动进度条到未缓存位置 → hls.js 乱序请求切片 → 永远转圈
- 不同浏览器刷新 → 失效边界移动

### 根因

解耦前，录制 FFmpeg 单进程产出 98 个 segment，PTS 是同一条连续时间轴。解耦后每片独立 FFmpeg 进程转码，默认 PTS 都从 0 开始：

```
解耦前（单进程）：seg000 PTS 0-10s, seg001 PTS 10-20s, seg050 PTS 500-510s
解耦后（逐片转码，默认）：seg000 PTS 0-10s, seg001 PTS 0-10s, seg050 PTS 0-10s
```

hls.js seek 到 500s → 用累计 EXTINF 算得 seg050 → 但 seg050 的 PTS 是 0-10s，非预期的 500-510s → 时间轴冲突 → 乱序请求循环。

### 备选方案

| 方案 | 原理 | 改动量 |
|------|------|--------|
| A: `-copyts -vsync cfr` | 保留录制层 PTS 时间轴 + 输出 CFR 均匀帧间距 | 2 flag |
| B: `-output_ts_offset` + `-vsync cfr` | 按 seg 序号算绝对 PTS 偏移 + CFR | 5 行解析 + 2 flag |
| C: `#EXT-X-INDEPENDENT-SEGMENTS` | m3u8 声明每片独立可解码，hls.js 用 index 定位 | 后端 1 行标签 |
| D: `#EXT-X-DISCONTINUITY` 每片都加 | 告诉播放器每片之间编码参数变了 | 后端标签 |

### 选择：方案 B

理由：

| 维度 | A | B | C |
|------|---|---|---|
| 依赖录制层 PTS 质量 | 依赖 | 不依赖 | 不依赖 |
| B 帧 DTS 交互不确定性 | 有（bf=2 重排序） | 无（DTS 由编码器新生成） | 无 |
| hls.js 实现依赖 | 无 | 无 | 有 |
| 语义 | "继承录制时间轴" | "我给每片分配时间位置" | "每片独立，用 index 定位" |
| 行业对标 | 无 | AWS MediaConvert 分片转码 | YouTube/Twitch 直播归档 |

方案 B 是确定性最高的——数学计算，不依赖录制 PTS 质量，不涉及 `-copyts` 在 B 帧重排序下的未验证行为。改动在 `electron/handlers/recorder/transcoding/index.ts`：

```typescript
const segMatch = path.basename(inputPath).match(/^seg(\d+)/);
const segIndex = segMatch ? parseInt(segMatch[1], 10) : 0;
const tsOffset = segIndex * HLS_SEGMENT_DURATION; // 10s

'-output_ts_offset', String(tsOffset),
'-vsync', 'cfr',
```

### 行业技术选型对比

| 场景 | PTS 处理方式 | 代表 |
|------|------------|------|
| 整文件转码 → 切片 | 单进程自然连续 | CoWatch .bat 流程、绝大多数 VOD |
| 分布式/分片转码 | 按 chunk index 设 PTS offset | AWS Elemental MediaConvert、Bitmovin |
| 直播 → VOD 归档 | 每片独立 + INDEPENDENT-SEGMENTS | Twitch、YouTube Live |
| 客户端逐片上传 | 业界无完全一致的先例 | CoWatch 的特有架构 |

CoWatch 的架构（客户端 HLS 录制 → 逐片转码 → 逐片上传 → 服务端拼接 VOD）在业界没有完全相同的对标。最接近的是直播 CDN 边缘节点的分片转码流水线（用方案 B）。

### CoWatch 的特殊性

- **必须 HLS**：只有 HLS 能在录制过程中实时产出独立 segment，使三层解耦（边录边传）成为可能。如果改用 MP4 单文件，必须等录制结束后才能切片上传——回到旧方案的串行流程
- **必须逐片转码**：录制层用 CQ23 + bf0 + la0（低延迟保游戏不卡），转码层用 CQ30 + bf2 + la20（压缩率 ~50%）。录制和压缩解耦是架构设计的核心约束
- **不像直播平台**：直播平台 OBS 用 NVENC SDK 直调，帧全程留在 GPU 上（零拷贝），PTS 由应用层管理。CoWatch 走 FFmpeg 命令行，帧经过 `hwdownload`（GPU→CPU 往返），PTS 由 FFmpeg 管线管理，应用层无控制

## 问题 2：录制画面冻结 / 音画不同步

### 现象

- 录制 3:35 的视频，3:00~3:07 出现 6 秒画面冻结，之后音画不同步持续到 3:32
- FFmpeg 日志：连续 6 秒 `dup=N` 计数不变，`time` 不推进
- `[audio_capture] Warning: Audio data discontinuity detected`
- 恢复后 `dup` 暴增，每 100 帧 ~98 帧是复制的

### 根因

ddagrab 的 Desktop Duplication API 在 GPU 重负载时停摆。CoWatch 的帧管线每帧做一次 GPU→CPU→GPU 往返（`hwdownload`），60fps 下 ~156 MB/s PCIe 带宽。三重负载（游戏渲染 + ShadowPlay 即时回放 + CoWatch ddagrab）共同争抢 GPU 显示引擎和 PCIe 带宽，在激烈场景下 ddagrab 丢帧/停摆。

同时 `aresample=async=1:min_hard_comp=0.100` 的 100ms 补偿窗口远不够填 6 秒的音画 gap → 音画永久不同步。

### 为什么不影响 OBS / ShadowPlay

OBS 和 ShadowPlay 用 NVENC SDK 直调，帧**全程留在 GPU 上**（零 GPU↔CPU 拷贝）：
- OBS：DXGI 捕获 → GPU 表面 → NVENC 直接编码
- ShadowPlay：NVFBC 捕获 → NVENC 直接编码

CoWatch 走 FFmpeg 命令行：`ddagrab → hwdownload(GPU→CPU) → scale/format(CPU) → h264_nvenc(CPU→GPU)`，多了一次往返。

### 为什么解耦前 30fps 没这问题

30fps 下 `hwdownload` 带宽减半（~78 MB/s），CPU 格式转换量减半，ddagrab 请求 GPU 显示引擎的频率减半。在 3060/4060 等单 NVENC 芯片的消费级 GPU 上，30fps 三项负载没跨过临界线。

### 备选方案

| 方案 | 改动量 | 效果 |
|------|--------|------|
| 录制降回 30fps | 3 行参数 | ddagrab 负载减半，高负载场景不再瓶颈 |
| GPU 端滤镜（`hwupload_cuda → scale_cuda`） | 录制管线重写 | 消除 `hwdownload`，帧全程留在 GPU |
| NVENC SDK 直调 | 4-6 周开发 | OBS 级别性能，零 GPU↔CPU 拷贝 |
| 60fps 作为 pro 选项，默认 30fps | 参数 + UI | 用户按需选择 |

### 行业对比

| 产品 | 帧管线 | 60fps 性能 |
|------|--------|-----------|
| OBS | NVENC SDK 直调，零拷贝 | 1080p60 流畅（高端 GPU） |
| ShadowPlay | NVFBC + NVENC SDK | 原生性能，几乎无开销 |
| Medal.tv / Outplayed | GPU 厂商 SDK | 游戏内覆盖，低开销 |
| CoWatch | FFmpeg CLI + hwdownload | 依赖 GPU 型号和游戏负载 |

## 问题 3：upload 层 Token 过期

### 现象

- 录制 >1h 后切片上传全部 401
- 补传（resume）不受影响

### 根因

upload 层用 `electron.net.fetch`（非 axios），不在渲染进程 401 拦截器管辖范围。刷新后的 token 不同步到 upload 层 config。

### 修复

已在 `todo-token.md` 中记录并修复。改动：`upload/index.ts` 新增 `updateAuthToken()` 函数，`index.ts` 的 `setAuthTokenForRecorder()` 同步调用。

## 问题 4：window-watch 误判窗口消失

### 现象

- 全屏录制时，游戏窗口未关闭但 window-watch 触发"目标窗口消失"
- `desktopCapturer.getSources({types:['window']})` 在全屏/最小化时不会列出窗口

### 根因

window-watch 通过 `desktopCapturer.getSources({types: ['window']})` 枚举当前窗口列表。游戏在全屏独占模式下，窗口可能不在枚举结果中。连续 3 次（15s）检测不到 → 判定消失 → 触发优雅停止。

### 影响

`isWindowAlive` 用作 ffmpeg crash 时的快速判断：窗口消失 → crash 属预期，跳过重启直接 stop。全屏录制在 crash 重启时可能因误判而放弃重启。

```
-output_ts_offset {segIndex * 10} -vsync cfr

```
