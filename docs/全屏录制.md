# Windows 全屏录制兼容性分析

> 状态：调研备份，未实施。后续迭代时参考。

## 问题背景

用户操作流程：打开 CoWatch 桌面端 → 打开游戏 → WindowPicker 选择游戏窗口 → 开始录制 → 切换到游戏 → 全屏化。

当前架构中，Electron 的 `desktopCapturer`（源列表）和 ffmpeg `gdigrab`（实际录制）使用**完全不同的捕获管道**：

| 组件 | Windows 底层 API | 能力 |
|------|-----------------|------|
| `desktopCapturer`（源列表 + 缩略图） | Windows Graphics Capture API | 能看到独占全屏窗口 |
| ffmpeg `gdigrab`（实际录制） | GDI / BitBlt（依赖 DWM 合成） | **看不到独占全屏窗口** |

这导致 WindowPicker 里显示了游戏窗口的缩略图，但 ffmpeg 开始录制后可能黑屏。

---

## Windows 全屏的三种模式

| 模式 | 原理 | gdigrab 能否捕获 | 典型场景 |
|------|------|:---:|------|
| **独占全屏（Exclusive Fullscreen）** | GPU 直接输出到显示器，绕过 DWM | ❌ 黑屏 | 老游戏、部分竞技游戏 |
| **无边框窗口全屏（Borderless Windowed）** | 仍是窗口，DWM 合成，无边框覆盖全屏 | ✅ | 大多数现代游戏默认 |
| **全屏优化（FSE Optimized）** | 独占全屏但 DWM 仍参与合成 | ⚠️ 部分能捕获 | Win10+ 游戏默认 |

### 独占全屏 → 必黑屏

```
用户全屏化 → 游戏接管 GPU → DWM 被绕过
→ gdigrab 调用 BitBlt → DWM 没有该窗口的合成内容 → 返回黑屏
→ ffmpeg 不崩溃，继续"录制"黑帧 → 用户毫不知情
```

GDI/BitBlt 是 DWM 之上的 API，独占全屏绕过了 DWM，GDI 就看不到任何内容。OBS 早期版本也有同样的问题。

### 无边框窗口全屏 → 通常可以，但有坑

**坑 1：窗口标题变化**

部分游戏在全屏切换时**销毁旧窗口、创建新窗口**，新窗口标题可能不同。此时 `gdigrab -i title=旧标题` 找不到窗口 → ffmpeg 报错退出 → 触发 crash 重启 → 重启后仍找不到 → 连续 3 次 crash 后放弃录制。

**坑 2：HDR 显示**

Windows 11 HDR 模式下，无边框窗口的游戏画面可能使用 HDR 色彩空间（10-bit / BT.2020），gdigrab 的 BitBlt 只能获取 SDR 内容，结果要么颜色错误（偏紫/偏绿），要么直接黑屏。

### 全屏优化（FSE）→ 不稳定

Windows 10 引入的"全屏优化"实质是：游戏以为自己在独占全屏，但 DWM 仍在后台合成。BitBlt **有时**能捕获到内容，取决于：

- 游戏是否使用了 DXGI Flip Model
- GPU 驱动版本
- Windows 版本

行为不可预测，有时能录有时不能，是最糟糕的情况——用户无法确定录制是否成功。

## 当前代码的已知问题

### 问题一：gdigrab 只能录窗口，无法录整屏

`recorder.ts` 中 Windows 分支硬编码为 `gdigrab` + `title=`：

```ts
// Windows：gdigrab 按窗口标题捕获
inputArgs = [
  '-f', 'gdigrab',
  '-framerate', '30',
  '-i', `title=${safeTitle}`,
];
```

但 WindowPicker 允许用户选择 `screen` 类型的录制源。当用户选择"整屏"时，`source.name` 类似 "Entire Screen"，ffmpeg 执行 `gdigrab -i title=Entire Screen` → 找不到该窗口标题 → ffmpeg 启动失败。

### 问题二：窗口标题匹配不稳定

1. **标题动态变化**：很多游戏窗口标题会变化（如 "League of Legends (TM) Client" → "League of Legends"），录制期间标题变了，ffmpeg 不会自动跟随
2. **标题重复**：多个同名窗口时 `gdigrab` 会匹配到第一个
3. **特殊字符**：`safeTitle` 只转义了双引号，但 gdigrab 对 `&`、`|`、`<`、`>` 等字符的处理可能有隐患
4. **中文标题**：部分中文游戏标题在 gdigrab 匹配时存在编码问题

### 问题三：HLS 路径反斜杠

```ts
const segPattern = path.join(tmpDir, 'seg%03d.ts');
```

Windows 上 `path.join` 生成 `C:\Users\...\seg%03d.ts`（反斜杠）。某些 ffmpeg 版本在 HLS muxer 中对反斜杠的处理不一致，可能将 `\s`、`\U` 等误解析为转义序列。更安全的做法：

```ts
const segPattern = path.join(tmpDir, 'seg%03d.ts').replace(/\\/g, '/');
```

ffmpeg 在所有平台上都能正确处理正斜杠路径。

### 问题四：Windows 权限提示缺失

WindowPicker 的空状态提示缺少 Windows 屏幕录制权限说明，需补充：

Windows 上同样存在权限问题：
- Windows 10 2004+：系统有"屏幕录制"隐私设置，某些组策略环境下可能被禁用
- Windows 11 22H2+：更严格的隐私控制，`desktopCapturer` 可能返回空列表或黑屏缩略图
- UAC 提升的窗口：以管理员权限运行的窗口无法被非管理员进程的 `desktopCapturer` 捕获

## 修复方案

### 方案 A：gdigrab desktop + crop（最小改动，部分修复）

```ts
// Windows 分支改为：
if (sourceId.startsWith('screen:')) {
  inputArgs = ['-f', 'gdigrab', '-framerate', '30', '-i', 'desktop'];
} else {
  // 窗口录制：也用 desktop + crop，避免标题匹配问题
  inputArgs = ['-f', 'gdigrab', '-framerate', '30',
               '-offset_x', '0', '-offset_y', '0',
               '-video_size', '1920x1080', '-i', 'desktop'];
}
```

| 维度 | 评估 |
|------|------|
| 独占全屏 | ❌ 仍然黑屏（desktop 模式也走 BitBlt） |
| 无边框全屏 | ✅ 能捕获，且无标题匹配问题 |
| 标题变化 | ✅ 不依赖标题 |
| 副作用 | 录到整个桌面（任务栏、其他窗口），需要 crop |

**结论：解决了标题匹配问题，但独占全屏仍然无解。**

---

### 方案 B：检测独占全屏 + 提示用户使用无边框模式（UX 修复，不改捕获）

在 `handleConfirmSource` 时，通过 `sourceId` 判断用户选的是窗口还是整屏，如果是窗口且是游戏进程，弹窗提示：

> "检测到您选择了游戏窗口。如果游戏使用独占全屏模式，录制画面可能为黑屏。建议在游戏设置中将显示模式改为「无边框窗口」或「窗口化全屏」。"

| 维度 | 评估 |
|------|------|
| 独占全屏 | 不修复，但用户知情 |
| 实现成本 | 极低 |
| 用户体验 | 比"录了 30 分钟黑屏"好得多 |

OBS 也是这么做的——OBS 在 Windows 上默认使用 DXGI Desktop Duplication，但遇到独占全屏也会提示用户切换无边框。

### 方案 C：架构升级——用 Electron desktopCapturer 做捕获，ffmpeg 只做编码（根本修复）

```
当前架构：
  ffmpeg gdigrab → 同时捕获 + 编码

新架构：
  Electron desktopCapturer.getSources()
  → navigator.mediaDevices.getUserMedia({chromeMediaSource: 'desktop'})
  → MediaStream → 编码 → HLS 切片上传
```

**为什么这能解决独占全屏问题**：Electron 的 `desktopCapturer` 在 Windows 10+ 底层使用 **Windows Graphics Capture API**（不是 GDI），这个 API：
- ✅ 能捕获独占全屏内容
- ✅ 能捕获 HDR 内容
- ✅ 不依赖窗口标题

| 维度 | 评估 |
|------|------|
| 独占全屏 | ✅ 根本解决 |
| 无边框全屏 | ✅ |
| HDR | ✅ |
| 实现成本 | 🔴 高——需要重构整条录制管道 |

#### 方案 C-1：纯渲染进程方案（最简单）

```
renderer: getUserMedia({chromeMediaSource: 'desktop', chromeMediaSourceId: sourceId})
→ MediaRecorder (WebM/VP8)
→ 上传 WebM 到后端
```

- 缺点：WebM/VP8 质量不如 H.264；无法做 HLS 切片；后端需要支持 WebM

#### 方案 C-2：渲染进程捕获 + 主进程编码

```
renderer: getUserMedia → <video> → requestAnimationFrame → sendFrame via IPC
main: receive raw frames → pipe to ffmpeg stdin → HLS encode + upload
```

- 缺点：IPC 传输 raw frames 带宽巨大（1920×1080×4 bytes × 30fps ≈ 250MB/s），需要共享内存或 Native Addon

#### 方案 C-3：Native Addon 方案（OBS 级别）

```
C++ native addon: DXGI Desktop Duplication → 直接拿到 GPU 纹理
→ 传给 ffmpeg NVENC/QSV 硬编（零拷贝 GPU→GPU）
→ HLS 切片上传
```

- 缺点：开发成本极高，需要 C++ / N-API / DXGI 知识

---

### 方案 D：混合方案（推荐，平衡成本和效果）

#### 短期（方案 A + B）

1. `gdigrab desktop` 替代 `title=`（修复标题匹配 + 整屏录制）
2. 检测游戏进程 + 弹窗提示无边框模式（用户知情）
3. WindowPicker 里黑屏缩略图显示"独占全屏模式，录制可能为黑屏"

#### 中期（方案 C-1）

1. 渲染进程用 `getUserMedia` + `MediaRecorder` 录制
2. 作为"兼容模式"：当检测到 gdigrab 返回黑帧时自动切换
3. 输出 WebM 格式，后端增加 WebM→HLS 转码

#### 长期（方案 C-3）

1. 如果用户量增长到需要专业录制，做 Native Addon
2. DXGI Desktop Duplication + GPU 零拷贝硬编

## 额外注意事项

### ffmpeg-static 在 Windows 上的路径

`getFfmpegPath` 处理了 `app.asar` → `app.asar.unpacked` 的替换，Windows 上 `ffmpeg-static` 的二进制文件名应为 `ffmpeg.exe`。`ffmpeg-static` 包已处理平台差异，大概率没问题，但需在 Windows 上实测确认。

### stdin 'q' 退出时序

Windows 上用 `ffmpegProcess.stdin?.write('q')` 优雅退出 ffmpeg 是正确的（SIGTERM 在 Windows 上等于 SIGKILL）。边界情况：如果 ffmpeg 的 stdin buffer 已满，`write('q')` 可能阻塞。更安全的做法是 `write('q\n')`（加换行符确保 ffmpeg 接收到完整命令），或 `end()` 在 `write` 回调中调用。
