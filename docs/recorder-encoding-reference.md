# CoWatch 录屏编码参数演变与优化参考

> 最后更新：2026-07-06
> 文件：`electron/handlers/recorder/index.ts`
> 本文档记录录屏编码参数的演变过程、当前问题、以及后续可选优化方向。

---

## 一、时间线

### Phase 1 — 初始版本（900p + CQ28，无低延迟优化）

**参数：**
- 分辨率：900p（maxWidth 1600）
- NVENC：`-rc vbr -cq 28 -b:v 0 -maxrate 5000k -bufsize 10000k`
- 无低延迟调优：无 `-tune ll`、无 `-bf 0`、无 `-rc-lookahead 0`
- FFmpeg 版本：8.1

**实测结果：**

| 用户 | 编码器 | 分辨率 | 卡顿 | 画质 | 码率 |
|------|--------|--------|------|------|------|
| A（有 NVIDIA GPU） | h264_nvenc 硬编 | 900p | **明显卡顿**（全屏/窗口均卡） | 良好 | ~10 Mbps |
| B（无 NVIDIA GPU） | libx264 软编 | 480p（maxWidth 854） | 无卡顿 | **不可接受** | 低 |

**问题：**
1. 硬编 900p CQ28 无低延迟优化 → 编码器默认使用 B 帧 + lookahead → 编码延迟 3-4 帧 → 画面卡顿
2. 软编 480p 分辨率太低，画质不可接受
3. maxrate 5000k + bufsize 10000k 在 CQ 模式下被 FFmpeg 强制清零（后文详述），实际无约束

---

### Phase 2 — 卡顿优化 + FFmpeg 版本调整

**改动项：**

| 改动 | 详情 | 原因 |
|------|------|------|
| 分辨率 900p → 720p | maxWidth 1600 → 1280 | 降低编码负担，减少像素量 36% |
| CQ 28 → 30 | NVENC `-cq 30`；软编 `-crf 30` | 720p 下 CQ30 视觉可接受 |
| NVENC 低延迟参数 | `-preset p4 -tune ll -rc-lookahead 0` | 编码延迟从 3-4 帧降到 0-1 帧 |
| 全局禁用 B 帧 | `-bf 0`（所有平台） | B 帧增加延迟 + DTS 不单调风险 |
| FFmpeg 版本 8.1 → 7.1 | 支持旧 NVIDIA 驱动（如 driver 581） | nv-codec-headers 12.2 → min driver R535 |
| FFmpeg 版本 7.1 → 回退 8.1 | gyan.dev FFmpeg 7.1 不支持 gfxcapture | gfxcapture 是打包时决定的确定性条件，不支持说明版本选错 |
| 删除 gfxcapture 检测 | 移除 `detectGfxcaptureSupport()` + gdigrab 回退 | FFmpeg 是本地打包依赖，支持与否在打包时已确定；不支持应在测试阶段暴露而非运行时回退掩盖 |

> ⚠️ **纠正：** gfxcapture 在 7.1 上不支持是在测试阶段发现的，测试后即回退到 8.1。
> **从未在生产环境使用 gdigrab 回退路径。** gfxcapture "崩溃导致 gdigrab" 的场景不存在。

**当前参数：**

```typescript
// NVENC（当前生效参数）
encodeArgs = ['-c:v', 'h264_nvenc', '-rc', 'vbr', '-cq', '30', '-b:v', '0',
              '-preset', 'p4', '-tune', 'll', '-rc-lookahead', '0',
              '-maxrate', '5000k', '-bufsize', '10000k'];

// 全平台
platformVfArgs = ['-bf', '0'];  // 全平台通用

// 分辨率
maxWidth = 1280  // 硬编
maxWidth = 854   // 软编

// HLS
HLS_SEGMENT_DURATION = 10  // 10 秒切片
GOP = 30 * 10 = 300        // 每 300 帒一个 I 帧
```

**实测结果：**

| 用户 | 编码器 | 分辨率 | 游戏卡顿 | 录制回放 | 画质 | 码率 |
|------|--------|--------|----------|----------|------|------|
| A（有 NVIDIA GPU） | h264_nvenc 硬编 | 720p | **无卡顿** ✅ | **严重卡顿** ❌ | 可接受（低于 Phase 1） | ~10 Mbps |
| B（无 NVIDIA GPU） | libx264 软编 | 480p | 无卡顿 | — | 不可接受 | 低 |

**Phase 2 引入的新问题：录制视频严重卡顿**

低延迟参数（`-rc-lookahead 0 -tune ll`）移除了编码器的 32 帧缓冲，解决了游戏卡顿，但暴露了一个一直被缓冲掩盖的问题：

- **ddagrab/gfxcapture 捕获产生 VFR（可变帧率）**：帧间隔不规则（16ms/50ms/33ms 混合），由 Desktop Duplication API 的捕获节奏决定
- **Phase 1 时**：lookahead 32 帧缓冲充当了帧率平滑器，将不规则 PTS 归一化为均匀输出 → 录制流畅
- **Phase 2 时**：缓冲被移除，不规则 PTS 直通到 HLS 输出 → 播放卡顿
- **Windows 受影响**：Windows 一直漏了 `fps=30` 滤镜做 CFR 归一化，移除缓冲后暴露 VFR 卡顿

**修复：** 在 Windows lavfi 滤镜链末尾添加 `fps=30` 滤镜（CFR 归一化）。

```typescript
// 修复前（Windows）
winScaleFilter = `scale=w='min(iw,1280)':h=-2,format=yuv420p`;

// 修复后（Windows）
winScaleFilter = `scale=w='min(iw,1280)':h=-2,format=yuv420p,fps=30`;
```

`fps=30` 滤镜通过丢帧/补帧将 VFR 输入归一化为恒定 30fps 输出，PTS 均匀 33ms，录制回放流畅。

---

### Phase 3 — VFR 修复（添加 fps=30 帧率归一化）

**改动项：**

| 改动 | 详情 | 原因 |
|------|------|------|
| Windows lavfi 链添加 `fps=30` | `winScaleFilter` 末尾追加 `,fps=30` | ddagrab/gfxcapture 产生 VFR，无 lookahead 缓冲后 PTS 不规则直通导致录制卡顿 |

**当前参数（Phase 3 修复后）：**

```typescript
// NVENC
encodeArgs = ['-c:v', 'h264_nvenc', '-rc', 'vbr', '-cq', '30', '-b:v', '0',
              '-preset', 'p4', '-tune', 'll', '-rc-lookahead', '0',
              '-maxrate', '5000k', '-bufsize', '10000k'];

// Windows lavfi 滤镜链（ddagrab/gfxcapture 共用）
winScaleFilter = `scale=w='min(iw,1280)':h=-2,format=yuv420p,fps=30`;

// 全平台
platformVfArgs = ['-bf', '0'];  // 全平台通用

// 分辨率
maxWidth = 1280  // 硬编
maxWidth = 854   // 软编

// HLS
HLS_SEGMENT_DURATION = 10  // 10 秒切片
GOP = 30 * 10 = 300        // 每 300 帧一个 I 帧
```

**待验证：** 修复后录制回放是否流畅，同时游戏保持无卡顿。

## 二、问题根因分析

### 2.1 码率未降的原因

| 改动 | 码率影响 | 方向 |
|------|----------|------|
| 900p → 720p（像素减少 ~36%） | -36% | 降码率 |
| CQ 28 → 30 | -15~20% | 降码率 |
| `-bf 0`（全 P 帧，无 B 帧压缩） | +30~40% | 升码率 |
| `-tune ll`（低延迟缓冲策略） | +5~10% | 升码率 |
| `-rc-lookahead 0`（无前瞻码率分配） | +10~15% | 升码率 |
| **合计** | ≈ **0%** | 码率不变 |

**结论：** 缩减的 ~50% 和新增的 ~50% 大致抵消。低延迟参数的码率膨胀效应等于分辨率+质量参数的压缩收益。

### 2.2 maxrate 未生效的原因

FFmpeg `nvenc.c` 源码中 CQ 模式的处理逻辑：

```c
// CQ mode shall discard avg bitrate/vbv buffer size and honor only max bitrate
ctx->encode_config.rcParams.averageBitRate = avctx->bit_rate = 0;
ctx->encode_config.rcParams.vbvBufferSize  = avctx->rc_buffer_size = 0;
ctx->encode_config.rcParams.maxBitRate     = avctx->rc_max_rate;
```

当使用 `-cq 30` 时，FFmpeg **强制将 `averageBitRate` 和 `vbvBufferSize` 清零**。

VBV（Video Buffering Verifier）码率约束模型**必须同时有 `maxBitRate` + `vbvBufferSize` 才能工作**：
- maxBitRate = 进水管最大流速
- vbvBufferSize = 水桶容量
- bufsize = 0 → 无桶 → 无法量水 → maxrate 变成纯装饰值

| 参数 | 用户写的 | FFmpeg 实际传给 NVENC 的 |
|------|----------|--------------------------|
| averageBitRate | 0（`-b:v 0`） | 0（CQ 强制清零） |
| maxBitRate | 5000000（`-maxrate 5000k`） | 5000000 ✅ |
| vbvBufferSize | 10000000（`-bufsize 10000k`） | **0**（CQ 强制清零）❌ |

**结果：** `vbvBufferSize = 0` → VBV 模型不存在 → maxrate 无约束 → 编码器自由飙码率 → 实际 ~10 Mbps 远超 5 Mbps。

### 2.3 低延迟编码效率 vs 全优化编码效率

**同样 6 Mbps 码率，不同编码条件的视觉质量差异：**

| 编码条件 | 720p 每比特的有效视觉信息 | 等效视觉质量码率 |
|----------|--------------------------|------------------|
| 全优化（B 帧 + lookahead + 多 pass） | 高 | 6 Mbps ≈ 6 Mbps |
| 低延迟（`-bf 0` + `-tune ll` + `-rc-lookahead 0`） | 低（40-50% 损耗） | 6 Mbps ≈ 3 Mbps 全优化 |

**当前 10 Mbps 低延迟编码的视觉质量 ≈ 全优化编码下 5-6 Mbps。** 并非"浪费级画质"。

## 三、当前参数完整清单

### 3.1 NVENC（h264_nvenc）

```
-c:v h264_nvenc
-rc vbr                    # VBR 模式（承载 CQ 参数）
-cq 30                     # 恒定质量等级 30
-b:v 0                     # 平均码率不限（CQ 模式下 FFmpeg 强制清零）
-preset p4                 # 速度/质量甜点
-tune ll                   # 低延迟调优（核心防卡顿参数）
-rc-lookahead 0            # 禁用前瞻分析（核心防卡顿参数）
-bf 0                      # 禁用 B 帧（全局，所有平台）
-maxrate 5000k             # 峰值码率上限（CQ 模式下因 bufsize=0 未生效）
-bufsize 10000k            # VBV 缓冲区大小（CQ 模式下被 FFmpeg 强制清零，无效）
-g 300                     # GOP 大小（30fps × 10s）
```

### 3.2 视频捕获

| 平台 | 全屏录制 | 窗口录制 |
|------|----------|----------|
| Windows | ddagrab（DXGI Desktop Duplication） | gfxcapture（WGC API，GPU 零拷贝） |

缩放策略：`scale=w='min(iw,1280)':h=-2`（等比缩放，最大宽 1280）

### 3.3 QSV（h264_qsv）

```
-c:v h264_qsv -global_quality 30 -look_ahead 1 -b:v 0 -maxrate 5000k -bufsize 10000k
```

### 3.4 AMF（h264_amf）

```
-c:v h264_amf -quality quality -b:v 0 -maxrate 5000k -bufsize 10000k
```

### 3.5 软编（libx264）

```
-c:v libx264 -crf 30 -preset veryfast
maxWidth = 854  // ~480p
```

### 3.6 音频

```
-c:a aac -b:a 128k -strict -2
-f s16le -ar 48000 -ac 2  // audio_capture WASAPI Loopback
-af aresample=async=1:min_hard_comp=0.100:first_pts=0  // 音画同步校正
```

### 3.7 HLS 输出

```
-f hls
-hls_time 10              // 10 秒切片
-hls_list_size 0          // 保留全部切片
-g 300                    // GOP = 30fps × 10s
```

## 四、后续优化方向

### 方案 A — 录制后离线重编码（最推荐）

**核心思路：录制参数和回放参数是两个独立问题。**

```
录制阶段：CQ30 + -bf 0 + -tune ll + -rc-lookahead 0（保无卡顿）
    ↓ 录制结束后
重编码阶段：VBR + B 帧 + lookahead + 高 preset（保体积 + 保画质）
    ↓
上传 COS → 回放（从压缩版播放）
```

**重编码参数示例：**

```
ffmpeg -i original.ts -c:v h264_nvenc -rc vbr -cq 30 -preset p7
       -bf 2 -rc-lookahead 20 -maxrate 6000k -bufsize 12000k
       -c:a copy -f hls -hls_time 10 ...
```

| | 录制原始（低延迟） | 重编码后（全优化） |
|---|---|---|
| 码率 | ~10 Mbps | ~5 Mbps |
| 11min 文件 | ~900 MB | ~420 MB |
| CDN 成本 | 当前水平 | 降 ~55% |
| 画质 | 720p CQ30 低延迟 | 720p CQ30 全优化（**视觉更好**） |
| 重编码耗时 | — | 11min 视频 ≈ 1-2 min（NVENC p7 远超实时） |

**注意事项：**
- 重编码不降画质，而是用更高效算法表达同样视觉质量
- 需新增 `stop()` 回调后的重编码流程
- 原始 ts 可先上传 COS（保证即时可用），重编码完成后替换
- 架构改动量：中等（新增重编码流程 + COS 替换逻辑）

---

### 方案 B — 渐进恢复 B 帧 + 小窗口 lookahead（零架构改动）

**尝试参数：**

```
-bf 1            // 1 个 B 帧（最小引入，延迟增加 <1 帧）
-rc-lookahead 8  // 8 帧前瞻（30fps = 267ms，不影响感知延迟）
```

保留 `-tune ll` 和 `-preset p4`。

**预估收益：** 码率从 ~10 Mbps 降到 ~8 Mbps（恢复 ~20% 编码效率）。

**风险：** 需在 4060 上实测是否重新卡顿。

> **之前卡顿的根因可能不是 B 帧/lookahead 本身**，
> 而是 Phase 1 时编码参数整体未优化（默认 B 帧数量、默认 lookahead 窗口过大）。
> `-bf 1` + `-rc-lookahead 8` 是极保守的参数，与 Phase 1 的默认值差异很大。
> gfxcapture 现已正常工作（GPU 零拷贝捕获），编码负担比 Phase 1 更轻。

**实测优先级高：** 如果不卡顿，这是最省成本的改动——零架构改动，参数微调即可。

---

### 方案 C — 恢复 900p（画质优先，码率略升）

既然低延迟模式下码率 ~10 Mbps 和 Phase 1 的 900p 相当，
降分辨率省下的码率被低延迟参数吃掉了——不如恢复 900p。

```
maxWidth = 1600   // 900p
-cq 30             // CQ30（比 Phase 1 的 CQ28 略低，但分辨率更高补偿了质量）
```

| | 720p CQ30 | 900p CQ30 |
|---|---|---|
| 码率 | ~10 Mbps | ~14 Mbps |
| 11min 文件 | ~900 MB | ~1150 MB |
| CDN 成本 | 当前 | +28% |
| 画质 | 低延迟编码下的 720p | 低延迟编码下的 900p（**明显更清晰**） |

28% 成本增量换来显著画质提升。CDN 成本 0.4 元/人/日 → 增至 ~0.5 元/人/日。

### 方案 D — HEVC/H.265（编码效率 +40%，但兼容性受限）

```
-c:v hevc_nvenc -rc vbr -cq 30 -b:v 0 -preset p4 -tune ll -bf 0
```

| 浏览器 | HLS + H.264 | HLS + HEVC |
|--------|-------------|-------------|
| Safari | ✅ | ✅ |
| Chrome | ✅ | ❌ |
| Firefox | ✅ | ❌ |
| Edge | ✅ | ✅（需 HEVC 扩展） |
| Electron | ✅ | ✅ |

**仅适用于纯 Electron 桌面端场景。有 Web 端回放需求时不可行。**

### 方案 E — Constrained VBR（从 CQ 切换到受约束 VBR）

放弃 CQ 模式（因为 FFmpeg CQ 清零 bufsize 导致 maxrate 无效），切换到受限 VBR：

```
-c:v h264_nvenc -rc vbr -b:v 6000k -maxrate 8000k -bufsize 12000k
-preset p4 -tune ll -rc-lookahead 0 -bf 0
```

**删掉 `-cq 30`**（否则 FFmpeg 又清零 averageBitRate 和 vbvBufferSize）。

VBV 约束生效：`bufsize/maxrate = 12Mbit/8Mbps ≈ 1.5s` 缓冲窗口。

| | CQ30（当前） | VBR 6Mbps | VBR 8Mbps |
|---|---|---|---|
| 码率 | ~10 Mbps（不受控） | ~6 Mbps（受约束） | ~8 Mbps（受约束） |
| 11min 文件 | ~900 MB | ~450 MB | ~600 MB |
| maxrate 生效 | ❌ | ✅ | ✅ |
| 静态场景码率 | ~1-2 Mbps | ~2-3 Mbps | ~3-4 Mbps |
| 复杂场景码率 | 不封顶 | ≤8 Mbps | ≤10 Mbps |

**注意：** VBR 下 QP 在帧间波动（静态帧 QP 更高、复杂帧 QP 更低）。
低延迟模式下 VBR 6 Mbps ≈ 全优化 3 Mbps 视觉质量，720p 游戏场景下操作清晰、特效轻微损失。
如需接近当前画质，建议 `-b:v 8000k`。

## 六、关键概念速览

### I/P/B 帧

- **I 帧（关键帧）**：完全自包含，不参考其他帧，体积最大（≈10× P 帧），GOP 起点
- **P 帧（预测帧）**：参考前面的 I/P 帧，只编码差异，体积中等
- **B 帧（双向预测帧）**：同时参考前后 I/P 帧，体积最小（≈P 帧的 1/3）
- **`-bf 0` 的代价**：去掉 B 帧后所有 inter-frame 变成 P 帧，码率膨胀 30-40%
- **GOP**：I 帧到下一个 I 帧之间的帧序列，`-g 300` = 30fps × 10s

### VBV 码率约束模型

```
进水管：最大流速 = maxrate（6 Mbps）
桶容量 = bufsize（8 Mbit）
出水管：每帧编码输出的比特量（不稳定）

编码一帧前：
  - 检查桶里有多少水 + 本帧进水期间能再注入多少
  - 简单帧出水少 → 桶水位上升 → 为后续复杂帧攒"余量"
  - 复杂帧出水多 → 桶水位下降 → 只要桶不空，画质不受损
  - 桶不能透支 → 编码器确保本帧输出 ≤ 当前水位 + 本帧进水

bufsize/maxrate ≈ 缓冲时间窗口
  8000k/6000k ≈ 1.33s → 编码器最多借 1.33s 前攒下的余量维持短暂爆发质量
```

### CQ vs VBR

| | CQ 模式 | Constrained VBR |
|---|---|---|
| 目标 | 视觉质量恒定，不在乎体积 | 体积可控，质量尽量好 |
| 适用场景 | 离线转码、归档保存 | 流媒体、直播、存储受限 |
| 码率 | 不确定（可能 2 Mbps 也可能 20 Mbps） | 平均锚定，峰值受 maxrate 约束 |
| FFmpeg nvenc.c 行为 | **强制清零 averageBitRate + vbvBufferSize** | 正常传递所有参数 |
| maxrate 有效性 | ❌ 无效（bufsize=0 → VBV 不存在） | ✅ 有效（VBV 约束生效） |

### 低延迟编码效率损失

| 被砍掉的优化 | 效率损失 | 原因 |
|-------------|----------|------|
| `-bf 0`（无 B 帧） | +30~40% 码率 | B 帧利用双向参考，同等质量只需 P 帧的 1/3 比特 |
| `-rc-lookahead 0` | +10~15% 码率 | 无前瞻，每帧独立分配比特，无法"借"码率 |
| `-tune ll` | +5~10% 码率 | 低延迟缓冲策略限制内部优化空间 |

| 优先级 | 资料 | 说明 |
|--------|------|------|
| ⭐⭐⭐ | NVIDIA NVENC OBS 指南 | NVENC preset/tune/B 帧选择策略，最对口 |
| ⭐⭐⭐ | FFmpeg H.264 编码指南 | CRF/CQP/VBR/CBR 模式区别、maxrate/bufsize 交互 |
| ⭐⭐ | x264 参数指南：B 帧选择与压缩效率 | B 帧对码率影响（编码原理通用） |
| ⭐⭐ | H.264 Wikipedia | I/P/B 帧定义、参考帧机制、GOP 结构 |

## 七、Phase 1 卡顿根因深度分析

> 核心结论：**Phase 1 硬编卡顿不是 GPU/CPU 算力不足，而是 FFmpeg 管线延迟导致的时间戳错乱。**

### 7.1 证据链

| 证据 | 含义 |
|------|------|
| 软编 480p 全程无卡顿 | CPU/GPU 有余量，算力不是瓶颈 |
| NVENC 是 GPU 专用编码芯片 | 900p CQ28 30fps 对 NVENC 轻松，编码速度远超实时 |
| Phase 1 参数无低延迟优化 | 默认 lookahead 32 + B 帧 2-3 → 管线积压帧 |

### 7.2 Phase 1 管线延迟拆解

```
Phase 1 的 FFmpeg 管线：

屏幕捕获（ddagrab/gfxcapture）
  → hwdownload（GPU→CPU 内存搬运）
  → format 转换（bgra→yuv420p）
  → scale 缩放（900p）
  → NVENC 编码（B帧 + lookahead 默认值）
      ├── lookahead 缓冲：等待 32+ 帧（默认 -rc-lookahead 32）
      ├── B帧重排序：编码顺序 ≠ 显示顺序
      └── 编码延迟：3-4 帧后才输出第一帧
  → HLS muxer（要求 DTS 严格单调递增）
      → ts 切片写入磁盘
```

| 延迟源 | Phase 1 默认值 | 延迟量 | 说明 |
|--------|----------------|--------|------|
| `-rc-lookahead` | 32（NVENC 默认） | ~1 秒 | 编码器缓存 32 帧后才开始分配码率 |
| B帧重排序 | `-bf` 默认 2-3 | ~100-133ms | 编码顺序 vs 显示顺序差异 |
| hwdownload + format | 必须做 | ~5-10ms | GPU→CPU 内存搬运 |
| **总管线延迟** | — | **~1.1-1.2 秒** | 第一帧从捕获到 HLS 输出 |

### 7.3 卡顿机制：不是"编码慢"，是"管线在攒帧"

编码器不慢——它在等 lookahead 缓冲填满后才开始高速编码输出。但 HLS muxer 在等待期间拿不到数据，切片写入出现空窗期 → 用户看到卡顿。

**B 帧重排序带来更隐蔽的问题：DTS 不单调。**

```
显示顺序：  I₁  P₂  B₃  P₄  B₅  P₆
编码顺序：  I₁  P₂  P₄  B₃  P₆  B₅  ← B帧必须等后续P帧先编码
DTS：       0   1   3   2   5   4   ← 不是严格递增！
```

HLS muxer 要求 DTS 严格单调递增。B 帧重排序导致 DTS 回跳 → muxer 需额外处理 → 切片时间戳错乱 → 播放端画面跳帧/卡顿。

### 7.4 软编为什么没卡

Phase 1 软编参数：`-c:v libx264 -crf 28 -preset veryfast`（480p）

- 480p 像素量极小，编码几乎无延迟（每帧 <1ms）
- veryfast preset 不使用 lookahead（mbtree 等高级分析关闭）
- B 帧设置极保守（b-adapt=0, max_bframes=1）
- 总管线延迟 <50ms → 帧从捕获到输出几乎零等待

**软编没卡不是因为 CPU 强——是因为 480p + veryfast 的管线延迟几乎为零。编码速度慢，但输出节奏稳。**

### 7.5 对比核心差异

| | Phase 1 硬编 900p | Phase 1 软编 480p |
|---|---|---|
| 编码速度 | **快**（NVENC 专用芯片） | 慢（CPU 通用计算） |
| 管线延迟 | **高**（~1.1s，lookahead+B帧） | **低**（<50ms，无缓冲） |
| 输出节奏 | **间歇性**（攒一批→突发输出） | **稳定**（每帧即编即出） |
| DTS 时序 | **有回跳风险**（B帧重排序） | **单调递增**（无B帧问题） |
| 卡顿原因 | 管线延迟 + DTS 错乱 | 无 |

**一句话：硬编卡顿是"输出节奏不稳"，不是"编码速度不够"。**

## 八、FFmpeg 管线架构 vs NVENC SDK 直调

### 8.1 直播平台为什么能做到 1080p 6Mbps 保画质

OBS / Twitch / YouTube Live 推流推荐的 NVENC 参数：

| 参数 | OBS 默认（直播常用） | CoWatch 当前 |
|------|---------------------|--------------|
| 分辨率 | 1080p | 720p |
| 码率模式 | CBR/VBR（显式 `-b:v`） | CQ（质量优先） |
| `-b:v` | 6000k | 0 |
| `-bf` | 2 | 0 |
| `-rc-lookahead` | 20 | 0 |
| `-tune` | 无（或 `ull` 仅超低延迟场景） | `ll` |
| `-preset` | p5 或 p6 | p4 |
| 码率 | 6 Mbps（受控） | 10 Mbps（不受控） |

**直播平台用 B 帧 + lookahead + 较高 preset，照样不卡。** 因为 OBS 是单进程直接调用 NVENC SDK。

### 8.2 关键架构差异

| | OBS（直播平台） | CoWatch（FFmpeg 外部进程） |
|---|---|---|
| 编码器接口 | OBS 直接调用 NVENC SDK API | FFmpeg 命令行进程（spawn + pipe） |
| 帧传递 | GPU surface → NVENC，帧留在 GPU 上 | lavfi → hwdownload → CPU → encode（GPU↔CPU 搬运） |
| 音频处理 | OBS 内置 WASAPI，与应用同进程 | audio_capture → pipe:0 → FFmpeg（跨进程管道） |
| 输出 | RTMP 直推 / 本地录制 | HLS muxer + ts 切片写入 |
| 帧时序控制 | OBS 自主管理 PTS/DTS | FFmpeg 内部管线管理，应用层无控制 |
| 进程间通信 | 无（单进程） | 2 个独立进程 + 2 条 pipe |

**最核心差异：OBS 帧全程留在 GPU 上（零搬运），CoWatch 帧必须在 GPU↔CPU 间来回搬运 + 跨进程 pipe 传音频。**

这意味着 CoWatch 的 `-bf 0 + -tune ll + -rc-lookahead 0` **不是解决 NVENC 编码慢——是在补偿 FFmpeg 管线的额外延迟。**

### 8.3 NVENC SDK 直调的技术领域分类

| 层级 | 涉及的领域 | 离前端/后端的距离 |
|------|-----------|-----------------|
| 系统编程 | Windows API（DXGI Desktop Duplication、WGC API、WASAPI） | 🔴 完全不同 |
| GPU 编程 | NVENC SDK（C API，GPU surface 管理，CUDA interop） | 🔴 完全不同 |
| 多媒体工程 | H.264 NAL 解析、B帧重排序、PTS/DTS 管理、HLS mux | 🔴 完全不同 |
| 跨语言桥接 | C++ → Node.js N-API addon（ABI 兼容、内存管理、崩溃处理） | 🟡 半跨领域 |
| Electron 集成 | addon 加载、IPC 通信、多进程架构 | 🟡 已熟悉的领域 |

**只有最后一层是 JS/TS 开发者熟悉的，上面四层是系统编程 + 多媒体工程领域。**

| | 前端/后端 | NVENC SDK 直调所需 |
|---|---|---|
| 语言 | JS/TS → 纯逻辑 | C/C++ → 指针、内存管理、ABI |
| 错误处理 | try/catch → 日志 | 段错误 → 进程直接崩溃，无 error handler |
| 调试 | console.log / debugger | GDB/WinDbg → 需看寄存器和内存地址 |
| 并发 | async/await → 事件循环 | 多线程 + GPU 异步 → 管锁、竞态、回调时序 |
| 跨平台 | 浏览器适配 | 三个 OS 三套 API（Win DXGI / Mac VideoToolBox / Linux V4L2） |
| 文档质量 | MDN 级别（详尽） | NVIDIA SDK PDF（晦涩）+ Windows MSDN（散落） |

**预计学习曲线 4-6 周才能写出第一个可工作原型，之后还有无尽的兼容性坑。**
这是"进入一个全新工程领域"的难度，不是"学一门新语言"的难度。

### 8.4 方案路线图

| 阶段 | 方案 | 改动量 | 预期效果 | 适用时机 |
|------|------|--------|----------|----------|
| **短期** | 方案 B（bf1 + lookahead8） | 参数微调 | 码率降 ~20% | 立即可测试 |
| **中期** | 方案 A（离线重编码） | 新增流程 | 码率降 ~55%，画质更好 | 商业化前 |
| **长期** | NVENC SDK 直调 | 重构录制核心 | 录制+回放都优化 | 有系统编程资源时 |

## 九、录制+转码分离方案详细分析

> 基于方案 A（离线重编码）的两种执行模式分析。

### 9.1 转码参数

保持 CQ30 画质不变，只改编码效率参数（B帧 + lookahead + preset）：

```
ffmpeg -i original.ts \
  -c:v h264_nvenc -rc vbr -cq 30 -b:v 0 \
  -preset p7 -bf 2 -rc-lookahead 20 \
  -c:a copy \
  -f hls -hls_time 10 -hls_list_size 0 \
  output.m3u8
```

**预期效果：**
- 同 CQ30 画质，码率从 ~10 Mbps 降到 ~5 Mbps（编码效率恢复 ~50%）
- 视觉质量**不低于**录制版（全优化编码更高效，每比特承载更多视觉信息）
- 音频直通（`-c:a copy`），不重新编码

### 9.2 场景 A — 后台并行转码

**流程：**
```
用户停止录制 A → 后台开始转码 A
用户开始录制 B → 录制 B + 转码 A 同时进行
```

**资源竞争分析：**

| 资源 | 录制 B 占用 | 转码 A 占用 | 冲突风险 |
|------|------------|------------|----------|
| NVENC 芯片 | 1 session（低延迟参数） | 1 session（全优化参数） | ❌ 无——4060 支持多 session 并发 |
| NVDEC 芯片 | 不用 | 1 session（解码输入文件） | ❌ 无——录制不碰 NVDEC |
| GPU 3D 渲染 | 不用（ddagrab/gfxcapture 不走 3D 管线） | 不用 | ❌ 无——游戏独占 3D 管线 |
| 屏幕捕获 API | DXGI/WGC | 不用 | ❌ 无——转码不碰屏幕捕获 |
| CPU | ~10-20%（pipe + 格式转换 + HLS mux） | ~15-30%（demux + filter + mux） | ⚠️ **唯一潜在冲突点** |
| 磁盘 I/O | 写 ts 切片（~1.25 MB/s） | 读输入 + 写输出（~5-10 MB/s） | ⚠️ HDD 有风险，SSD 无压力 |
| 内存 | ~200-400 MB | ~300-500 MB | ❌ 无——现代系统充裕 |

**关键判断：录制和转码走的是完全不同的硬件路径。唯一共享的是 CPU 和磁盘 I/O。**

**CPU 冲突风险评估：**

Phase 1 卡顿是结构性延迟（每帧延迟 1+ 秒），而场景 A 的 CPU 冲突是**偶发性延迟**——转码 CPU 峰值时可能短暂抢占录制管线的 CPU 时间，导致偶尔掉帧（1 小时录制中可能掉 2-3 帧），用户基本无感知。

| 系统配置 | 卡顿风险 | 说明 |
|----------|----------|------|
| 6 核+ CPU + SSD | **极低** | CPU 和 I/O 都有富余 |
| 4 核 CPU + SSD | **低** | CPU 偶尔紧张，OS 调度能保障录制 |
| 4 核 CPU + HDD | **中等** | 磁盘 I/O 可能争抢 |
| 4 核以下 CPU | **较高** | 不建议后台并行转码 |

**降低风险的措施：**
- 转码进程设为低优先级（`spawn` 时传 `priority: 'below normal'`）
- 转码用 p5 而非 p7（减少单帧编码时间，降低 CPU 峰值）
- 转码限制线程数（`-threads 2`），给录制管线留 CPU 余量
- 监控录制帧率，掉帧率 >5% 时自动暂停转码

**与 Phase 1 卡顿对比：**

| | Phase 1 卡顿 | 场景 A 潜在卡顿 |
|---|---|---|
| 性质 | **结构性**——每帧延迟 1+ 秒 | **偶发性**——CPU 峰值时偶尔掉帧 |
| 频率 | 持续，每帧都卡 | 1 小时可能掉 2-3 帧 |
| 用户感知 | 明显卡顿 | 基本无感知 |
| 根因 | lookahead 32 + B 帧重排序 | 转码 CPU 峰值抢占 |

### 9.3 场景 B — 手动批量转码

**流程：**
```
用户录制视频 A → 本地保存
用户录制视频 B → 本地保存
用户全部录制结束后 → 手动触发 A 和 B 的转码
```

**零卡顿风险**——录制已结束，CPU/GPU 全部可用于转码。

**转码速度估算（RTX 4060，720p 30fps）：**

| 参数组合 | 估算编码速度 | 11 分钟视频 | 1 小时视频 |
|----------|-------------|------------|-----------|
| p4 + bf0 + la0（当前录制参数） | ~400-500 fps | ~40-50 秒 | ~3.5-4.5 分钟 |
| p6 + bf2 + la20 | ~200-300 fps | ~66-99 秒 | ~6-9 分钟 |
| p7 + bf2 + la20（推荐离线转码） | ~150-250 fps | ~80-132 秒 | ~7.2-12 分钟 |

> fps = 编码器输出帧率，远超实时 30fps。转码耗时 = 视频总帧数 / 编码速度。

**实际预期：**
- 11 分钟视频，p7 + bf2 + la20，SSD 系统：**约 1.5-2.5 分钟**
- 1 小时视频：**约 7-12 分钟**

**影响因素：**

| 因素 | 影响 |
|------|------|
| SSD vs HDD | SSD 几乎无影响；HDD 可能增加 30-60 秒 |
| 输入是单个 ts 还是多个切片 | 多个切片需先 concat，增加 10-20 秒 |
| CPU 性能 | demux/mux 需 CPU，但 720p 下不是瓶颈 |
| GPU 温度 | 游戏刚结束 GPU 温度高可能降频 → 速度降 10-20% |

### 9.4 场景选择建议

| | 场景 A（后台并行） | 场景 B（手动批量） |
|---|---|---|
| 用户体验 | 录完 B 后 A 已转码完成，无等待 | 录完后需等待转码（1.5-2.5 min/11min 视频） |
| 卡顿风险 | 低（6 核+SSD）/ 中（4 核+HDD） | **零** |
| 转码速度 | 略慢（CPU/IO 竞争） | 全速 |
| 实现复杂度 | 中（并发控制 + 优先级 + 监控） | 低（串行处理） |
| 适用场景 | 连续录制多段视频 | 录制一段/几段后统一处理 |

**建议：先做场景 B，后续升级为场景 A。**

理由：
1. 场景 B 零风险，实现简单——`stop()` 回调后串行触发转码
2. 1.5-2.5 分钟等待在游戏复盘场景下完全可接受（用户录完本来就需要休息/回顾）
3. 场景 A 可作为 v2 优化——在场景 B 稳定后加"后台转码"开关

## 十一、三方案对比与商业化定位

> 基于 Phase 1~3 的演变历程和根因分析，将录制优化方向整理为三种面向不同用户群的商业化方案。

### 11.1 方案定义

| | 方案 1（当前代码） | 方案 2（录制+转码双队列） | 方案 3（录制+转码彻底分离） |
|---|---|---|---|
| **核心思路** | 极速编码保不卡顿，画质妥协 | 录制保不卡顿，转码二次压缩 | 录制保不卡顿，手动触发转码 |
| **录制参数** | 720p CQ30 bf0 la0 tune ll p4 | 960p CQ30 bf0 la0 tune ll p4 | 960p CQ30 bf0 la0 tune ll p4 |
| **转码参数** | 无 | p7 bf2 la20 CQ30（后台并行） | p7 bf2 la20 CQ30（手动触发） |
| **GPU 占用** | 游戏 + 录制 | 游戏 + 录制 + 转码 | 游戏 + 录制 |
| **录制阶段码率** | ~10 Mbps | ~17 Mbps（仅存本地，不上传） | ~17 Mbps（仅存本地，不上传） |
| **最终上传码率** | ~10 Mbps | ~5-6 Mbps（转码后上传） | ~5-6 Mbps（转码后上传） |
| **最终画质** | 720p 低延迟级 ≈ 全优化 5-6Mbps | **960p 全优化级** ≈ 5-6Mbps | **960p 全优化级** ≈ 5-6Mbps |
| **实时性** | 录完即可上传回看 | 最后一段延迟 1.5-2.5min | 用户手动触发转码后上传 |
| **上传带宽需求** | 10Mbps（挑战 100M 上行） | 5-6Mbps（100M 上行可承受） | 5-6Mbps |

### 11.2 画质对比说明

**为什么方案 2/3 的 960p 全优化级画质明显优于方案 1 的 720p 低延迟级：**

| | 方案 1 | 方案 2/3（转码后） |
|---|---|---|
| 分辨率 | 720p (1280×720) | 960p (~1707×960) |
| 像素量 | 921,600 | ~1,637,760（1.78×） |
| 编码效率 | 低（bf0 + la0 + tune ll） | 高（bf2 + la20 + p7） |
| 每比特承载的视觉信息 | 低 | 高 |
| 码率 | ~10 Mbps | ~5-6 Mbps |
| 等效全优化码率 | ~5-6 Mbps | ~5-6 Mbps（已为全优化） |

**关键结论：** 方案 2/3 在更低码率下提供了更高分辨率 + 更高编码效率的画质。这不是"降码率换画质"，而是"提升编码效率让每比特更有价值"。

### 11.3 方案 2 卡顿风险再确认（RTX 3060+）

**最低显卡门槛：RTX 3060（Ampere 架构，1 NVENC 引擎，12GB 显存）**

**GPU 侧无冲突——三个任务走不同硬件单元：**

| GPU 硬件单元 | 游戏占用 | 录制占用 | 转码占用 | 冲突？ |
|---|---|---|---|---|
| 3D 渲染管线 | ✅ 游戏渲染 | ❌ 不碰 | ❌ 不碰 | ❌ |
| NVENC 编码器 | ❌ | ✅ 1 session | ✅ 1 session | ❌ 支持并发 |
| NVDEC 解码器 | ❌ | ❌ | ✅ 1 session | ❌ |
| 显存 | ~2-4GB | ~200-400MB | ~300-500MB | ❌ 12GB 充裕 |

**CPU 侧竞争可控——RTX 3060 典型搭配 6 核 12 线程 CPU：**

| CPU 负载 | 游戏 | 录制 | 转码（低优先级） | 合计 | 余量 |
|---|---|---|---|---|---|
| 6 核 12 线程 | ~10-20% | ~10-20% | ~15-30%（below normal） | ~35-70% | 充裕 |

**Phase 1 卡顿 vs 方案 2 潜在影响的性质完全不同：**

| | Phase 1 卡顿 | 方案 2 潜在影响 |
|---|---|---|
| 性质 | **结构性**——每帧延迟 1+ 秒 | **偶发性**——CPU 峰值时偶尔掉帧 |
| 频率 | 持续，每帧都卡 | 30 分钟可能掉 1-2 帧 |
| 用户感知 | 明显卡顿 | **基本无感知** |
| 根因 | 管线延迟（lookahead 32 + B 帧重排序） | 转码 CPU 峰值短暂抢占 pipe I/O |
| 解法 | 砍编码优化（bf0 + la0） | 转码设低优先级 + 监控掉帧率 |

**RTX 3060 配置下方案 2 卡顿风险判定：极低。**

防护措施：
- 转码进程设 `priority: 'below normal'`
- 转码用 `-threads 2`，给录制管线留 CPU 余量
- 监控录制帧率，掉帧率 >5% 时自动暂停转码
- 转码 preset 用 p5（而非 p7），降低 CPU 峰值

### 11.4 用户画像与商业化定位

| 方案 | 目标用户 | 典型场景 | 核心诉求 | 实时性需求 |
|---|---|---|---|---|
| **方案 1** | 陌生人游戏分锅 | 单局游戏后立即分享 | 录完立即可看、可分享 | 拉满 |
| **方案 2** | 熟人长期游戏（中上配置） | 一晚多局，前面的可以先复盘 | 画质好、成本低、前面的视频不用等 | 可接受最后一段延迟 1-2min |
| **方案 3** | 配置差或无实时需求 | 偶尔录制，不急于分享 | 画质好、成本最低、无卡顿风险 | 无 |

### 11.5 方案 2 的分辨率选择考量

**为什么方案 2/3 录制阶段用 960p 而非 720p：**

既然录制阶段的码率不受限（CQ30 无 VBV 约束，且不上传只存本地），提高分辨率只增加本地文件大小，不影响：
- 录制时卡顿（NVENC 编码 960p 和 720p 的速度差异极小）
- 上传带宽（录制阶段不上传）
- 最终成本（转码后码率由 VBV 约束控制）

| 录制分辨率 | 本地文件大小（11min） | 转码后码率 | 转码后画质 |
|---|---|---|---|
| 720p | ~900MB | ~5 Mbps | 720p 全优化级 |
| 960p | ~1.5GB | ~5-6 Mbps | **960p 全优化级** |
| 900p | ~1.3GB | ~5-6 Mbps | 900p 全优化级 |

**960p 录制 → 转码后 5-6Mbps 的性价比最优：** 本地多占 600MB（用户磁盘一般不紧张），换来 960p 分辨率提升，视觉质量显著优于 720p。

## 十二、方案 2 的升级变种：逐切片转码（延迟从「一局」降到「一个切片」）

> 方案 2 原始设计是「录制整段视频 → stop 后后台转码 → 上传」，延迟单位为一局游戏（1.5-2.5min）。
> 逐切片转码变种将转码粒度从「一局」降到「一个 HLS 切片」（10s），延迟从分钟级降到秒级。

### 12.1 核心思路

当前架构**已经是逐切片处理**的：

```
FFmpeg 录制 → 写 seg001.ts → chokidar 'add' → uploadSegment() → 上传后端
                写 seg002.ts → chokidar 'add' → uploadSegment() → 上传后端
                写 seg003.ts → chokidar 'add' → uploadSegment() → 上传后端
                ...
```

逐切片转码在 chokidar 检测到切片后、uploadSegment 之前插入转码步骤：

```
FFmpeg 录制 → 写 seg001.ts → chokidar 'add' → transcodeSegment() → 写 seg001_opt.ts → uploadSegment() → 上传后端
```

**关键点：不需要 pipe，和当前架构一样是基于磁盘文件的逐切片传递。** 音频使用 pipe（audio_capture → pipe:0 → FFmpeg），但视频切片从来就不是 pipe——是 FFmpeg 写文件、chokidar 读文件。

### 12.2 B 帧边界问题——在逐切片模式下不存在

逐切片模式下 B 帧的跨切片引用问题**自动消失**：

HLS 切片本身就是 GOP 对齐的——每个 ts 切片必须以 IDR（关键帧）开头，这是 HLS 规范的要求。代码中 `-g 600`（60fps × 10s）已确保这一点。

```
seg001.ts 内部帧序列：
  IDR → P → P → ... → P → P

用 -bf 2 重编码后：
  IDR → P → B → B → P → B → B → ... → P → B → B → P
```

切片内所有 B 帧只引用本切片内的 I/P 帧。切片开头是 IDR（全量帧，不参考任何其他帧），因此没有跨切片引用的问题。

`-rc-lookahead 20` 在切片末尾确实看不到下一个切片的前 20 帧，但每个切片有 600 帧（10s × 60fps），只有最后 ~3% 的帧受影响，对整体码率优化效果的影响可忽略。

### 12.3 延迟量化

**方案 2 原始版（整段重编码）：**

| 步骤 | 耗时 |
|------|------|
| 录制整段视频 | 11min |
| stop → 全段转码 | 1.5-2.5min |
| 上传 | ~30s |
| **总延迟** | **2-4 分钟** |

**逐切片转码变种：**

| 步骤 | 耗时 | 说明 |
|------|------|------|
| FFmpeg 写切片 | 每 10s 一个 | `-hls_time 10` |
| chokidar 检测 | ~500ms | `awaitWriteFinish stabilityThreshold` |
| spawn 转码 FFmpeg | ~300-500ms | 进程启动 |
| 转码 600 帧（p5） | ~1.5-2.5s | 720p，NVENC p5 |
| 上传切片（固定步长限速） | ~3-15s（无积压）/~10-30s（有积压） | 无积压时全速，有积压时 3-7Mbps |
| **每个切片的总延迟** | **~6-19s** | 切片写入后 6-19s 可回放 |

**用户 stop 后的延迟：**

- 最后一个切片：写入 + 检测 + 转码 + 上传 ≈ **10-20 秒**
- 前面所有切片：**已经在 COS 上可回放**
- **总延迟 = ~10-20 秒**

### 12.4 资源竞争分析——脉冲式 vs 持续式

**关键区别：方案 2 原始版是持续转码，逐切片变种是间歇性脉冲转码。**

方案 2 原始版：转码是持续运行的进程，CPU/GPU 占用持续 1.5-2.5 分钟。

逐切片变种：每 10 秒做一次 1.5-2.5 秒的短脉冲转码，**75-85% 时间完全空闲**。

| 资源 | 录制占用 | 逐切片转码占用 | 冲突风险 |
|------|----------|---------------|----------|
| NVENC | 1 session（持续） | 1 session（1.5-2.5s/10s，脉冲） | ❌ 3060+ 支持并发 |
| NVDEC | 不碰 | 1 session（脉冲） | ❌ 录制不用 NVDEC |
| GPU 3D | 游戏独占 | 不碰 | ❌ |
| CPU | ~10-20%（pipe + mux） | ~10-20%（1.5-2.5s/10s，脉冲） | ⚠️ 但 75-85% 时间空闲 |
| 磁盘 I/O | 写 ~1.2MB/s | 读+写 ~8MB/s（1.5-2.5s/10s） | ❌ SSD 无压力 |
| 显存 | 游戏纹理 | 转码缓冲 ~200MB（短暂） | ❌ 3060 12GB 充裕 |

**CPU 是唯一潜在冲突点，但转码只在每个 10 秒窗口的前 2-3 秒活跃。** 录制管线的时敏操作（pipe 读、HLS mux）分散在整 10 秒窗口内，大概率落在转码空闲期。即使偶尔重叠，影响也只是单个切片掉 1-2 帧，不是持续卡顿。

防护措施：
- 转码 FFmpeg 进程 `priority: 'below normal'` → Windows 调度器优先保障录制进程
- 转码用 `p5` 而非 `p7`（单切片 600 帧，p5 约需 2-3s，CPU 峰值更低）
- 转码队列串行执行（避免多个转码同时争 CPU）
- 监控录制帧率，掉帧率 >5% 时自动暂停转码队列

### 12.5 转码参数

```
ffmpeg -i seg001.ts \
  -c:v h264_nvenc \
  -rc vbr -cq 28 \
  -preset p5 \
  -bf 2 \
  -rc-lookahead 20 \
  -c:a copy \
  -f hls -hls_time 10 \
  -hls_segment_filename seg001_opt.ts \
  seg001_opt.m3u8
```

说明：
- `-cq 28`：交付质量目标，低于录制层 CQ23（源质量高于交付质量，避免世代损失）
- 纯 CQ 模式：NVENC 在 CQ 模式下清零 vbvBufferSize，maxrate/bufsize 为死参数已移除。码率随内容复杂度自由波动，上传带宽由 `upload/throttle.ts` 固定步长限速控制（无积压时全速，有积压时 3-7Mbps，硬顶封死）
- `-preset p5`：比 p7 快 ~50%，CPU 峰值更低，适合脉冲式转码
- `-bf 2`：恢复 B 帧，编码效率提升 ~30%
- `-rc-lookahead 20`：恢复前瞻，码率分配更合理
- `-c:a copy`：音频直通，不重新编码

### 12.6 架构改动量——极小

**核心改动：在 chokidar → upload 流程中间插入一步**

```
当前流程：
  chokidar 'add' → uploadSegment(filePath)

新流程：
  chokidar 'add' → transcodeSegment(filePath) → uploadSegment(transcodedPath)
```

**需要新增的代码：**

**需要修改的代码：**

**不需要改的：**
- 录制参数（CQ23 + bf0 + la0 + 720p@60fps，高质量源捕获）

## 十三、三层解耦架构设计（录制-转码-上传分离）

### 13.1 问题背景

当前架构（含逐切片转码变种）存在一个硬伤：**网络不稳定时会终止录制**。

现有代码中，`consecutiveFailRounds >= 5` 或 `pendingQueue >= 15` 会触发 `abort`，直接停止录制。这意味着用户在弱网环境下录制会被意外中断，丢失后续画面。

**核心矛盾：** 录制（本地 GPU/CPU 操作）和上传（网络 I/O）被耦合在同一个流程中，网络问题被向上传导为录制停止。

### 13.2 设计目标

| 目标 | 说明 |
|------|------|
| 录制永不因网络停止 | 录制是纯本地操作，网络状态不应影响 |
| 转码不碰网络 | 转码是纯本地操作，网络再差也全速进行 |
| 上传 best-effort 降速 | 网络差时上传退避拉长，但不停录制 |
| Stop 后未传切片持久化 | 切片信息持久化到本地，下次启动自动补传 |

### 13.3 三层架构

```
┌─────────────────────────────────────────────────────────┐
│                    录制层（Recording）                     │
│  FFmpeg 低延迟捕获 → seg001.ts seg002.ts seg003.ts ...   │
│  [永不因网络停止]  [只关心屏幕捕获+编码，不感知网络状态]      │
└──────────────┬──────────────────────────────────────────┘
               │ chokidar 'add' 检测新切片
               ▼
┌─────────────────────────────────────────────────────────┐
│                    转码层（Transcode）                     │
│  spawn FFmpeg (p5/bf2/la20/CQ28) → seg001_opt.ts ...    │
│  [纯本地，不碰网络]  [转码完成立即删除原始切片]  [串行队列]    │
│  [脉冲式：2-3s/10s 活跃，70-80% 空闲]  [进程优先级 below normal] │
└──────────────┬──────────────────────────────────────────┘
               │ 转码完成事件
               ▼
┌─────────────────────────────────────────────────────────┐
│                    上传层（Upload）                       │
│  uploadSegment → pRetry + 指数退避 → 后端                 │
│  [best-effort]  [网络差退避拉长：10s→20s→40s→80s→160s]     │
│  [不通知录制层停止]  [积压切片暂存本地磁盘]  [上传成功删切片]  │
└─────────────────────────────────────────────────────────┘
```

### 13.4 各层职责详解

#### 录制层

| 属性 | 值 |
|------|-----|
| 编码器 | h264_nvenc |
| 参数 | `-preset p4 -tune ll -rc-lookahead 0 -bf 0 -rc vbr -cq 23 -b:v 0` |
| 分辨率 | 720p（maxWidth 1280） |
| 帧率 | 60fps（`-vsync cfr -r 60`，ddagrab/gfxcapture 均设 60） |
| 切片时长 | 10s |
| 原始码率 | ~18-35 Mbps（CQ23 + 720p@60fps，约22-44MB/片） |
| 网络感知 | **无** — 不监听网络状态，不因网络停止 |

录制层只做一件事：捕获屏幕 → 编码 → 写 HLS 切片到磁盘。chokidar 监听切片目录，检测到新切片后交给转码层。

**与当前代码的差异：** 移除 `consecutiveFailRounds >= 5` 和 `pendingQueue >= 15` 的 abort 逻辑。录制永不因网络停止。

#### 转码层

| 属性 | 值 |
|------|-----|
| 编码器 | h264_nvenc |
| 参数 | `-preset p5 -bf 2 -rc-lookahead 20 -rc vbr -cq 28 -b:v 0`（纯 CQ，无 maxrate/bufsize） |
| 输入 | 原始切片 `seg001.ts`（~22-44MB） |
| 输出 | 转码切片 `seg001_opt.ts`（~3-6MB） |
| 执行方式 | 串行队列，一次只转一个切片 |
| 进程优先级 | below normal（不和录制抢 CPU） |
| 网络感知 | **无** — 纯本地操作 |

每个切片 600 帧（10s × 60fps），p5 转码约 2-3 秒。每 10 秒窗口中只有 2-3 秒活跃，70-80% 时间空闲。

**转码完成后立即删除原始切片**，释放磁盘空间。原始切片（~22-44MB）比转码切片（~3-6MB）大 5-7 倍，尽快删除避免磁盘积压。

**CQ 分工原理：** 录制层 CQ23 < 转码层 CQ28，源质量高于交付质量。转码层在高质量源上做压缩优化（p5/bf2/la20），避免"在压缩品上再压缩"的世代损失。NVENC 硬件编码速度不受 CQ 值影响，录制层低 CQ 的代价仅是中间文件更大（用完即删）。

**纯 CQ 模式（无码率上限）：** NVENC 在 CQ 模式下会清零 vbvBufferSize，导致 maxrate/bufsize 为死参数。与其留着误导，不如直接移除——让 CQ 自由分配码率，复杂场景多给比特是正确的（人眼可感知）。文件大小随内容复杂度波动是 feature 不是 bug。上传带宽控制由 `upload/throttle.ts` 自适应处理（无积压时全速上传，有积压时固定步长上调 + 硬顶封死 3-7Mbps），不在编码层做。

**转码失败的 fallback：** 如果转码失败（如 FFmpeg 崩溃），将原始切片直接送入上传队列（不转码），保证不丢数据。

#### 上传层

| 属性 | 值 |
|------|-----|
| 协议 | HTTP POST（net.fetch + ReadableStream body） |
| 限速 | 自适应（无积压时全速，有积压时 AIMD 1-20Mbps，`upload/throttle.ts`） |
| 超时 | 动态计算（30s~120s，基于文件大小和限速速率） |
| 重试 | pRetry + 指数退避 |
| 退避序列 | 1s → 2s → 4s → ... → 60s（上限）+ ±50% jitter |
| 并发 | 串行（一次 1 个，`isUploading` 标志防并发） |
| 网络感知 | **有** — 退避拉长等效降低吞吐量 |

上传层是唯一感知网络的层。网络差时退避拉长，等效降低上传吞吐量，但**不通知录制层停止**。积压的转码切片暂存在本地磁盘，等网络恢复后自动补传。

**上传成功后删除转码切片**，释放磁盘空间。

### 13.5 GPU 资源分配

三者走不同硬件单元，互不冲突：

| GPU 硬件单元 | 游戏 | 录制 | 转码 |
|---|---|---|---|
| 3D 渲染管线 | ✅ 占用 | ❌ | ❌ |
| NVENC 编码器 | ❌ | ✅ 1 session（持续） | ✅ 1 session（脉冲 2-3s/10s） |
| NVDEC 解码器 | ❌ | ❌ | ✅ 1 session（脉冲） |
| 显存 | 占用 | ~200MB | ~300MB（脉冲） |

**RTX 3060+ 门槛：**
- 支持 3+ NVENC session 并发（录制 1 + 转码 1 + 预留 1）
- 显存 12GB 充裕（游戏 4-8GB + 录制 200MB + 转码 300MB）
- CPU 6 核 12 线程可处理脉冲转码

**唯一共享资源是 CPU**，但转码是脉冲式（70-80% 空闲），且进程优先级设为 below normal，冲突极低。

### 13.6 磁盘空间管理

> **重要澄清：** "三层"是职责上的抽象，不是物理上的文件并存。一个切片的生命周期是线性流转的：
> `seg001.ts`（原始）→ 转码 ~2-3s → 删除原始 → `seg001_opt.ts`（转码）→ 上传 → 删除转码。
> 同一切片不可能同时以原始和转码两种形态存在。转码过程中两者短暂共存仅 ~2-3 秒。

三层解耦后，磁盘上同时存在的文件类型：

| 文件类型 | 命名 | 大小/片 | 生命周期 |
|----------|------|---------|----------|
| 原始切片 | `seg001.ts` | ~44-75MB | 录制产生 → 转码完成删除 |
| 转码切片 | `seg001_opt.ts` | ~5-7.5MB | 转码产生 → 上传完成删除 |
| 持久化切片 | `seg001_opt.ts` | ~5-7.5MB | Stop 时未上传 → 持久化到管理列表 |

**网络正常时**，磁盘峰值约 2-3 片（1 原始 + 1 转码中 + 1 上传中）≈ 55-90MB。

**网络极差时**，转码切片积压。假设 30 分钟对局、10s 切片 = 180 片 × 6.5MB ≈ 1.17GB。需要设置磁盘水位线，超过阈值时上传层降速（不停止录制），或提示用户磁盘空间不足。

### 13.7 Stop 流程

```
用户点击 Stop
    │
    ├─ 1. 录制层：FFmpeg 进程终止，不再产生新切片
    │
    ├─ 2. 转码层：继续清空转码队列
    │      （已在磁盘上的原始切片继续转码，1-2s/片，通常 0-2 片）
    │
    ├─ 3. 上传层：检查上传队列积压量（未上传的已转码切片数）
    │      │
    │      ├─ < 阈值（5片）：等待全部上传完成 → 调 finish → 清理临时目录
    │      │
    │      └─ ≥ 阈值（5片）：持久化未上传切片信息到本地 → 调 finish → 退出
    │
    └─ 4. 持久化内容：
           ├─ 未上传的已转码切片（seg*_opt.ts，~6-8MB/片）
           ├─ 未被转码的原始切片（seg*.ts，~25-43MB/片）— 通常 0-2 片
           └─ 元数据 JSON（objectKey、文件路径、状态、录制ID）
```

**阈值 5 片 = 50 秒视频 ≈ 30-37MB 转码切片。** 网络恢复后几秒即可传完，不值得让用户等。

## 十四、Phase 4a 验证失败 — `fps=30` 滤镜无效的根因与修复

### 14.1 验证结果

Phase 4a 低延迟参数（`p4 + tune ll + la0 + bf0`）应用后：

| 项目 | 结果 |
|------|------|
| 游戏体验 | ✅ 无卡顿 |
| 录制回放 | ❌ **严重卡顿** |
| 参数状态 | `fps=30` 滤镜已加，但无效 |

结论：游戏卡顿修好了，但录制视频卡顿——问题不在捕获，在编码后 PTS 归一化方式。

### 14.2 根因：`fps=30` 滤镜在编码前归一化，但 NVENC 覆盖了 PTS

FFmpeg 管线中 PTS 的流转路径：

```
ddagrab（VFR 捕获）
  → hwdownload + format + scale（格式转换）
  → fps=30 滤镜（❌ 此处归一化 PTS，但...）
  → h264_nvenc 编码（⚠️ NVENC 重新生成 PTS，覆盖上方归一化结果）
  → HLS muxer（写入文件，PTS 已非均匀）
```

**关键问题：`h264_nvenc` 在极低延迟模式（`p4 + tune ll + rc-lookahead 0`）下逐帧立即输出，编码器根据自身节奏重新打 PTS。** `fps=30` 滤镜在编码前把 PTS 归一化了，但 NVENC 编码后又给了一遍新的 PTS，之前的归一化被覆盖。

### 14.3 修复：移除 `fps=30` 滤镜，改用 `-vsync cfr -r {target_fps}`（muxer 阶段强制 CFR）

`-vsync cfr` 的作用点在**封装器（muxer）阶段**，是整个管线的最后一步，在编码器输出之后、写入文件之前：

```
ddagrab（VFR 捕获）
  → 格式转换
  → h264_nvenc 编码（NVENC 重新生成 PTS）
  → HLS muxer（✅ -vsync cfr 在此处强制均匀 PTS，不受编码器影响）
```

**与 `fps=N` 滤镜的本质区别（帧率无关，以下以 60fps 为例）：**

| | `fps=60` 滤镜 | `-vsync cfr -r 60` |
|---|---|---|
| 作用阶段 | 编码前（滤镜链） | 封装时（muxer） |
| 是否能抵抗编码器 PTS 覆盖 | ❌ 不能 | ✅ 能（最后一步） |
| 帧丢/补位置 | 原始帧（编码前） | 编码后数据包（muxer） |
| 适用场景 | 通用 | **硬件编码器（NVENC/QS/AMF）推荐** |

### 14.4 代码改动（`electron/handlers/recorder/index.ts`）

**改动 1：** 移除 Windows `winScaleFilter` 中的 `,fps=30`

```typescript
// 修复前
const winScaleFilter = `scale=w='min(iw\,${maxWidth})':h=-2,format=yuv420p,fps=30`;

// 修复后
const winScaleFilter = `scale=w='min(iw\,${maxWidth})':h=-2,format=yuv420p`;
```

**改动 2：** 在编码器参数之后、GOP 参数之前，插入 `-vsync cfr -r {target_fps}`

```typescript
// 新增输出参数（统一输出参数，当前帧率 = 60fps）
'-vsync', 'cfr', '-r', '60',
'-g', String(60 * HLS_SEGMENT_DURATION),  // GOP = 600 帧 = 10 秒（60fps × 10s）
```
